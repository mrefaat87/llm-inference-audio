Tokenization mechanics new

BPE step by step, vocabulary sizing, and why tokenizer design is now an infrastructure decision

How BPE (Byte Pair Encoding) works

BPE builds a vocabulary by iteratively merging the most frequent character pairs:

  • Initialize: Start with individual characters. "lower" → ['l','o','w','e','r']
  • Count pairs: Scan entire training corpus for frequency of adjacent pairs.
  • Merge most frequent: If "lo" appears 500 times, merge into a single token "lo". Add to vocabulary.
  • Repeat: Continue until target vocabulary size (32K, 64K, 128K). The result is a merge table — an ordered list of merge rules replayed during inference tokenization.

SentencePiece (Google) differs in that it treats input as raw bytes with no whitespace assumptions — critical for languages without word boundaries (Chinese, Japanese, Thai). Uses "▁" to represent spaces, making tokenization fully reversible.

Vocabulary size is a direct infrastructure trade-off:

Why this is an infrastructure decision
  • Capacity planning: Token density varies by language. A model handling 100 req/s in English might only handle 30 req/s in Japanese.
  • KV cache budgeting: Token count determines memory consumption. Tokenizer fertility is a first-order variable in your KV cache capacity model.
  • Prefix caching hit rates: Tokenizers that produce consistent tokenizations for common prefixes get better cache hit rates.
  • Cost attribution: Token-based pricing means the tokenizer directly determines revenue per request. Changing the tokenizer between model versions changes pricing.

Embeddings — what they are and when they're calculated

The very first step in every forward pass — converting discrete tokens into continuous vectors

Why tokens need to become vectors at all

A neural network can only do math on numbers — specifically, floating-point vectors. The text you type is first broken into tokens (word pieces, roughly), and each token is assigned an integer ID from the vocabulary. "Bank" might be token ID 4521. But you cannot feed the integer 4521 into a matrix multiply in any meaningful way — the model would think "bank" is 4521 times more important than "a" (ID ~1). The integer ID is just a lookup key, not a meaningful number.

The solution: maintain a learned lookup table called the embedding matrix, of shape (vocab_size × d_model). Each row is the learned vector representation of one token. To "embed" a token, you just fetch its row. For GPT-3: 50,257 vocabulary tokens × 12,288 d_model = 617M parameters just for the embedding table.

These vectors are learned during training. Tokens that appear in similar contexts end up with similar vectors. After training, "king" and "queen" are nearby. "Bank" (financial) and "bank" (river) may occupy different neighborhoods depending on context.

Positional embeddings — encoding sequence order

The embedding table gives each token its semantic identity — but says nothing about where in the sequence it appears. "Dog bites man" and "Man bites dog" contain the same tokens; their meaning differs entirely by position. Positional embeddings add position information to each token vector.

When exactly embeddings are calculated during inference

There are two phases in LLM inference — understanding these is fundamental to everything that follows in the Serving sections:

  • Prefill (also called "prompt processing"): You feed in the entire user prompt at once. All tokens are embedded in parallel — the full embedding table is indexed simultaneously for every token in the prompt. The model processes them all in one forward pass, computing all the K and V vectors that will be needed later. This happens once, at the very start, before any generation begins. Prefill is compute-bound — the bottleneck is raw arithmetic throughput (how fast the GPU can do math).
  • Decode (also called "generation"): You generate one new output token at a time. Each generated token is embedded immediately before the next decode step begins. This embedding lookup is essentially instant — it's just a memory fetch. Decode is memory-bandwidth-bound — the bottleneck is how fast you can load model weights from HBM to the compute units, not the math itself. The GPU's arithmetic units often sit idle waiting for data.
A common misconception: during decode, do previous tokens get re-embedded on every step? No. Their embedding was computed during prefill, and their K and V vectors were computed from those embeddings. Those K and V vectors are stored in the KV cache and reused. Re-embedding would be wasteful. The only new embedding cost per decode step is for the single new token just generated.
Weight tying — a memory optimization worth knowing

The embedding table has shape (vocab_size × d_model). The output projection at the end of the model — which converts the final layer's hidden states back into logits (raw, unnormalized scores — one per vocabulary token — that represent how likely each token is to be the next word; these get passed through softmax to become actual probabilities) over the vocabulary — also has shape (d_model × vocab_size), which is exactly the transpose. Some models (GPT-2, many others) "tie" these two matrices — they share the same weights, just transposed. This saves ~617M parameters for GPT-3-scale models with no meaningful quality loss, because the embedding table and output projection are semantically related (both map tokens to the same d_model space).

Deep Dive — Why tying works, and when it hurts

Why it works: If the model learns a coherent semantic geometry, the output logit for token t given hidden state h should be proportional to cosine similarity of h with E[t]. Tying forces E = UT, making this exact: the prediction score is the dot product of h with the token's input embedding. This encourages the embedding space to directly encode generation probability — good regularization at small-to-medium scale.

When it hurts (at scale): During training, gradients from next-token prediction (through the output projection) are much larger and more frequent than gradients through the input embedding path. The shared matrix gets shaped primarily to serve output projection, degrading input representation quality. There's also a geometric conflict: some tokens should be semantically similar (synonyms, close in embedding space) but have very different conditional generation probabilities. Tying cannot optimize for both. This is why most large frontier models (LLaMA-3, Mistral, Qwen, DeepSeek) untie embeddings at scale. Small models (GPT-2 level) still benefit from the regularization.

Q, K, V — queries, keys, and values

The three projections that power attention — built from the bank and river example

Before diving in, three foundational terms. A token is a word or word-piece — the smallest unit the model processes. The sentence "I don't like cats" might be split into tokens: ["I", "don", "'t", "like", "cats"]. A vector is just a list of numbers (e.g., 128 floating-point values) that represents something in a mathematical space the model can operate on. An embedding is the process of converting a token into a vector — the model learns a lookup table during training where each token maps to a specific vector of numbers (covered in detail in the Embeddings section).

Every token in a sequence needs to figure out which other tokens are relevant to it. Attention is the mechanism that does this. Q, K, and V are the three separate vector projections that make attention work — and the best way to understand them is through a concrete example.

Take the sentence: "The bank near the river was flooded." followed by: "It was too damaged to reopen." The model must figure out what "it" refers to — "bank" or "river." This is exactly the problem Q, K, and V solve.

What each projection does
Q — Query — "what am I looking for?"
Each token generates a Query vector that encodes what it is searching for. It's the question this token is asking of the rest of the sequence. The Query vector is computed by multiplying the token's embedding vector by a weight matrix W_Q — a grid of numbers that transforms one vector into another. It's called "learned" because these numbers are discovered during training (the model adjusts them millions of times via gradient descent — an algorithm that repeatedly measures prediction errors and nudges each weight slightly to reduce them).
For "it": its Q vector encodes something like "I am a pronoun that needs a concrete, physical, damageable noun referent." That's the search intent.
K — Key — "what do I contain?"
Each token also generates a Key vector — its advertisement of what it is. Other tokens compare their Q against this K to decide how relevant this token is. Think of it as the label on a filing cabinet drawer — a short description that helps you decide whether to open it. The Key is computed from the same embedding vector via a different weight matrix W_K.
"bank" → Key says "I am a concrete noun, a physical structure, something that can be damaged and closed." "river" → Key says "I am a body of water, a natural entity." "was" → Key says "I am a past tense verb." (terrible match for a pronoun needing a noun)
V — Value — "what do I actually give you once selected?"
Once "it" decides "bank" is the best match by comparing Q against K, it doesn't pull in bank's Key — it pulls in bank's Value. The Value is the full, rich representation of what "bank" means in this specific context. The Key was the label; the Value is everything inside the drawer. The Value is computed via weight matrix W_V.
"bank"'s Value contains: it's near a river, it was flooded, it's the subject of the earlier sentence, it's a financial institution that can reopen — far richer than the Key advertised. This richer information is what flows forward into the next layer.
Why Key and Value are separate — the important subtlety

If Key and Value were the same thing, you'd be forced to use your full, rich representation as your search index — noisy and inefficient. Separating them lets the model learn how to advertise itself (K) independently from what to share once selected (V). The Key is optimized purely for matching. The Value is optimized purely for information transfer. This separation is one of the most elegant design decisions in the transformer architecture.

The actual computation, step by step
  • Score: "It" takes its Q vector and computes a dot product (multiply corresponding elements pair-wise and sum the results — a single number that measures how similar two vectors are; higher = more similar) with every other token's K vector. "Bank" produces a high score (similar vectors). "River" produces a medium score. Grammatical words like "was" and "the" produce near-zero scores.
  • Scale: Divide all scores by √d_head (the square root of the per-head vector dimension). Without this, dot products of high-dimensional vectors can get very large, causing softmax to output values extremely close to 0 or 1 — which produces near-zero gradients (the error signals that flow backward during training to update weights) and stops learning. This is the "scaled" in scaled dot-product attention.
  • Mask: In autoregressive generation (generating text one token at a time, where each new token depends on the previous ones — "auto" = self, "regressive" = feeding back), a token cannot attend to future tokens it hasn't generated yet. Set those positions to −∞ so they become zero after softmax.
  • Softmax: A mathematical function that converts a list of raw scores into probabilities that sum to 1.0 — larger scores get exponentially larger shares, and very small scores get driven toward zero. "It" might end up with ~70% on "bank," ~20% on "river," and 10% spread across everything else.
  • Aggregate: Take a weighted sum of all V vectors using those probabilities. The output for "it" is now a vector that is mostly "bank"'s Value, partly "river"'s Value, and barely anything from grammar words. This blended vector flows into the next layer carrying the resolved meaning of "it."
The output of attention for "it" is NOT the word "bank" — it's a new vector that has absorbed context from bank, river, flooded, and everything else in proportion to how relevant they were. This is richer than picking a single referent. The model always carries forward a weighted blend of context, not a binary choice.

How Q, K, V are calculated — the mechanics

Each token starts as an embedding vector of size d_model (e.g., 12,288 for GPT-3). To get Q, K, and V for one head, you multiply this vector by three separate learned weight matrices:

  • Q = token_vector × W_Q   (W_Q has shape d_model × d_head)
  • K = token_vector × W_K   (W_K has shape d_model × d_head)
  • V = token_vector × W_V   (W_V has shape d_model × d_head)

These weight matrices are learned during training — the model discovers through gradient descent what projection produces the best Q, K, V for understanding language. Every layer has its own independent W_Q, W_K, W_V, so the same token gets projected differently at each layer, capturing different types of relationships at different levels of abstraction.

MHA (Multi-Head Attention) is the standard design where every attention head gets its own independent K and V — explained in detail in the Multi-head Attention section. Variants like GQA and MQA reduce this by sharing K/V across heads.

During autoregressive generation, every new token needs to attend to all previous tokens — requiring their K and V vectors. You could recompute them from scratch each step, but that wastes compute. Instead they're stored in GPU HBM (High Bandwidth Memory — the GPU's main memory, typically 80 GB on an A100/H100, analogous to RAM on a CPU server but with much higher bandwidth) as you go — this is the KV cache. At 4.7 MB per token for GPT-3, a 100k token context needs ~470 GB just for the KV cache. This is why long-context serving is fundamentally a memory problem.

Deep Dive — Why causal-only attention won for generation

The example above shows "it" attending only to earlier tokens — this is the causal mask enforced during autoregressive generation. Bidirectional attention (BERT-style) still wins for pure embedding/retrieval tasks (MTEB benchmarks), but the industry converged on causal decoder-only for generation for three compounding reasons: (1) Data scaling: next-token prediction works on any raw text corpus with no labels, making training data practically unlimited. Encoder-decoder requires paired data or specialized denoising objectives. (2) Architectural subsumption: a decoder-only model with very long context can subsume any seq2seq task by concatenating input + output — the encoder-decoder split provides no architectural benefit you can't replicate with causal attention. (3) Serving simplicity: one model, one KV cache, one forward pass shape. At production scale, this simplicity dividend is large.

Multi-head attention

Why one attention operation isn't enough — and how running many in parallel fixes it

The fundamental limitation of single-head attention

Single-head attention runs one Q/K/V operation across the entire d_model space. It can learn one type of relationship between tokens. But language is dense with simultaneous, independent relationship types. Consider this sentence: "The animal didn't cross the street because it was too tired."

  • "it" needs to resolve to "animal" (coreference resolution)
  • "cross" needs to find its subject "animal" (syntactic subject tracking)
  • "tired" needs to find what it modifies (modifier-head relationship)
  • "didn't" needs to connect to "cross" (negation scope)

These are four different relationship patterns happening simultaneously within a single sentence. A single attention operation cannot learn all four — it can only specialize in one. Multi-head attention solves this by running H independent attention operations in parallel, each potentially specializing in a different relationship type.

How multi-head attention works mechanically

Instead of one W_Q, W_K, W_V, you have H sets of them — one per head. Each head has its own W_Q^h, W_K^h, W_V^h of shape (d_model × d_head), where d_head = d_model / H. All H heads run simultaneously on the GPU. Each produces an output vector of size d_head. The H output vectors are concatenated back into a single vector of size H × d_head = d_model, then projected through a final W_O matrix to produce the layer's output.

Because each head works in a subspace of size d_head = d_model/H, the total compute is the same as one big attention operation — you're splitting the space, not adding to it. The efficiency comes from parallel specialization, not from doing more work.

Does specialization actually happen?

Yes — research has confirmed that different heads develop different behaviors, though never with clean hard boundaries. Studies of transformer models have found heads that consistently track:

  • Syntactic dependencies (what is the subject/object of this verb?)
  • Coreference (what does this pronoun refer to?)
  • Positional patterns (attending to the immediately previous or next token)
  • Semantic similarity (which words are conceptually related?)
  • Rare tokens (some heads specialize in unusual or domain-specific words)

This specialization is entirely emergent — you don't design or label it. Gradient descent discovers it because it produces better predictions. In GPT-3's 96 × 96 = 9,216 total attention heads, there's an enormous space for diverse specialization across the depth and width of the network.

The relationship between heads and layers

Every transformer layer contains exactly one multi-head attention block. Each layer has its own independent W_Q, W_K, W_V, W_O matrices — completely separate from other layers. Heads in layer 1 learned entirely different patterns than heads in layer 50, because the input to layer 50 is already a highly abstract representation built by the previous 49 layers.

Conceptually: heads add width within a layer (parallel specializations at the same level of abstraction), while layers add depth (each building more abstract representations on top of the previous).

The Model › Layers & Dimensions

Layers, hidden layers, and hidden dimensions

The vocabulary is inconsistent across papers and blogs — here is what everything actually means

The terms "layer," "hidden layer," and "hidden dimension" get used interchangeably but mean different things. Getting these definitions straight is foundational to understanding parameter counts, memory requirements, and why certain architectures work the way they do.

What a transformer layer actually is

A transformer layer — also called a transformer block — is one complete processing step. It is not a single matrix multiply. It contains two distinct sub-layers inside it, applied in sequence:

  • The attention sub-layer: Takes all the token vectors, runs multi-head attention (tokens look at each other and gather context), and produces a new set of token vectors where each token has now "seen" the rest of the sequence. This is the Q/K/V mechanism described in the previous section.
  • The FFN sub-layer (Feed-Forward Network): "Feed-forward" means data flows in one direction — input in, output out, no loops or cross-token communication. The FFN takes each token vector independently and runs it through two matrix multiplications (a matrix multiply, or "matmul," transforms a vector by multiplying it against a grid of learned weights — it's the fundamental operation in neural networks, the way the model applies what it has learned to new inputs). Between the two matmuls is a non-linear activation function (like ReLU or GeLU — a simple mathematical function that introduces non-linearity. Without it, stacking multiple matrix multiplications would collapse into a single matmul, and the network could only learn linear relationships. The activation function is what lets the model learn complex, non-linear patterns). The FFN is where most of the model's "knowledge" is stored — factual recall, domain knowledge, and learned patterns live in these weight matrices.

Each sub-layer also has a residual connection — the input to the sub-layer is added element-wise back to its output (output = sublayer(input) + input). This creates a "skip path" that lets gradients flow directly backward through the network during training without degrading. Without residuals, deep networks (96 layers!) would be virtually untrainable because gradient signals would vanish before reaching early layers. Also present is layer normalization — a per-token operation that rescales the vector's values to have consistent mean and variance, preventing numbers from exploding or shrinking to zero as they flow through dozens of layers. These don't add many parameters but are essential for training stability.

GPT-3 has 96 of these transformer layers stacked sequentially. The output of layer N becomes the input to layer N+1.

What "hidden layer" means — the confusing term

The term "hidden layer" comes from older neural network vocabulary (pre-transformer). It just means "any layer that isn't the raw input or the final output." In transformer contexts, people use it to mean two different things:

  • Sometimes it refers to the transformer blocks themselves (all of them, since none is literally the input or output layer)
  • Sometimes it refers specifically to the inner expansion layer of the FFN — the part that "widens" to 4× d_model before contracting back

When someone says "hidden states," they mean the token vector representations flowing through the network at each layer. When someone says "hidden dimension," they mean d_model.

How the vector flows through the network

Take the word "bank." It enters as an integer (its index in the vocabulary, say 4521). The embedding table converts it to a vector of 12,288 numbers. That vector then travels through all 96 layers. At each layer, attention updates the vector based on context (making "bank" near "river" different from "bank" near "deposit"). The FFN updates the vector based on stored knowledge. After 96 layers of transformation, the resulting vector is a rich representation of "bank in this specific context." The output head then projects it to vocabulary size to predict the next token.

Key intuition: early layers tend to learn syntactic patterns (word order, grammatical structure, punctuation roles). Middle layers learn semantic patterns (word meaning, entity types). Late layers learn reasoning patterns (logical inference, coreference, discourse structure). This abstraction hierarchy is why deep models (more layers) handle complex reasoning better than shallow ones.
Deep Dive — How firm is this hierarchy? Quantization implications

The "syntax → semantics → reasoning" progression is a useful heuristic but the empirical picture is messier than it sounds. Early probing studies (Tenney et al. 2019) on BERT found a rough ordering, but recent work on large decoder-only models complicates this: one study found 57% of contextual phenomena peaked in late layers and 43% in early layers, with zero phenomena peaking where the narrative predicts (middle). The cleaner finding: 87% of diverse phenomena route through the same late-layer "hub," suggesting less modular specialization than probing folklore implies.

Quantization implication — counterintuitive: You might expect early "syntax" layers to be more quantizable. In practice, the opposite holds. The first and last few layers are consistently the most sensitive to quantization — early layers have high activation variance, and final layers project onto vocabulary (both high-stakes). Middle layers often tolerate more aggressive quantization. Mixed-precision frameworks (AWQ, GPTQ) assign bit-widths empirically via Hessian sensitivity, not by the syntax/semantics narrative.

The Model › Parameter Count

How model parameters are counted

A complete walkthrough from first principles to the 175B number — and why parameter count doesn't equal inference cost

A "parameter" is simply a number stored in a weight matrix that gets updated during training through gradient descent, and then frozen during inference (inference means running the trained model to generate output — as opposed to training, which is the process of learning the weights). The total parameter count of a model is the sum of every single number in every single weight matrix in the entire network. Nothing more complicated than that.

Why parameters matter — and why they don't tell the whole story

Parameter count determines two things: how much memory you need to load the model, and roughly how much the model can "know." A 7B parameter model stored in FP16 (2 bytes per number) takes 14 GB of GPU memory. A 70B model takes 140 GB. A 175B model takes 350 GB.

But parameter count does NOT equal inference compute cost. This is critical. A dense model is one where every parameter is used on every input — all weights activate for every token. An MoE (Mixture of Experts) model has many sets of weights but only activates a subset per token (covered in detail in the MoE section). An MoE model with 400B total parameters but only 50B active per token has the same compute cost per forward pass (one complete trip of input data through all layers of the model — the fundamental unit of inference work) as a dense 50B model — but potentially the knowledge capacity of a 400B model. Parameter count and compute cost are only tightly coupled in dense models.

Where parameters live — GPT-3 breakdown (d_model=12,288, 96 layers)

Attention layers: Each layer has four weight matrices — W_Q, W_K, W_V (each projects d_model → d_model), and W_O (the output projection — takes the concatenated outputs from all attention heads and projects them back into a single d_model-sized vector; also d_model × d_model). That's 4 × 12,288 × 12,288 ≈ 603M parameters per layer. Across 96 layers: ~58B.

FFN layers: Each FFN has two matrices. W1 expands from d_model to d_ff = 4 × d_model: that's 12,288 × 49,152. W2 contracts back: 49,152 × 12,288. Per layer: ~1.2B. Across 96 layers: ~116B.

Embedding table: One vector per vocabulary token. GPT-3 vocabulary has 50,257 tokens, each with a 12,288-dimensional vector: ~617M parameters.

Deep Dive — If FFN has 2/3 of params, why does optimization focus on attention?

The parameter distribution and the runtime bottleneck distribution are different. FFN is a fixed cost per token per layer — it doesn't grow, doesn't accumulate state, and is embarrassingly parallel. Attention creates a growing memory structure (the KV cache) that expands with every token generated and every request in the batch. KV cache consumes GPU memory proportional to batch_size × seq_len × layers × heads × d_head, and running out of KV cache memory is the primary OOM cause in production inference, not FFN weights. During decode, attention accounts for over 50% of memory bandwidth cycles stalled on data access. The KV cache's dynamic growth determines concurrency (throughput), drives preemption/swapping, and determines TTFT degradation under load — which is why GQA, MLA, FlashAttention, and KV cache quantization all target attention. Think of it like AWS Auto Scaling: the fixed instance cost (FFN) matters, but the scaling constraint you're always fighting is the dynamic resource that grows with demand (KV cache = warm instance pool).

This is why quantization is not just about efficiency; it often determines whether a model is deployable at all.

Mixture of Experts (MoE)

How to scale model knowledge without proportionally scaling compute — and why this changes everything about serving

The problem with dense transformers at scale

In a standard dense transformer, every token at every layer passes through the exact same FFN — one set of weights, applied identically to all inputs. If you want the model to know more (larger knowledge capacity), you make the FFN bigger. But making the FFN bigger means every forward pass is more expensive. Parameter count and compute cost are tightly coupled: you cannot increase one without increasing the other.

This is a fundamental inefficiency. Not every token needs the full model capacity. A token that's part of a simple grammatical construction doesn't need the same compute as a token in a complex multi-step reasoning chain. A token about French cuisine doesn't need the same weights as a token about quantum mechanics. Dense models waste compute by applying all their capacity uniformly to all inputs.

The MoE solution — conditional computation

MoE replaces the single FFN in each transformer layer with N parallel FFNs (the "experts") plus a small learned routing network (the "router" — a tiny neural network, typically just a single weight matrix, that takes a token vector as input and outputs a probability score for each expert, deciding which experts should handle this token). For each token at each MoE layer, the router selects the top-K experts (usually K=2) to process that token. Only those K experts run — the other N-K sit idle for this token. Each expert's output is weighted by its router score and summed to produce the final output.

This is called conditional computation: the amount of computation is conditioned on the input. Different tokens take different computational paths through the model.

What an "expert" actually is

An expert is simply a feed-forward network — structurally identical to the FFN in a standard transformer layer. It has two linear layers with an activation function between them. There is nothing architecturally exotic about a single expert. The "mixture" is entirely in the routing mechanism that decides which experts process which tokens. Multiple experts means N × (FFN parameter count) total stored parameters while only paying K × (FFN compute cost) per token.

Concrete numbers — Mixtral 8×7B

Mixtral 8×7B has 8 experts per MoE layer with K=2 active per token. Total parameters: ~47B. Effective compute per token: equivalent to a dense ~13B model (2 of 8 experts active = 25% compute utilization of the full expert pool). But the model's knowledge capacity is much closer to a 47B dense model than a 13B model, because different experts have learned different knowledge domains.

DeepSeek-V3 pushed this further: 256 routed experts + 1 shared expert (always active), top-8 routed experts active per token (9 total active), plus a no-auxiliary-loss load balancing mechanism. Massive knowledge capacity at a fraction of dense equivalent compute cost.

Does expert specialization actually happen?

Yes — research on Mixtral's routing found that experts develop soft, probabilistic specializations. Some experts preferentially handle certain languages. Some specialize in code. Some in mathematical reasoning. Some in factual recall. The specialization is never hard-coded — the router sends tokens to multiple experts and each expert sees diverse inputs. But statistically, each expert has learned to be better at certain types of content than others.

Deep Dive — Auxiliary loss vs. specialization: how DeepSeek-V3 solves the tension

There's a real conflict: auxiliary load-balancing loss penalizes skewed expert utilization via gradient descent, but if expert #3 is genuinely better at math tokens, forcing uniform load actively suppresses that specialization. Models trained with heavy auxiliary loss show expert overlap (multiple experts learn similar functions) and degraded perplexity (the standard metric for language model quality — lower is better; it measures how "surprised" the model is by real text. A perplexity of 10 means the model is as uncertain as if choosing from 10 equally likely options at each token).

DeepSeek-V3's solution: Instead of penalizing imbalance through the loss (which contaminates task gradients), V3 uses a bias-adjusted routing scheme. Each expert has a learnable bias term added to its routing score. At each training step, expert load is monitored — overloaded experts get their bias decreased, underloaded experts get it increased. Critically, the bias update happens outside of backpropagation — it's a rule-based heuristic adjustment, not a gradient update. The task loss gradients flowing through the router remain completely unaffected, preserving whatever specialization the model wants to learn. Think of it like AWS Auto Scaling: instead of penalizing instances for being popular (killing the signal), you adjust the routing weights at the load balancer level without touching the application.

The key insight for infrastructure: MoE decouples parameter count from compute cost. A dense 50B model and an MoE model with 50B active parameters are roughly equivalent in inference compute — but the MoE model might have 400B total parameters and therefore much greater knowledge capacity. You get dense-50B speed with 400B-model knowledge. This is why frontier labs (DeepSeek, Google, OpenAI) have converged on MoE for their largest models.

Number formats new

FP32, FP16, BF16, FP8, INT8, INT4 — what the bits mean and why format choice drives everything in quantization

Every weight and activation in a neural network is stored as a number in some binary format. The format determines two critical things: how much memory it consumes (fewer bits = smaller model, lower HBM bandwidth required per decode step) and how precisely it can represent values (fewer bits = more rounding error = potential quality degradation). Understanding the structure of each format is what makes quantization tradeoffs make sense — without this foundation, the differences between GPTQ, FP8, and SmoothQuant feel arbitrary.

The three components of floating-point numbers
  • Sign (1 bit): Is this number positive or negative? 0 means positive, 1 means negative. Every floating-point format has exactly 1 sign bit.
  • Exponent (multiple bits): Sets the scale of the number — the order of magnitude. Think of it as the power of 2 you're multiplying by. More exponent bits = wider dynamic range (can represent both very tiny and very large numbers in the same format). With 8 exponent bits you can represent values from ~10⁻³⁸ to 10³⁸. With 4 exponent bits the range collapses to roughly 10⁻⁴ to 10⁴.
  • Mantissa (multiple bits): Sets the precision within the range established by the exponent — how many significant digits you get. More mantissa bits = finer distinctions within the same order of magnitude.

The value represented is approximately: (−1)^sign × 2^exponent × (1 + mantissa_as_fraction). The exponent sets the ballpark; the mantissa fills in the precision within that ballpark. Concrete analogy: think of scientific notation like 6.022 × 10²³. The exponent (23) sets the scale (hundreds of sextillions). The mantissa (6.022) sets the precision within that scale. With only 1 digit of mantissa you'd have 6 × 10²³ — same ballpark, less precise. With more mantissa digits (6.02214076) you get finer precision within the same scale. This is exactly how floating-point formats work, but in base 2 instead of base 10.

Why INT formats have no exponent — and why this is the root of the activation quantization problem

Integer formats (INT8, INT4) have no exponent. They represent values on a fixed linear scale — INT8 covers exactly the integers from −128 to 127 with uniform spacing. Every step is the same size. There is no way to represent both 0.001 and 500 in the same tensor without massive precision loss.

Neural network weights tend to be fairly uniformly distributed — INT8 and INT4 quantization works well for weights because there usually aren't extreme outliers. But neural network activations (the intermediate values flowing between layers) are NOT uniformly distributed. They consistently have large outlier values — a small number of activations that are 10× or 100× larger than the typical activation in that layer. This is a well-documented phenomenon across virtually all transformer architectures.

In a fixed INT8 range of −128 to 127, if your activations span from −0.01 to 500, you set the scale to cover 500. Now your step size is ~4 per INT8 unit. Any activation smaller than ~4 in magnitude collapses to the same quantized value — you've lost all precision for the "normal" activations because you're spending all your precision range on the outliers. Quality collapses dramatically. This is precisely why naive INT8 quantization of activations fails for LLMs, and why SmoothQuant, AWQ, and GPTQ all exist: they're all solving the activation outlier problem in different ways.

Why FP8 succeeds where INT8 fails for activations

FP8 keeps an exponent. Even with only 4 exponent bits (E4M3), the floating-point format can represent both 0.001 and 500 in the same tensor without precision collapse — the exponent automatically scales to cover the dynamic range. No manual calibration, no scaling factors, no clipping decisions needed. The format handles the outlier problem automatically through its exponent bits. This is the fundamental reason FP8 inference on H100 achieves near-FP16 quality while INT8 inference requires elaborate distribution reshaping to achieve the same.

BF16 — the special case that explains the training/inference format split

BF16 (Brain Float 16) has 8 exponent bits (same as FP32) and only 7 mantissa bits. Same dynamic range as FP32, but lower precision. For training, dynamic range matters more than precision: you need to represent both the tiny gradients from early layers and the large activations in later layers without overflow or underflow. BF16 was designed exactly for this. H100 uses BF16 as its default training format. For inference, FP16 is often preferred (better precision) or FP8 (better compute efficiency with H100's native FP8 Tensor Cores).

MLA — Multi-head Latent Attention new

DeepSeek's architectural innovation that achieves 93% KV cache reduction without meaningful quality loss

The problem being solved — KV cache is the long-context wall

As you learned in the KV cache section, the KV cache grows linearly with sequence length. For a 70B model using standard MHA, KV cache per token is ~4.7 MB. At 100k tokens, that's 470 GB of KV cache alone — more than the model weights (140 GB in FP16). The KV cache has become the dominant memory consumer for long-context serving.

GQA and MQA attack this by sharing K/V heads across Q heads: GQA might reduce KV cache by 8× (from 64 K/V heads to 8). MLA goes further — not by sharing heads, but by compressing the information content of K and V entirely differently.

The MLA insight — low-rank compression of K and V

The key observation behind MLA: K and V vectors across all heads at a given token and layer are not independent — they contain significant redundancy. If you have 64 heads each with a 128-dimensional K vector, that's 8,192 numbers per token per layer. But the actual information content is much lower — the vectors are correlated because they all derived from the same token embedding through related projection matrices.

MLA exploits this redundancy by learning to compress all K and V information into a single low-dimensional latent vector per token per layer. Then at attention time, the full K and V vectors for all heads are reconstructed from this latent vector via learned projection matrices.

  • What gets stored in the KV cache: One small compressed latent vector per token per layer — much smaller than num_heads × d_head × 2 (for K and V)
  • What happens at attention time: Project the latent vector back up to get K and V for all heads. Small extra compute, but the memory savings are enormous.
The numbers from DeepSeek-V2

DeepSeek-V2 introduced MLA and reported a 93% reduction in KV cache memory compared to their equivalent MHA baseline, with no meaningful quality loss on benchmarks. This is dramatically more aggressive than even MQA, which would only achieve ~1/64 reduction (one K/V head for 64 Q heads). MLA achieves this because it's compressing the information itself, not just sharing pointers to it.

Practically: if GPT-3 MHA needs ~4.7 MB KV cache per token, an equivalent MLA model might need ~0.3 MB per token. At 100k tokens: 470 GB → ~30 GB. This change alone makes very-long-context serving fundamentally more economical.

Why Kimi K2 and others adopted it

Kimi K2 uses MLA combined with their reduced attention head count and increased expert sparsity. These are all facets of the same co-design philosophy: reduce the parts of the architecture that scale badly with context (attention heads + KV cache memory), and increase the parts that scale well (MoE experts). The combination lets them serve 128k+ context requests at costs competitive with models serving much shorter contexts.

Deep Dive — MLA's compute tradeoff: when does compression pay off?

MLA's 93% KV cache reduction comes at a cost: projecting the compressed latent vector (d_c ~512) back to full K/V for all heads at attention time adds ~2 matrix multiplications per layer. For DeepSeek-V2 (80 layers): ~1.3 billion extra FLOPs per decode step. This sounds significant, but decode is memory-bandwidth-bound, not compute-bound — the arithmetic units are underutilized anyway. The 93% KV cache reduction means 93% less HBM bandwidth for loading cached KV, which is the actual bottleneck. The extra compute is free because you're using spare arithmetic capacity.

Crossover point: For very short sequences (batch=1, seq_len < ~50-100 tokens), the extra projection compute is non-trivial compared to the tiny attention matmul. Below that crossover, standard GQA can be faster since there's no decompression overhead. The exact crossover is hardware-dependent (compute-to-bandwidth ratio). On H100, MLA's advantage appears at batch sizes > 1 or seq_len > ~100 tokens. Since production serving almost always exceeds these thresholds, MLA is almost always a win in practice.

MLA is to KV cache what FlashAttention was to attention memory — it doesn't change the attention algorithm itself, but it transforms the memory cost from O(num_heads × d_head × context_length) to O(d_latent × context_length), where d_latent is much smaller. The industry is converging on MLA-style KV compression for frontier long-context models.

Architecture Frontier › Multi-token Prediction

Multi-token prediction (MTP) new

Training models to predict multiple tokens simultaneously — and why this both improves training and enables faster inference

The standard autoregressive limit

Standard language model training uses next-token prediction: given tokens 1 through N, predict token N+1. The model learns from the signal "was token N+1 correct?" This is how every GPT-style model is trained. At inference time, this means exactly one token per forward pass — 100 tokens of output requires 100 forward passes through the entire model. This is the fundamental sequential bottleneck of autoregressive decode. It is a hard ceiling on single-request decode throughput.

What MTP adds to training

MTP modifies the training objective to predict not just token N+1 but tokens N+1, N+2, N+3, ..., N+K simultaneously. The model maintains K prediction heads — one for each look-ahead offset. All K heads are trained simultaneously during each forward pass. The model receives gradient signal from all K predictions at once.

DeepSeek's specific implementation adds auxiliary prediction heads that share the main model's internal representations rather than operating independently. These heads are not separate classifiers — they share computations with the primary next-token head, forcing the model to build representations that are useful for predicting multiple steps ahead simultaneously.

Why this improves training stability

Predicting multiple steps ahead imposes a consistency constraint. If your model's prediction for token N+1 is inconsistent with a plausible prediction for token N+3, the multi-step gradient signal penalizes this inconsistency. The model is forced to maintain coherent internal representations that can support multi-step planning, not just local next-token prediction. DeepSeek observed empirically that this regularization produced more stable training convergence — the loss curves were smoother and the final model quality improved on reasoning tasks that require multi-step coherence.

The inference connection — MTP as built-in speculative decoding

Recall speculative decoding: a small draft model proposes N candidate tokens, the large model verifies all N in a single parallel forward pass (since you already have the proposed tokens, you can run verification in parallel like prefill), you accept the matching prefix, and continue. The acceptance rate determines the speedup.

The problem with external speculative decoding: the draft model is a separate smaller model with different characteristics. It may have lower quality on certain domains, leading to lower acceptance rates. You also need to hold both models in GPU memory simultaneously.

With MTP, the auxiliary prediction heads trained alongside the main model serve as the built-in draft heads. During inference: the main model generates token N+1 via its primary head. Simultaneously, the auxiliary heads propose tokens N+2, N+3, N+4. In the next decode step, instead of processing only token N+1 to generate N+2, you verify the proposals for N+2, N+3, N+4 in parallel. Accepted proposals mean you advance multiple tokens in one step.

Because the draft heads were trained jointly with the main model and share its representations, they tend to have higher acceptance rates than external draft models — they were literally trained to be consistent with the verifier. DeepSeek V3 reported approximately 1.8× decode throughput improvement from this approach in practice.

The tradeoff and when it helps most

MTP adds training cost (auxiliary heads must be trained and their gradients backpropagated). At inference, the auxiliary heads add a small amount of compute per forward pass. The net benefit is positive when output sequences are long enough for the ~1.8× decode speedup to amortize the overhead. Agentic tasks, extended reasoning chains, and long-form generation benefit most. For very short outputs (a few tokens), the overhead may not be worth it.

Multi-token prediction is one of the techniques the Dynamo podcast flagged as a potential unhobbler for decode throughput. Currently decode is capped at one token per step — MTP with speculative decoding is an architectural approach to breaking that ceiling without a separate draft model. Whether it eventually fully removes this constraint or just improves it by a useful constant is still being determined as the technique matures across more model architectures and training regimes.

Model-hardware-context co-design new

Why attention head count is now an infrastructure decision, not a research one

For most of deep learning history, model architecture was designed primarily to maximize benchmark quality. Hardware was a separate concern — you trained on whatever was available, then figured out serving later. This separation is disappearing. Frontier labs now design model architecture, training curriculum, and serving infrastructure as a single integrated system. This is what "co-design" means, and it's fundamentally changing how inference infrastructure works.

The concrete example: Kimi K2's deliberate architectural tradeoff

Kimi K2 (Moonshot AI, 2025) provides the clearest public example of co-design thinking. They explicitly published a blog post explaining why they made a specific architectural choice: they reduced the number of attention heads and slightly reduced the attention dimension, while simultaneously increasing the total number of experts but keeping the number of activated experts per token constant — i.e., increasing expert sparsity.

They ran experiments showing this combination gave better performance per unit of serving cost at their target context lengths. Why does this tradeoff work at the fundamental physics level?

  • Attention scales quadratically with context length. If you have 64 attention heads instead of 32, you do 2× the attention work — and that cost grows as O(n²) with sequence length. At 128k tokens, halving the attention heads cuts attention compute by 50%, but the benefit is even larger than it sounds because of the quadratic scaling.
  • MoE experts scale constantly with context length. Each expert processes a fixed amount of compute per token regardless of how long the sequence is. Adding more experts (even with fixed activated count) increases knowledge capacity without increasing context-scaling cost.
  • The net result: Fewer attention heads + more (sparse) experts = a model that's cheaper to serve at long contexts while maintaining comparable knowledge capacity. The tradeoff is deliberately optimized for serving economics, not just training quality.

Why context length has stalled at ~1M tokens

Context length has essentially stalled near 1 million tokens for about two years. The reason is straightforward: attention's quadratic O(n²) compute cost (FlashAttention solved the O(n²) memory cost, but the compute remains unavoidably quadratic — see FlashAttention deep dive). Doubling context length quadruples attention computation. At 1M tokens on a large model, attention already consumes a disproportionate share of compute and memory. Going to 10M tokens would require attention computation to increase ~100×, which is infeasible on current hardware.

The architectural response has been exactly what co-design predicts: reduce attention heads and replace that capacity with mechanisms that scale linearly with context length — MoE experts, state space model layers (Mamba, etc.), or hybrid architectures that use attention selectively rather than at every layer. The hardware constraint (attention quadratic cost in HBM) is directly shaping model architecture choices at the frontier.

The key mental shift: "how many attention heads should this model have?" is no longer purely a research quality question. It is an infrastructure economics question, answered by analyzing serving cost at the target context length distribution, multiplied by the expected request volume. This is what makes modern AI infrastructure engineering genuinely different from classical systems work.

NVLink, InfiniBand, and GPU memory access

What lives where, how fast data moves, and whether GPUs can reach into remote servers' memory directly

The GPU memory hierarchy — bandwidth determines what's possible

Inside a GPU server, there are multiple levels of memory with dramatically different speeds. Understanding these speeds is not just trivia — they directly determine which operations are bottlenecks and why certain optimizations matter so much. Before the table, some GPU architecture terms you'll see repeatedly:

  • CUDA core: The basic arithmetic unit on an NVIDIA GPU — it performs one floating-point operation. An H100 has thousands of CUDA cores working in parallel.
  • SM (Streaming Multiprocessor): A cluster of CUDA cores plus its own small fast memory. Think of each SM as a mini-processor. An H100 has 132 SMs. All SMs run simultaneously on different chunks of data.
  • Tensor Core: A specialized arithmetic unit (inside each SM) designed specifically for matrix multiplications — the core operation in neural networks. Tensor Cores compute entire small matrix multiplies in one clock cycle rather than doing individual multiplications. They're what make H100s so much faster for ML than raw CUDA core counts suggest.
  • SRAM (Static RAM): Small, extremely fast on-chip memory sitting right next to the compute units (inside each SM). Contrast with HBM which sits off-chip. SRAM is ~6x faster than HBM but ~1000x smaller.
  • Kernel (CUDA kernel): A function that runs on the GPU. When people say "launch a kernel," they mean "execute this specific operation on the GPU." Each kernel runs across many SMs in parallel. "Kernel fusion" means combining two separate operations into one kernel to avoid writing intermediate results back to slow HBM.

It's also why SRAM is so precious — it's 6× faster than HBM, which is why FlashAttention's SRAM-tiling strategy produces such large speedups.

NVLink — GPU to GPU within one server

NVLink is NVIDIA's proprietary high-bandwidth interconnect between GPUs within the same physical server. On DGX H100 systems, 8 GPUs are connected via NVLink 4.0 at 900 GB/s total bidirectional bandwidth per GPU. An NVSwitch chip creates a full all-to-all mesh — any GPU can communicate with any other GPU simultaneously at full bandwidth, not just adjacent pairs.

This bandwidth (900 GB/s) is what makes tensor parallelism practical. Tensor parallelism requires an all-reduce operation after every attention and FFN layer — every GPU must share its partial result with all others. At 900 GB/s, this all-reduce completes in microseconds, making the communication overhead small relative to the computation savings. At InfiniBand speeds (50 GB/s), the same all-reduce would dominate the step time and destroy any parallelism benefit.

InfiniBand — server to server across the cluster

InfiniBand is the high-speed network fabric connecting different physical servers in a GPU cluster. NVIDIA's Quantum-2 InfiniBand at 400 Gbps per port (~50 GB/s) is the standard in H100 clusters. Compare: NVLink at 900 GB/s is 18× faster than InfiniBand at 50 GB/s.

This enormous bandwidth gap is why tensor parallelism stays intra-node (NVLink) while pipeline parallelism and context parallelism work inter-node (InfiniBand). Tensor parallelism generates high-frequency, high-bandwidth communication (all-reduce every layer). Pipeline parallelism and context parallelism generate lower-frequency communication (activation tensors once per layer for PP; K/V chunks per ring step for CP), which InfiniBand can handle acceptably.

Can GPUs access memory on different servers directly?

Yes — through RDMA (Remote Direct Memory Access) over InfiniBand. RDMA allows a GPU on Server A to read from or write to the HBM of a GPU on Server B without either CPU being involved at all. The data path is: GPU HBM → GPU NIC → InfiniBand switch fabric → GPU NIC → GPU HBM on the remote server. No CPU copies, no OS kernel involvement, no context switches.

GPUDirect RDMA is the NVIDIA feature that enables this. Without it, the data path would include two extra CPU copies: GPU HBM → CPU RAM → NIC (on send side) and NIC → CPU RAM → GPU HBM (on receive side). With GPUDirect RDMA, the CPU is bypassed entirely, achieving effective throughput of ~40 GB/s on a 400 Gbps InfiniBand link.

This is exactly how KV cache transfer works in prefill/decode disaggregation: after prefill finishes on the prefill worker, the KV cache (potentially 10-100 GB for long prompts) is transferred via GPUDirect RDMA directly into the decode worker's HBM. The decode worker can start generating the first output token as soon as the KV cache arrives.

1. Data parallelism
1. Data parallelism

The simplest strategy: make N complete copies of the model, each on its own GPU or set of GPUs. Each copy (replica) handles different requests independently. A load balancer distributes incoming requests across replicas.

  • What gets split: The request stream — different requests go to different replicas
  • Communication needed: None during inference. Each replica is fully independent. (In training, gradients must be synchronized across replicas, but this doesn't apply at inference time.)
  • Requirement: The full model must fit on one GPU (or whatever the base replica size is)
  • Best for: High-throughput serving of models that fit on 1-2 GPUs (7B, 13B). Maximum simplicity. Horizontal scaling.
  • Limitation: Doesn't help when the model is too large for one GPU, and doesn't reduce per-request latency at all.
2. Tensor parallelism (recommended for inference)

Split individual weight matrices across GPUs. Every GPU holds a slice (shard) of every layer and cooperates on every single forward pass. If W_Q is 12,288×12,288 and you use 8-way TP, each GPU holds a 12,288×1,536 slice. Every GPU computes its portion of the matrix multiply in parallel. After each layer, an all-reduce operation combines the results before proceeding to the next layer. All-reduce is a collective communication pattern where every GPU sends its partial result to every other GPU, and all GPUs end up with the same combined (summed) result — think of it as "everyone shares their partial answer, everyone gets the full answer." It's the most common communication pattern in distributed ML.

  • What gets split: Weight matrices within each layer, distributed across GPUs within one node
  • Communication needed: All-reduce at every layer — very frequent, high-bandwidth required
  • Requirement: Fast interconnect — NVLink (900 GB/s). Only practical within a single 8-GPU node. The all-reduce latency over InfiniBand (50 GB/s) would dominate and erase the parallelism benefit.
  • Best for: Reducing latency (TTFT and TBT). 8-way TP means each token's forward pass runs 8× faster since all 8 GPUs work on it simultaneously. This is the primary tool for hitting low-latency SLAs.
  • Limitation: Cannot scale beyond one NVLink-connected node (8 GPUs typically) without becoming communication-bottlenecked.
Worked example: 8-way tensor parallelism on LLaMA 70B
1W_Q matrix: 8,192 × 8,192 = 67M params. With 8-way TP, each GPU holds an 8,192 × 1,024 slice = 8.4M params.
2Forward pass: All 8 GPUs compute their slice of Q = input × W_Q_slice simultaneously. Each produces a partial result.
3All-reduce: The 8 partial results are summed across all GPUs via NVLink. Data volume: 8,192 × 2 bytes (FP16) = 16 KB per all-reduce. At 900 GB/s NVLink: ~0.02 μs. At 50 GB/s InfiniBand: ~0.3 μs (15× slower — why TP stays intra-node).
4Total all-reduces per forward pass: 2 per layer × 80 layers = 160 all-reduces. Total communication overhead at NVLink: ~3 μs. At InfiniBand: ~48 μs — starts to matter at decode step times of ~20ms.
Net effect: each GPU does 1/8 of the work → forward pass runs ~8× faster → TTFT and TBT reduced ~8×. This is the primary tool for low-latency SLAs.
3. Pipeline parallelism — why it's not recommended for inference

Split the model's layers across GPUs sequentially. GPU 1 holds layers 1-24, GPU 2 holds layers 25-48, GPU 3 holds layers 49-72, GPU 4 holds layers 73-96. A token flows through each GPU one after another: GPU 1 processes it and passes activations to GPU 2, which passes to GPU 3, etc.

Deep Dive — TP all-reduce: it's 2 per layer, not 1

A transformer layer has two sub-layers that each need all-reduce: (1) after attention output projection — Q/K/V projections are column-parallel (no comm needed), but the output projection W_O is row-parallel, requiring all-reduce; (2) after FFN's second linear layer — FFN's up-projection is column-parallel, but the down-projection is row-parallel, requiring all-reduce. Total: 2N all-reduce operations for N layers. For LLaMA-3 70B (80 layers): 160 all-reduces per forward pass. This is why NVLink's 900 GB/s bandwidth is non-negotiable — at InfiniBand 50 GB/s, 160 all-reduces per decode step would completely dominate step time.

Pipeline parallelism is widely used in training (where large batches minimize bubble impact) but is generally avoided for inference serving. Use tensor parallelism instead for latency reduction. Pipeline parallelism for inference is a last resort when the model is too large for even a fully NVLink-connected node.

4. Expert parallelism (MoE models only)

In MoE models, distribute different experts across different GPUs. Each GPU holds a subset of the expert FFNs. When the router selects experts for a token, that token must be sent to whichever GPU holds its assigned expert — requiring all-to-all communication at every MoE layer.

  • What gets split: Expert FFN modules, distributed by expert index across GPUs
  • Communication needed: All-to-all at every MoE layer — unlike all-reduce (where every GPU sends the same data and gets back the combined result), all-to-all means every GPU sends different data to every other GPU (each token goes to whichever GPU holds its assigned expert). This is the most expensive collective operation in distributed ML because the communication pattern is unpredictable and cannot be compressed.
  • Operational problem: Popular experts become hot GPUs. If the router consistently sends 30% of tokens to expert #3, GPU 3 is overloaded while GPU 7 sits mostly idle. Load imbalance is a real production challenge.
  • Best for: MoE models where you must distribute experts across GPUs to fit the total parameter count
5. Context parallelism — for very long sequences

The challenge: attention requires every token to see every other token's K and V vectors. CP solves this with ring attention.

How ring attention works: Arrange GPUs in a ring. Each starts with its own Q, K, V chunk. In each step: (1) each GPU computes attention between its Q chunk and the K/V it currently holds, accumulating a partial result; (2) simultaneously, all GPUs rotate their K/V to the next GPU in the ring. After N-1 rotations, every GPU has seen all K/V chunks and has the full attention output for its token range. Critically, the K/V transfer is overlapped with computation — while GPU 1 computes attention with the K/V it just received, the next K/V chunk is already being transferred. Minimal overhead.

Difference from sequence parallelism: sequence parallelism only splits non-attention parts of the layer (LayerNorm, FFN), using an all-gather to reconstruct the full sequence before attention. Context parallelism splits the sequence including attention, using ring attention instead of all-gather. CP scales to much longer contexts because it avoids the O(N) all-gather that sequence parallelism requires.

The two phases of inference and why they create a scheduling problem

Prefill processes the entire input prompt in one shot. All tokens are available upfront, so they can all be processed in parallel in a single forward pass. Prefill is fast per token but uses the GPU heavily for a burst of time.

Decode generates output one token at a time. You cannot generate token N+1 until you know token N. Each decode step processes just one new token (plus the full KV cache of all previous tokens). Decode is inherently sequential, slow per token, and memory-bandwidth-bound — you're mostly loading weights, not doing arithmetic.

Different requests take wildly different amounts of time. A classification request might need 5 output tokens. A detailed explanation might need 800. With a fixed batch, everyone in the batch must wait for the slowest request to finish before the GPU can do anything else.

Naive batching — the broken approach

Collect N requests, process them all together as a batch, wait until every request has generated its final token, release the whole batch, collect the next N. Simple to implement. Terrible for GPU utilization.

Consider a batch of 32 requests where 31 finish in 20 tokens but 1 runs to 500 tokens. The GPU is serving 1 request for ~96% of the batch's runtime. GPU utilization: ~30-40%. Every new request queued behind this batch waits the full duration of the slowest member, regardless of how short its own output will be.

Analogy: a charter bus that drives to every passenger's final destination before returning to pick up new passengers. Continuous batching is a city bus — it drops passengers at each stop and immediately picks up new riders at that same stop. The vehicle is always full.

Continuous batching — how it actually works

At the end of every single decode step (every ~5-50ms), the scheduler wakes up and asks: which sequences just generated an end-of-sequence token and are finished? Those slots are immediately freed. Are there requests waiting in the queue? If memory allows, admit them into the freed slots right now. The batch composition changes dynamically at every decode step.

A request that needed only 5 output tokens is gone in 5 steps and its GPU memory is immediately reallocated to a new request. A 500-token request occupies its slot for 500 steps, but never blocks other short requests from using their own slots. GPU utilization: 80-90%+.

Continuous batching (also called iteration-level scheduling) was first introduced by Orca (Yu et al., OSDI 2022). vLLM (2023) adopted continuous batching and added PagedAttention as its core innovation — the paged KV cache management described in the next section. Together, these two ideas are the reason LLM serving costs dropped dramatically in 2023. Every major serving system (SGLang, TRT-LLM, Dynamo) implements continuous batching as a baseline.

The scheduler's constraints — this is where your EC2 expertise applies

The scheduler deciding what enters the batch at each step is solving a real-time bin-packing problem under two simultaneous constraints:

  • KV cache memory constraint: Every active sequence holds pages of KV cache in GPU HBM. Each new token generated by each sequence adds to that KV cache. The total KV cache usage across all active sequences cannot exceed available HBM. If you admit too many long-running sequences, you run out of memory.
  • Compute constraint: Larger batches mean more tokens to process per decode step. Beyond a certain batch size, adding more sequences doesn't increase throughput because the GPU is already saturated. You have to balance memory pressure against compute efficiency.
  • Preemption: If a request grows longer than expected and starts consuming too much KV cache memory, the scheduler can preempt it — save its KV cache to CPU RAM, free the HBM slot for other requests, and restore the sequence later when memory permits. This is swap-based preemption, exactly like OS virtual memory paging.
This scheduler is doing exactly what EC2 Auto Scaling does: bin-packing requests into available GPU memory while meeting latency SLAs. The difference is the bin size is measured in HBM bytes, the items are KV cache pages, and the SLA is TTFT and TBT rather than CPU utilization.
Deep Dive — How expensive is preemption in practice?

Concrete numbers for LLaMA-3 70B (GQA, 8 KV heads, 128 d_head, 80 layers, FP16): KV cache per token = 2 × 80 × 8 × 128 × 2 bytes = 320 KB/token. A 10k-token sequence = ~3.3 GB. Swapping to CPU at PCIe 5.0 (~64 GB/s) takes ~51 ms — roughly 1.5-2x one decode step. A round-trip (swap out + restore) costs ~100ms minimum.

Production reality: Swap-based preemption is rarely used at scale. vLLM V1 defaults to recompute preemption (drop the KV cache, re-run prefill when rescheduled) because recompute is often cheaper than PCIe transfer for moderate-length sequences, and CPU memory itself becomes a bottleneck under sustained load. The more common production responses to KV cache pressure: (1) reject new requests via admission control before OOM, (2) use GQA/MLA to shrink per-token KV footprint, (3) FP8 KV quantization (halves KV memory), (4) limit max_model_len. True swap preemption is a fallback for unexpected spikes, not a steady-state strategy.

KV cache, prompt caching, and routing-aware scheduling

Two different caching mechanisms at two different levels — where each decision happens

The KV cache — why it exists and what happens without it

During autoregressive decode, every new token needs to run attention against all previous tokens. Attention requires the K and V vectors of every previous token. You have two options: (1) recompute K and V from scratch for every previous token on every decode step, or (2) compute them once and store them.

Without a KV cache: generating token N requires running attention over tokens 1 through N-1, recomputing all their K and V vectors. Generating token N+1 requires doing it all again for tokens 1 through N. The total compute scales as O(N²) in the output length. For a 500-token response, you'd recompute token 1's K and V vectors 499 times. This is completely infeasible at any meaningful sequence length.

With a KV cache: you compute each token's K and V vectors once during prefill, store them in GPU HBM, and append new tokens as they're generated. Each decode step costs O(N) not O(N²) — you just load the cached K and V for all previous tokens and run attention once. This is mandatory. The KV cache is not an optimization; it's what makes LLM inference computationally feasible.

PagedAttention — how vLLM manages the KV cache

Naive KV cache management: allocate a contiguous block of GPU memory upfront for each request, sized for its maximum possible sequence length. Problems: (1) you don't know how long a response will be, so you over-allocate. (2) Contiguous allocation causes fragmentation — many small unusable gaps between allocations as requests finish at different lengths. vLLM measured 60-80% memory waste from this fragmentation.

PagedAttention manages KV cache exactly like an OS manages virtual memory with pages:

  • Physical KV cache memory is divided into fixed-size blocks (e.g., each block holds 16 tokens worth of K and V vectors across all layers)
  • A page table maps each sequence's logical token positions to physical blocks (just like virtual memory page tables map virtual addresses to physical addresses)
  • Blocks are allocated on demand as sequences grow — no upfront reservation
  • Blocks are non-contiguous in physical memory — a sequence can occupy scattered blocks
  • Blocks can be shared between sequences that have a common prefix (enables prompt caching at zero marginal cost)

Result: memory fragmentation drops from ~60% to near-zero. The same HBM can now hold significantly more active sequences, directly increasing batch size and throughput.

Prompt caching — cross-request KV reuse

Many requests share a common prefix. A customer support bot always starts with a 2,000-token system prompt. A RAG (Retrieval-Augmented Generation — a pattern where relevant documents are retrieved from a database and prepended to the prompt to give the model fresh knowledge) pipeline always includes the same retrieved documents. Without prompt caching, every request independently runs prefill on that shared prefix, generating the same KV vectors over and over. This is pure compute waste.

Prompt caching stores the computed KV vectors for known prefixes and reuses them. When a new request arrives, the scheduler checks: does the first N tokens of this request's prompt match any cached prefix (by hashing the token sequence)? If yes, skip prefill for those tokens and load their cached KV vectors directly. For a 2,000-token system prompt on LLaMA-3 70B, this saves roughly 100ms of prefill time on every single request. Anthropic exposes this as a first-class API feature.

Routing-aware scheduling — the distributed systems problem

In a multi-worker cluster (many GPU machines), prompt caching creates a cache locality problem. Worker A has cached the KV vectors for your system prompt. Worker B has not. If a new request is routed to Worker B, it must compute the prefix from scratch. If routed to Worker A, it gets the cache hit for free.

The load balancer must therefore be cache-aware. The naive approach — consistent hashing on the prompt prefix — routes all requests with the same prefix to the same worker. Excellent for cache hits. Terrible if that prefix is very popular: one worker gets all traffic while others sit idle.

The opposite extreme — pure load balancing (least connections, round robin) — distributes load perfectly but completely ignores cache locality. Cache hit rate approaches zero.

Production systems navigate this with hybrid policies: consistent hash routing as the primary signal, with overflow to other workers when the primary is above some utilization threshold. The exact threshold and fallback logic are tuned per deployment. This is an active research area with no settled best approach.

Radix attention — tree-based prefix caching (SGLang's approach)

Hash-based prefix caching (vLLM's approach) works by hashing blocks of 16 tokens and looking up matches. This works well for linear shared prefixes — the same system prompt across all requests. But real workloads often have branching prefix patterns:

  • A chatbot with 5 different system prompts, each with 3 different few-shot example sets = 15 prefix branches
  • A RAG pipeline where different documents are prepended to the same base prompt
  • Multi-turn conversations that share early turns but diverge at different points

Radix attention (SGLang) stores cached KV blocks in a radix tree (also called a prefix tree or trie) — a tree data structure where each node represents a segment of tokens, and branches represent divergence points. To look up a cache match, walk the tree from root, following the token sequence. You match as far as the tree goes, then prefill only the remaining tokens.

Deep Dive — Prefix cache matching granularity

A single-token change mid-prefix does NOT invalidate the entire cache in block-based systems — it invalidates from the block boundary containing the changed token onward.

vLLM: Uses content-addressed block hashing. KV cache is organized into blocks of 16 tokens. Each block is hashed based on its token content and its prefix hash (a hash chain). If a 1024-token prompt changes at token 50 with block size 16, the first 3 blocks (tokens 0-47) still cache-hit; block 4 (tokens 48-63) misses because its content changed; all subsequent blocks miss because their prefix hashes depend on block 4. Partial reuse at block granularity.

SGLang: Uses a radix tree (RadixAttention) with token-level granularity at the tree node level, storing segments of arbitrary length as nodes. This matches at finer granularity than vLLM's 16-token blocks — better for workloads with variable-length shared prefixes (few-shot examples that differ in length). Both systems default to LRU eviction for cache management.

Chunked prefill

Solving the interference problem between prefill and decode in a shared serving system

Why prefill and decode interfere — the core problem

Prefill and decode have fundamentally incompatible resource profiles running on the same GPU:

Prefill is compute-bound. Processing 10,000 input tokens in parallel saturates the GPU's arithmetic units. A long prefill job can take 200-500ms and fully occupies the GPU during that time.

Decode is memory-bandwidth-bound. Each decode step loads model weights from HBM and generates one token. Each step takes ~10-20ms and barely uses the GPU's arithmetic units.

The problem: in a continuous batching system, these two types of work share the same GPU and the same forward pass scheduler. When a new request arrives with a 10,000-token prompt, its prefill must run before it can join the decode stream. But while that prefill runs — for 200-500ms — every single ongoing decode sequence in the batch is completely blocked. They cannot generate their next token. Every user currently receiving a streaming response sees a complete freeze in the stream.

Why you can't just run them simultaneously

Your first instinct might be: why not run prefill and decode in parallel, as separate forward passes? The GPU executes one forward pass at a time. You cannot interleave two separate forward passes — the hardware doesn't support it. Whatever is in the current batch is what gets computed, and nothing else proceeds until that pass is done. The only lever you have is: what goes into each forward pass?

How chunked prefill works

Instead of processing an entire long prompt in one forward pass, break it into fixed-size chunks (e.g., 512 tokens per chunk). Each forward pass then becomes a mixed batch:

  • 512 tokens from the new request's prompt (one prefill chunk)
  • 1 new token from each of the ongoing decode sequences

All of this runs in one forward pass together. Prefill and decode tokens coexist in the same batch, processed simultaneously. After that forward pass (~20-25ms), decode sequences got their next token (no freeze), and the new request has prefilled 512 of its 10,000 tokens. Next step: another 512 tokens of prefill plus another round of decode. After ~20 steps, the full prompt is prefilled.

Deep Dive — How does the attention mask work in a mixed batch?

Each token type follows its own visibility rules via a structured block-diagonal attention mask. Prefill tokens within the current chunk attend to: (a) all tokens in preceding chunks (already in the paged KV cache), and (b) each other causally within the current chunk. Decode tokens attend only to their own per-sequence KV cache. The sequences never see each other. Frameworks like FlashInfer implement this with variable-length attention kernels (varlen attention) that handle heterogeneous mask shapes efficiently.

Compute penalty: Yes, there is interference. Prefill is compute-bound (matrix-matrix multiplications); decode is memory-bandwidth-bound (matrix-vector). Running them together means the GPU can't fully optimize for either regime. Sarathi-Serve showed this explicitly — there's a TTFT vs TBT Pareto curve controlled by chunk size. In vLLM, the chunk size (--max-num-batched-tokens) is a tunable parameter precisely because the right tradeoff is workload-dependent.

Chunk size as a tunable knob

The chunk size (e.g., 512 tokens) is a configurable parameter that directly trades TTFT against TBT smoothness. Larger chunks mean fewer steps to complete prefill (lower TTFT) but each step is more disruptive to decode (higher per-step TBT increase). Smaller chunks mean smoother decode but longer time to complete prefill. Production systems tune this based on their SLA priorities.

Chunked prefill in disaggregated inference

In a disaggregated setup (separate prefill and decode fleets), the original motivation for chunked prefill disappears — there are no decode sequences on the prefill worker to interfere with. But chunked prefill remains useful for two other reasons:

  • Head-of-line blocking within the prefill fleet: Without chunking, a single 50,000-token prompt monopolizes a prefill worker for several seconds while shorter prompts queue behind it. Chunking lets the scheduler interleave short and long prompts, improving average TTFT across the prefill fleet.
  • KV cache pipelining to decode workers: Completed chunks of KV cache can be shipped to decode workers incrementally while prefill is still running on remaining chunks. A decode worker can potentially start generating the first output tokens before the full prefill has finished — overlapping prefill computation with KV transfer and early decode. This is an active research area.

FlashAttention

Why standard attention is slow and memory-hungry — and how tiling in SRAM fixes both problems at once

The two problems with standard attention

Memory problem: Standard attention computes a score matrix of shape (sequence_length × sequence_length). For a 32,768-token context, that's over a billion entries. In FP16 that's ~2 GB just for this one intermediate result per layer. This matrix must be written to HBM, read back for softmax, written again, read again for the weighted sum of Values. Four HBM round-trips per attention layer. For a 96-layer model with long contexts: hundreds of GBs of HBM traffic just for attention intermediates.

Speed problem: All this HBM traffic is the bottleneck, not arithmetic. The GPU's Tensor Cores are fast enough to compute attention quickly, but they're starving — they finish their computation and wait for the next chunk of data to arrive from HBM. Standard attention is memory-bandwidth-bound, meaning you cannot make it faster by adding more TFLOPS.

These two problems compound: the O(n²) memory requirement also imposes a hard limit on context length — once the score matrix exceeds available HBM, you cannot run attention at all.

The FlashAttention solution — tiling in SRAM

FlashAttention's insight: you don't need to materialize the full N×N score matrix to compute the final attention output. You can compute it in small tiles that fit in SRAM (on-chip memory, ~20 TB/s) using a technique called "online softmax."

Normal softmax requires seeing all scores before normalizing: softmax(x_i) = exp(x_i) / sum(exp(x_j) for all j). To compute this you need all the x_j values at once — hence the full N×N matrix. Online softmax computes the same result incrementally: as you process each tile, you maintain a running maximum and running normalization factor, updating them tile by tile. The final result is mathematically identical to standard softmax but never requires the full matrix in memory at once.

  • Load a tile of Q (from HBM to SRAM)
  • For each tile of K and V: load them into SRAM, compute the partial attention scores for this Q×K tile, update the running max and normalization factor, accumulate the partial weighted V sum
  • Write the final attention output for this Q tile back to HBM — exactly once
  • Repeat for the next Q tile

The N×N score matrix is computed in tiles of SRAM and discarded immediately — it never exists in HBM. Q, K, V are each read from HBM exactly once. The output is written to HBM exactly once.

Why it enables everything else

FlashAttention isn't just a speed optimization — it's an enabler. Without it, 128k token contexts would require tens of GBs just for attention score matrices per layer, making them economically infeasible. With FlashAttention, the attention memory cost is O(n) in sequence length rather than O(n²). This shifts the limiting constraint from attention memory to KV cache memory — which is then addressed by GQA, MQA, MLA, and KV cache quantization.

Deep Dive — FlashAttention did NOT reduce compute complexity

Critical distinction: FlashAttention reduced attention memory from O(n2) to O(n). But attention compute is still O(n2) — the QKT matmul is O(n2 x d) FLOPs, and the AV matmul is O(n2 x d) FLOPs. These are fundamental to the attention mechanism and FlashAttention doesn't change them — it just performs them in SRAM tiles instead of materializing the full n x n matrix in HBM.

This is why long-context inference is still slow even with FlashAttention: the compute is unavoidably quadratic. FlashAttention removed the memory explosion (making 100k+ contexts physically feasible), but the O(n2) compute remains. This is exactly why co-design (reducing attention heads, replacing attention with linear-scaling mechanisms like MoE experts or state-space layers) is the next frontier: reducing the number of O(n2) operations rather than making each one more memory-efficient.

Almost every long-context serving system in production today depends on FlashAttention. It exemplifies the unhobbler pattern perfectly: it changed attention memory from O(n2) to O(n), which isn't just a constant-factor improvement — it changed what context lengths are physically possible to serve.

Quantization deep dive

AWQ, GPTQ, FP8, INT8, INT4, GGUF — what each does and when to use it

Quantization reduces the numerical precision of model weights (and sometimes activations) to use less memory and run faster. A 70B model in FP16 = 140 GB. In INT4 = ~35 GB. The memory difference determines whether a model is servable on a given hardware configuration at all. See the Number Formats section for why each format behaves differently — that foundation explains why the tradeoffs below exist.

Two fundamentally different approaches

Weight-only quantization (AWQ, GPTQ, GGUF): Only the stored weights are low-precision. Before the actual matrix multiplication — called a GEMM (General Matrix Multiply, pronounced "gem" — the single most important operation in neural network inference; every attention projection and every FFN layer is a GEMM) — weights are dequantized back to FP16. The arithmetic happens at FP16 precision. You save on memory and on HBM bandwidth (loading 4× less data per decode step), but you get no compute speedup — the GEMM itself runs at FP16.

Weight + activation quantization (FP8, INT8/SmoothQuant): Both weights AND the intermediate activation values flowing between layers are quantized. The matrix multiplication itself runs at low precision end-to-end. You get memory savings AND compute speedup — FP8 GEMMs are natively ~2× faster than FP16 GEMMs on H100's Tensor Cores. The challenge: activation distributions have outliers that destroy naive quantization quality (see Number Formats section for why).

GPTQ — layer-wise weight quantization with Hessian correction

GPTQ quantizes weights to INT4 or INT3 one layer at a time. For each layer, it solves a least-squares optimization: find the quantized weights that minimize the change in that layer's output on a calibration dataset (a small, representative sample of real data — typically 128-512 text passages — that the quantization algorithm runs through the model to observe how each weight affects outputs; the model is not being trained on this data, just measured). GPTQ uses second-order gradient information (the Hessian matrix — a mathematical structure that captures how sensitive the model's output is to changes in each individual weight; weights with large Hessian values are "important" and should be quantized more carefully, while weights with small values can be rounded aggressively with minimal quality loss) to identify which weights are most sensitive and compensate them first. This produces better quality than naively rounding to the nearest integer, especially at aggressive bit-widths like INT3.

Requirements: a calibration dataset (typically a few hundred samples from the training distribution), an offline quantization process that takes hours for large models, and a specialized fast GEMM kernel (like Marlin) to actually realize the inference speedup.

AWQ — activation-aware weight quantization

AWQ's key insight: not all weight channels are equally important. Channels that correspond to large activation magnitudes carry more signal and should be quantized more carefully. AWQ identifies these "salient" channels (by running a calibration pass to observe actual activation magnitudes), scales those channels before quantizing (making their values more spread out within the INT4 range), and applies the inverse scaling at inference time (which is absorbed into an adjacent operation at zero cost).

Result: generally better accuracy than GPTQ at INT4, especially on reasoning tasks. Also requires calibration data. Both AWQ and GPTQ are weight-only — they need the Marlin kernel (or equivalent) to achieve fast inference despite the INT4 storage.

FP8 — the current production standard on H100

FP8 quantizes both weights and activations, keeping floating-point format (sign + exponent + mantissa). The H100's Tensor Cores natively compute FP8 GEMMs at approximately 2× the throughput of FP16 GEMMs. FP8's exponent bits handle activation outliers automatically — the format can represent both 0.001 and 500 in the same tensor without precision collapse (unlike INT8).

FP8 E4M3 (4 exponent bits, 3 mantissa) is the standard for model weights and most activations. FP8 E5M2 (5 exponent bits, 2 mantissa) trades precision for higher dynamic range, sometimes used for gradient computations during training. No calibration dataset needed for many FP8 quantization approaches — the floating-point format handles the distribution automatically. Quality loss versus FP16 is minimal, often undetectable on standard benchmarks. FP8 is converging on being the default inference format for H100 serving in 2024-2025.

SmoothQuant INT8 — the A100 approach

SmoothQuant uses INT8 for both weights and activations to get the ~1.5× compute speedup from INT8 Tensor Cores on A100. The problem: activation outliers make naive INT8 collapse (see Number Formats). SmoothQuant's solution: multiply activations by a per-channel scaling factor s (making outlier channels smaller) and divide the corresponding weight channel by s (making those weights larger). The product is mathematically identical. But now both distributions are more uniform and INT8-friendly. The scaling factor is computed offline from a calibration pass. This "smoothing" operation migrates quantization difficulty from activations to weights, and weights are easier to quantize because their distribution is more regular.

GGUF — CPU and edge inference

GGUF is a file format from llama.cpp optimized for CPU inference. It supports mixed precision within a single model — sensitive layers (attention, early/late layers) get higher precision (Q6_K, Q8_0), while FFN layers get more aggressive compression (Q2_K, Q4_K). This layer-level heterogeneity preserves quality better than applying the same bit-width uniformly. GGUF models use CPU SIMD instructions (AVX-512, ARM NEON) for fast dequantization on laptops and edge devices. Not used in GPU production serving — AWQ/FP8 are faster on GPUs.

Deep Dive — Calibration data sensitivity for AWQ/GPTQ

How sensitive? Moderately. The calibration set shapes the quantization error distribution — a mismatch between calibration and serving distribution causes higher perplexity on out-of-distribution inputs. How much data? GPTQ: 128-512 samples of 2048 tokens each (~262k tokens standard). AWQ: even less — 32-128 samples since it only identifies salient weight channels, not full Hessians. Quality is surprisingly robust to calibration size once you hit ~100 samples; the distribution matters more than quantity. Marlin kernel

Why INT4 models were slower than FP16 — and how a fused kernel fixed it by never leaving SRAM

The problem — naive INT4 inference is slower than FP16

After quantizing a model's weights to INT4 (via AWQ or GPTQ), you've reduced memory by 4×. But to actually run inference, you need to do matrix multiplications (GEMMs). The GPU's Tensor Cores operate in FP16 (or FP8 on H100), not INT4. Before the GEMM can run, INT4 weights must be dequantized back to FP16.

The naive implementation does this in two sequential kernel calls: (1) a dequantize kernel that loads INT4 weights from HBM, converts them to FP16, and writes the FP16 result back to HBM; (2) a GEMM kernel that loads the FP16 weights from HBM and runs the matrix multiply. You've read HBM twice for the weights — once in INT4 form, once in FP16. Since HBM bandwidth is the bottleneck at decode, you've negated most of the benefit of quantization.

The result: INT4 models with naive dequantization can actually run slower than FP16 models at decode, despite using 4× less memory at rest. This was a major practical obstacle to INT4 deployment until fused kernels like Marlin solved it.

What Marlin does — fused dequantize + GEMM in one kernel

Marlin is a custom CUDA kernel that fuses dequantization and GEMM into a single operation. The key insight: SRAM (on-chip memory, ~20 TB/s) is 6× faster than HBM (3.35 TB/s). If you can keep the dequantized FP16 weights in SRAM/registers rather than writing them back to HBM, you avoid the second HBM read entirely.

Marlin's tiling strategy for each tile of the weight matrix:

  • Load from HBM to SRAM: Load a small tile of INT4 weights from HBM into shared memory. This is the only HBM read for these weights.
  • Prefetch while computing: While computing with the current tile, asynchronously prefetch the next INT4 tile from HBM into SRAM. Computation and memory transfer are pipelined — no stalls.
  • Dequantize in registers: Convert the INT4 values to FP16 directly in registers. The FP16 form exists only momentarily in registers — it never touches HBM or even SRAM.
  • GEMM with FP16: Run the matrix multiply using the FP16 weights now in registers against the activations. Fast Tensor Core operations.
  • Repeat: The next tile is already in SRAM due to prefetching. No stall between tiles.

Net result: INT4 weights are read from HBM exactly once (as INT4, 4× smaller than FP16). The dequantized FP16 values exist only transiently in registers and are consumed immediately. You've gone from 2 HBM reads per weight (naive) to 0.25 HBM reads per equivalent FP16 weight (fused INT4).

The actual speedup

Marlin achieves near-theoretical-peak GEMM throughput for INT4 quantized models on A100 and H100. In practice: 3-4× faster than naive dequantize-then-multiply. An AWQ INT4 model with the Marlin kernel can actually outperform the same model in FP16 at decode time, because you're loading 4× less data from HBM per decode step and the dequantization is essentially free.

The general principle — minimize HBM reads, keep work in SRAM

Marlin implements the same fundamental principle as FlashAttention: minimize HBM reads, do all computation in SRAM/registers, pipeline memory loads with computation to hide latency. This principle is the foundation of all high-performance GPU kernel engineering. Whenever a paper or blog post claims a "fused kernel" provides speedup, this is what they mean: two sequential operations with an HBM round-trip between them have been collapsed into one operation where intermediate results stay on-chip.

The bandwidth gap between SRAM (~20 TB/s) and HBM (~3.35 TB/s) is 6×. Every HBM read you eliminate, or replace with an SRAM read, unlocks 6× faster access to that data. This is why kernel engineering — which seems like low-level plumbing — produces such large end-to-end speedups in LLM inference.

Speculative decoding

Using spare GPU compute during decode to propose tokens in parallel — potentially 2-3× faster without quality loss

The opportunity — decode is compute-underutilized

Decode is memory-bandwidth-bound. Each decode step loads all model weights from HBM to generate one token. The arithmetic units spend most of their time waiting for data to arrive — they are not the bottleneck. This means there is spare arithmetic compute capacity during decode that is simply going unused.

For a large model (70B+), each decode step might take 20-50ms. Generating 500 output tokens takes 10-25 seconds of wall-clock time. The GPU is genuinely busy — HBM is running at high utilization — but the arithmetic units are underutilized because data loading is the limiting factor. Speculative decoding exploits this spare arithmetic capacity.

The core idea — draft then verify in parallel

A small, fast "draft" model generates N candidate tokens very quickly — each step takes maybe 1ms because it's a small model. Then the large "verifier" model processes all N candidate tokens in a single parallel forward pass.

Why can the verifier process N candidates in parallel? Normally, tokens must be generated sequentially because each token depends on the previous. But for verification, you already have all N proposed tokens — you can feed them all in simultaneously, just like prefill. The verifier runs one forward pass and at each of the N positions asks: "does my probability distribution agree with the proposed token?" If yes, accept. If no, reject and use the verifier's prediction instead. You continue from the first rejection point.

If the draft model proposes 4 tokens and the verifier accepts 3, you've advanced 3 tokens in roughly the time of 1 large model decode step. The key insight: the verifier's single parallel pass over N tokens costs approximately the same as 1 sequential decode step, because the work is the same — you're just doing it in one shot instead of N separate shots.

Draft model options
  • Separate smaller model: A 7B model drafting for a 70B verifier. Must share the same tokenizer (the algorithm that splits text into tokens — different tokenizers produce different token sequences from the same text, so draft and verifier must agree on how text is split). Works well when the smaller model is in the same model family. Memory cost: both models must fit in GPU memory simultaneously (7B + 70B in FP16 = 14 + 140 = 154 GB — already needs multiple GPUs, now with less headroom).
  • Same model, fewer layers (Medusa, hydra heads): Use the first N layers of the verifier as the draft, or add extra prediction heads to the main model. Guaranteed distribution alignment — higher acceptance rates because draft and verifier share weights.
  • MTP heads (built-in draft): If the model was trained with multi-token prediction, the auxiliary heads are already built-in draft heads with no memory overhead. See MTP section.
  • n-gram lookup: An n-gram is a sequence of n consecutive tokens (bigram = 2, trigram = 3, etc.). For text with lots of repetition (RAG documents, code with repeated patterns), simple n-gram matching against the already-generated context can propose tokens with zero model overhead and surprisingly high acceptance rates for specific domains.
Quality guarantee — the most important property

The output distribution of speculative decoding is mathematically identical to sampling from the verifier model alone. This is a formal guarantee, not an approximation. The rejection sampling scheme used in verification preserves the exact probability distribution of the verifier. You get the quality of the large model at the throughput of something approaching the draft model's speed (when acceptance rates are high). There is no quality-throughput tradeoff — just throughput versus system complexity and memory cost.

Deep Dive — Speculative decoding in batched continuous serving

Batched spec decode exists and is the standard production form. A single shared draft model generates candidate tokens for all requests in the batch simultaneously via a batched forward pass. The target model then verifies all candidates across all requests in a single batched forward pass.

Variable acceptance rates across requests: This is the core challenge. If request A has 90% acceptance and request B has 30%, the system handles this via request-level rollback — each sequence independently tracks accepted tokens. The batch proceeds to the next step with different effective sequence lengths per request. The system still gains if the average acceptance rate across the batch is high enough. Research shows batched speculative decoding needs acceptance rates > ~60-70% to break even against standard decode. Predictable text (code, templates) benefits most; creative/domain-specific text may not break even.

Speculative decoding is rare among inference optimizations: it offers free throughput gains (when acceptance rates are high) without any quality degradation. The costs are system complexity (running two models, managing verification logic) and memory overhead (holding both models in GPU memory). For production deployments with long outputs, this tradeoff is usually very favorable.

Chapter 4 Quiz — Optimization

Test your understanding of batching, KV cache, FlashAttention, quantization, and speculative decoding

Chapter 4 Quiz — Optimization
1 Continuous batching improved GPU utilization from ~30-40% to 80-90%+. Why is the improvement so dramatic?
In naive batching, all 32 requests must wait for the slowest to finish. If 31 requests need 20 tokens and 1 needs 500, the GPU serves 1 request for ~96% of the batch time. Continuous batching frees each slot immediately on completion and backfills with waiting requests — the batch composition changes at every decode step. The bus analogy: a city bus that drops passengers at each stop and picks up new riders, vs a charter bus that drives everyone to the farthest destination first.
2 FlashAttention reduced attention memory from O(n²) to O(n). Did it also reduce attention compute?
No. Attention compute is still O(n²) — the QK^T matmul is fundamental. FlashAttention only solved the memory wall: the N×N score matrix never materializes in HBM (computed in SRAM tiles instead). This is why long contexts are feasible but still slow — FlashAttention removed the memory explosion, but the quadratic compute remains.
3 An AWQ INT4 model with the Marlin kernel can outperform the same model in FP16 at decode. How is this possible when INT4 has lower precision?
Decode is memory-bandwidth-bound. INT4 loads 4× less data from HBM per step. Marlin fuses dequantization with the GEMM in one kernel — INT4 weights go from HBM → SRAM, are dequantized in registers (never written back to HBM in FP16 form), and immediately multiplied. The FP16 form only exists transiently in registers. Net: 4× less HBM traffic at the cost of tiny register-level dequant work, which is free because arithmetic units are underutilized during decode anyway.
4 In speculative decoding, the output distribution is mathematically identical to the large model alone. How can you get speedup without quality loss?
The trick is rejection sampling. When the draft model proposes token T with probability p_draft, and the verifier assigns probability p_verify: if p_verify ≥ p_draft, always accept. If p_verify < p_draft, accept with probability p_verify/p_draft. This scheme provably preserves the verifier's exact distribution. The speedup comes from verifying N draft tokens in a single parallel forward pass (same cost as 1 decode step), not from approximating the distribution.
5 Why does KV cache quantization to FP8 have minimal quality impact, while naive INT8 activation quantization fails badly?
KV cache values are already-computed outputs with more regular distributions than raw intermediate activations. The extreme outlier problem that plagues activation quantization (a few values 100× larger than typical) is less severe in cached K/V vectors. FP8's exponent bits handle remaining dynamic range automatically, while INT8's fixed linear scale would still struggle with any outliers.

Request length strategies

Short/short, short/long, long/short, long/long — four completely different serving problems

The fundamental asymmetry: prefill vs. decode bottlenecks

Prefill is compute-bound. Processing N input tokens in parallel is an arithmetic-heavy operation. The bottleneck is TFLOPS (Tera Floating-Point Operations Per Second — a measure of how many trillion arithmetic operations the GPU can perform per second; it's the GPU equivalent of "how fast can the CPU do math"). Faster GPUs (more TFLOPS) make prefill faster. The H100's 989 TFLOPS (with sparsity) vs the A100's 312 TFLOPS makes a big difference in prefill speed.

Decode is memory-bandwidth-bound. Each decode step loads all model weights from HBM to generate one token. The bottleneck is HBM bandwidth — how fast you can move bytes from memory to compute units. The H100 SXM (3.35 TB/s HBM bandwidth) is significantly faster at decode than the H100 PCIe (2 TB/s), for exactly this reason. More TFLOPS beyond a certain point doesn't help decode at all — the arithmetic units are already waiting for data.

This asymmetry means prefill and decode have different ideal hardware profiles. Disaggregated inference exploits this explicitly.

Prefill/decode disaggregation — the advanced solution for mixed workloads

The fundamental insight: prefill and decode have such different hardware requirements that running them on the same machines means you're always making hardware compromises for both. Disaggregation resolves this by splitting the serving fleet into two specialized pools.

Prefill workers receive new requests, run the full prefill (compute-bound, want high TFLOPS), and generate the KV cache for the prompt. They're done after prefill — they never run decode.

Decode workers receive KV caches from prefill workers (transferred via InfiniBand — a high-speed network fabric connecting GPU servers in a cluster, typically at 400 Gbps / ~50 GB/s — using RDMA, Remote Direct Memory Access, which lets GPUs read/write each other's memory directly without CPU involvement; see NVLink section for details), then run decode until the response is complete (memory-bandwidth-bound, want high HBM bandwidth). They never run prefill.

After prefill finishes on a prefill worker, the KV cache (which can be gigabytes for long prompts) is transferred over InfiniBand RDMA directly to the decode worker's GPU HBM, bypassing the CPU. The decode worker then begins generating tokens immediately. Each fleet scales independently — if decode is the bottleneck, add more decode workers without touching the prefill fleet. If a surge of long prompts arrives, scale up prefill workers.

Deep Dive — KV transfer is the emerging bottleneck in disaggregation

Concrete numbers for LLaMA-3 70B (GQA): KV cache = 320 KB/token. A 100k-token prompt = ~31.25 GB. At InfiniBand 400 Gbps (~50 GB/s): transfer takes ~625 ms. Even at 800 Gbps: ~312 ms. Both blow most TTFT budgets before a single decode token is generated. For long contexts (32k-128k tokens), KV transfer latency now dominates over decode compute time itself. This is why Mooncake uses RDMA with zero-copy, and Dynamo includes a KV transfer scheduler that pipelines transfers with decode. Chunked prefill can partially mitigate this by shipping completed KV chunks incrementally while prefill continues — an active research area.

Disaggregation is Anthropic's production serving architecture direction. The papers that formalize this: DistServe (OSDI 2024) and Splitwise (ISCA 2024). NVIDIA Dynamo implements this in their open-source inference framework. Being able to describe disaggregation clearly — including the networking requirements and the KV transfer mechanism — is high signal in any Anthropic infrastructure conversation.

Scheduling, admission control & prioritization new

SLO-aware scheduling, early rejection, priority tiers, and goodput-optimized serving

SLO-aware admission control — the Mooncake pattern

Before accepting a request, estimate whether you can complete it within the SLO. If not, reject immediately with a 503 rather than accepting, partially processing, and then failing — wasting GPU compute on tokens that never reach the user.

total_time = queue_wait + prefill_time + decode_time
prefill_time = prompt_tokens / prefill_throughput (e.g., 10,000 / 5,000 = 2s)
decode_time = predicted_output_tokens / decode_throughput (e.g., 500 / 50 = 10s)
queue_wait = f(queue_depth, current_throughput)

If total_time > SLO_deadline: reject immediately with 503 + Retry-After.

The hard part: estimating predicted_output_tokens before generation. See the Output Length Prediction section.

AWS analogy: This is like an NLB health check combined with a connection limit. Rather than accepting connections you can't serve, you reject at the load balancer. The difference: "can I serve this?" depends on the specific request and current system state.

Goodput-optimized scheduling

Goodput = requests meeting SLO / total requests attempted. This is different from throughput (tokens/sec) — a system can have high throughput but low goodput if many requests miss their SLO. A system doing 100 req/s with 95% SLO compliance has goodput of 95 req/s.

Key techniques from goodput research:

  • SLO-aware admission: Reject requests likely to miss SLO rather than degrading everyone's latency.
  • Preemption ordering: When memory pressure forces eviction, evict requests already likely to miss SLO, or those with least progress (minimizing wasted compute), or lowest priority tier.
  • Waiting policy: Sometimes delaying a new request (increasing its TTFT) is better than starting it immediately and causing TBT SLO violations for in-flight requests.
Priority tiers in production

Weighted Fair Queuing (WFQ): Assign weights to priority classes — e.g., Enterprise=10, Paid=5, Free=1. Each class gets bandwidth proportional to its weight. Under overload, Free gets 1/16 of capacity, not zero. Prevents complete starvation while maintaining priority ordering.

Preemption policies — who gets evicted first
  • FCFS (default in vLLM): Last-arrived evicted first. Simple but can evict nearly-complete requests.
  • Least-progress-first: Evict requests that generated fewest tokens. Minimizes wasted compute.
  • Lowest-priority-first: Evict from lowest tier. Best for multi-tenant systems.
  • Longest-remaining-first: If output length is predicted, evict requests with most remaining work. Frees the most memory per eviction.

Output length prediction new

Why predicting output length matters, how to do it, and what happens when you're wrong

Why it matters

You don't know how many tokens the model will generate until it emits EOS. This uncertainty breaks scheduling:

  • Bin-packing: A 2000-token request blocks a batch slot 20× longer than a 100-token request. Without prediction, short requests get stuck behind long ones.
  • SLO feasibility: Can't reject infeasible requests proactively if you don't know decode time.
  • Preemption: If a request is 95% done (predicted 100 tokens, generated 95), don't evict it.
  • KV cache budgeting: Each request's KV cache grows linearly. Predicting output length lets you pre-allocate correctly.

QLM — using distributions, not point estimates

QLM (from the Andes paper, UC Berkeley/Microsoft 2024) uses the Central Limit Theorem: even if individual predictions are noisy, across a batch of N requests, the total tokens predicted converges to the true total with variance shrinking as 1/√N. Per-request prediction can be mediocre, but batch-level capacity planning can be accurate.

Learning-to-Rank for SJF-like scheduling

Instead of predicting absolute lengths, predict relative lengths — "request A is shorter than request B." This is easier to learn and sufficient for Shortest-Job-First scheduling. Add aging to prevent starvation: effective_priority = shortness_score + aging_factor × wait_time. This is directly analogous to Linux's CFS scheduler or AWS weighted round-robin with priority aging.

What happens when predictions are wrong
  • Over-prediction (predicted long, actually short): Wasted KV cache allocation, but request finishes early. Minor inefficiency.
  • Under-prediction (predicted short, actually long): Dangerous. Triggers preemption, violates SLO, blocks "express lane." Mitigate by using the upper bound of the confidence interval for admission control.
Key insight: prediction accuracy matters less than you'd think. Even a noisy predictor that correctly identifies the top-25% shortest and bottom-25% longest requests enables 2-3× reduction in average latency for short requests.

The word "batch" means different things in prefill vs decode, which adds to the confusion:

  • Prefill batch: A single sequence with a 2,000-token prompt runs a "batch" of 2,000 tokens in one forward pass. All prompt tokens processed in parallel. The batch dimension here is tokens within one sequence.
  • Decode batch: 64 sequences each contribute 1 new token = a "batch" of 64 tokens. The batch dimension here is sequences, with 1 token each.

When someone says "batch size 64 with sequence length 2,048" — the 64 is how many sequences, the 2,048 is the per-sequence token count. During decode, each sequence contributes exactly 1 token, so the batch has 64 tokens total across 64 sequences.

Multi-turn inference new

How conversations work mechanically, why they're expensive, and how to design for them at scale

What makes multi-turn different from single-turn

In single-turn inference, every request is fully independent. A prompt arrives, gets prefilled, decode runs, the response is returned. Nothing persists. The server can forget everything the moment the response is sent.

In multi-turn (a conversation), each new user message depends on the full history of everything that came before — every prior user message and every prior assistant response. The model needs that entire history to generate a coherent next response. The naive approach: concatenate the full conversation history into the prompt on every turn.

Turn 1: 500 tokens. Turn 2: 500 + 400 (turn 1 response) + 200 (turn 2 message) = 1,100 tokens. Turn 5: ~3,500 tokens. Turn 10: potentially 8,000–15,000 tokens. The prompt grows with every turn. Multi-turn inference is fundamentally a long-context problem that gets progressively worse throughout the session.

Architecture 1 — Stateless (most systems today): The KV cache is evicted the moment each request finishes. On the next turn, the client sends the full conversation history as a new prompt. The server reprefills everything from scratch — including all tokens from previous turns it already processed. Wasteful, but operationally simple. Every server is stateless. Any server in the fleet can handle any turn of any conversation. Load balancing is trivial. No session affinity required.

Architecture 2 — KV persistence (where the industry is heading): After each turn finishes, the KV cache is kept alive — in GPU HBM if capacity allows, in CPU RAM as a secondary tier, or in dedicated KV storage (Mooncake architecture). The next turn only prefills new tokens and appends to the existing KV cache. A 10-turn conversation costs 10 × (average new tokens per turn) in prefill rather than 10 × (growing sum).

Many production systems still use Architecture 1 as the default, because it's operationally simple. However, prefix caching (Anthropic's prompt caching, vLLM's automatic prefix caching, SGLang's RadixAttention) is now widespread, creating a practical middle ground — the shared prefix portion of KV cache is reused across turns without full session persistence. Architecture 2 (full KV persistence) is where investment is going — Anthropic's extended thinking, long-context models, and agentic use cases all create strong economic pressure to solve KV persistence properly.
Why Architecture 2 is hard — the four challenges

1. Routing affinity. If the KV cache for a conversation lives on Server A, all subsequent turns must go to Server A. Your load balancer needs session affinity — consistent hashing on conversation ID. Straightforward to implement, but creates the same hot-spot problem as prefix caching: popular conversations or long-running sessions can saturate specific workers while others sit idle.

2. KV cache memory pressure. In-progress conversation KV caches are live — you can't evict them without losing the ability to continue cheaply. As conversations grow longer and more conversations are active simultaneously, KV cache competes with new request processing for HBM. You need an eviction policy: LRU across conversations, priority by recency, or commercial charging models (paying for "warm context"). If you evict a conversation's KV cache, the next turn falls back to full reprefill — functionally transparent to the user, just slower and more expensive.

3. Disaggregated architecture tension. In a disaggregated setup (prefill workers + decode workers), where does the KV cache live between turns? If it lives on the decode worker that handled the last turn, you need affinity to that specific decode worker — but decode workers are supposed to be stateless and interchangeable for scheduling flexibility. If you persist KV in a separate storage tier (Mooncake), you add latency loading it back on each turn. There is no clean solution today.

4. Dual representation management. Conversation text and conversation KV cache are different things with different lifecycles. The text must be persisted durably (it's the source of truth). The KV cache is a derived, expensive-to-compute artifact that can be regenerated from the text if needed. You're managing two representations with very different storage economics: text is kilobytes, KV cache is gigabytes.

Capacity planning — where multi-turn differs sharply from single-turn

Single-turn KV cache usage is predictable: it scales with request concurrency and output length. Multi-turn KV cache usage is not — it compounds with conversation depth over the session lifetime. A 20-turn conversation with 500 tokens per turn holds 10,000 tokens of KV cache indefinitely while active.

KV cache size per token is model-dependent — it scales with num_KV_heads × d_head × num_layers × bytes_per_element. For a dense GPT-3 style model in FP16 this is ~4.7 MB per token. For LLaMA-3 70B with GQA (8 KV heads), it's roughly 0.3 MB per token — but 10,000 tokens still means 3 GB of HBM per active long conversation, on top of 140 GB of model weights. Sizing your KV cache pool requires traffic data on conversation depth distribution — you cannot derive it from first principles alone.

Connection to prompt caching

Anthropic's prompt caching feature is a specific slice of this — it caches KV vectors for stable, static prefixes (system prompts, long context documents) across requests. Multi-turn conversation caching is the natural dynamic extension: instead of caching a static prefix, you cache the growing conversation prefix across turns. The engineering challenges are identical in kind, but harder in practice because the cache key is dynamic (growing with each turn) rather than static.

Deep Dive — KV cache validity across model versions and sampling changes

Model version update: KV cache vectors are outputs of specific W_K, W_V weights. If the model is updated — even a minor checkpoint update, adapter swap, or quantization change — all cached KV tensors are numerically incorrect for the new model's attention and must be discarded. There is no mechanism to "migrate" KV cache across model versions because the latent space geometry changes. Production systems handle this via versioned cache namespacing: each model version gets an isolated cache pool, and on rollout the old version's cache drains naturally via LRU. Common pattern: blue-green deployment where new replicas spin up, traffic shifts gradually, and old replicas serve existing warm sessions until they complete.

Sampling parameter changes: Temperature, top-p, top-k are controls that govern randomness when picking the next token from the model's probability distribution (temperature=0 always picks the most likely token; higher temperature spreads probability more evenly, increasing creativity/randomness; top-p and top-k limit which tokens are even considered). These are applied after the forward pass — they modify the logit distribution at sampling time but do not affect KV vectors. Changing temperature between turns does not invalidate the KV cache. However, there's a subtle correctness case: if earlier turns generated different tokens due to different sampling settings, the KV cache for those generated tokens would be wrong. vLLM handles this by including generated token IDs in the cache key hash chain — cache hits require matching both prompt and generated tokens.

How tool calling, multi-step reasoning, and extended thinking change the serving problem

What makes agentic workloads fundamentally different

Standard chat: request arrives, prefill, decode, done. Agentic workloads (Claude Code, computer use, multi-step reasoning) break every assumption:

AWS analogy: Standard chat is a stateless web server behind an ALB. Agentic inference is a WebSocket-based real-time application with long-lived connections, variable message sizes, and idle periods — much harder to load balance and scale.

How tool calls actually work — it's just tokens

A tool call is not a special system event. The model generates a tool invocation as regular output tokens in a structured format (JSON, XML, or a special markup). The serving system detects these tokens and acts on them. The entire mechanism is built on top of the same autoregressive decode — no special GPU operations, no side channels.

The stop sequence mechanism

The model is trained to emit a stop sequence when it wants to invoke a tool — a specific token pattern (like </tool_call> or "}\n" at the end of a JSON block). The serving system's sampler checks every generated token against a list of configured stop sequences. When a match is found, decode halts immediately.

This creates a subtle infrastructure problem: partial stop matching. If the stop sequence is </tool> and the model has generated </too, the sampler can't yet tell if this is the beginning of the stop sequence or just the word "too" in normal text. It must buffer these ambiguous tokens rather than streaming them to the client. If the next token is l>, it was a stop — discard the buffered tokens and halt. If the next token is th (making "tooth"), flush the buffered tokens to the client and continue.

This partial-stop buffering adds a small latency hiccup at every potential stop sequence prefix — typically negligible, but it means the serving system is doing string matching on every single generated token, and the streaming output can stutter briefly at partial matches.

The suspend-and-resume scheduling problem

When a tool call is detected, the serving system must:

  • Pause decode for this sequence — it's waiting for external tool results
  • Decide what to do with the KV cache — hold in GPU (wastes memory), swap to CPU (resume latency), or discard (re-prefill cost)
  • Signal the client — send the tool call JSON, wait for the client to execute the tool and return results
  • Resume — when tool results arrive (could be 100ms to 60+ seconds later), append them to the context, prefill the new tokens, and continue decode

The tricky part: the scheduler has a sequence that is "alive" (has state, has a KV cache, is part of a session) but "not active" (not contributing tokens to the batch, not doing useful GPU work). Every other serving optimization assumes sequences are either active or done — tool calls create a third state: suspended.

The KV cache as a long-lived resource

In standard serving, KV cache is allocated at prefill, used for seconds, then freed. In agentic serving, it becomes a long-lived resource that must persist across tool execution gaps. A 100K-token conversation on a 70B model uses ~32 GB of KV cache (with GQA) — a single session consuming a large fraction of available GPU memory.

Options for idle KV cache:

  • Hold in GPU memory: Simplest, wastes the most expensive resource during tool execution.
  • Swap to CPU memory: Free GPU for other requests. Swap-in adds ~100-500ms latency on resume.
  • Disaggregated KV store (Mooncake): KV cache in a separate storage tier. Any GPU can resume the session. Maximum flexibility, ~50-200ms retrieval latency.
  • Discard and re-prefill with prefix caching: Drop session KV cache. Rely on prefix caching for shared portions (system prompt). Only re-prefill session-specific tokens. Works when session context is small relative to shared prefix.
Extended thinking from a serving perspective

Thinking tokens are real tokens — each goes through the same decode forward pass, consumes the same compute, and extends the KV cache. A response with 10K thinking + 2K visible tokens has a KV cache footprint of 12K, not 2K.

This changes TTFT semantics: there are now two metrics — time to first thinking token (fast, like standard TTFT) and time to first visible token (can be 30+ seconds). Traditional latency-based autoscaling would incorrectly interpret 45 seconds of thinking as degradation.

Inference-time compute scaling

The broader principle: spending more compute at inference time to improve quality. Multiple approaches exist:

  • Best-of-N: Generate N candidates, score with a reward model, return the best. Cost: linear in N. Quality: logarithmic (diminishing returns). KV cache: all N share the same prefill.
  • Tree search with verification: Explore reasoning paths, score intermediate steps with a process reward model, prune bad branches. How o1/o3, DeepSeek-R1, Gemini 2.5 work. KV cache branching uses copy-on-write (PagedAttention's reference counting).

Research shows a 7B model with 100× inference compute can outperform a 70B model at 1× on reasoning tasks. The serving system must support 100× variance in per-request compute cost.

The emerging two-tier pattern

The industry is converging on:

  • API-served agents: Stateless serving with aggressive prefix caching. Send full context each turn. Let the serving system handle KV reuse transparently. Simpler, more robust, works well with existing infrastructure. This is how Claude Code and ChatGPT with tools work today.
  • Latency-critical / long-context agents: Session-aware serving with KV persistence or disaggregated KV stores. More complex but necessary when re-prefill cost becomes prohibitive (>100K token contexts).

1 A request with a 10K-token prompt arrives. Your prefill throughput is 5,000 tok/sec and decode throughput is 50 tok/sec. The predicted output is 500 tokens. Your SLO is 15 seconds. Should you accept or reject?
Calculate: Prefill = 10,000/5,000 = 2s. Decode = 500/50 = 10s. Total = 12s. 12s < 15s SLO → Accept. If queue wait adds >3s, reject. This is the Mooncake early rejection pattern — estimate total time at admission, reject immediately with 503 if infeasible, rather than accepting, partially processing, and failing the SLO (wasting GPU compute on tokens that never reach the user).
2 In an agentic session, the model generates a tool call and waits 5 seconds for tool results. During those 5 seconds, what's happening to GPU resources?
The KV cache is held in GPU HBM (consuming memory but generating zero tokens). The GPU's compute units are idle for this session. If average tool execution is 5s and average decode between tools is 3s, the GPU is idle 5/(5+3) = 62.5% of the time for agentic sessions. This is the core tension: hold the KV cache (waste memory) or swap it out (add resume latency). Production systems increasingly use prefix caching with full context re-send as a simpler alternative.
3 Why is chunked prefill's real benefit about TBT consistency rather than TTFT?
Without chunking, a 10K-token prefill causes a 500ms TBT spike for all streaming users — their token flow freezes completely. With chunking (512-token chunks), TBT increases from 20ms to ~25ms per step — barely noticeable. TTFT actually gets slightly worse with chunking (prefill spreads across more steps), but for interactive chat, smooth streaming matters more than minimum absolute TTFT. Users tolerate waiting slightly longer for the first token; they don't tolerate their stream freezing mid-response.
4 In disaggregated inference, the Berkeley retrospective found that chunked prefill closes 60-80% of disaggregation's latency benefit. When is disaggregation still worth it?
Independent scaling is the real win. When your workload is a mix of long-context RAG (prefill-heavy) and short chat (decode-heavy), disaggregation lets you scale each fleet independently — like separate ASGs for web tier and worker tier. Also worth it when: strict TBT SLOs (<50ms) can't tolerate any prefill interference, scale exceeds 50+ GPUs, or you have heterogeneous GPUs (high-FLOPS for prefill, high-bandwidth for decode).
5 Your output length predictor classifies requests as short (1-100 tokens), medium (100-500), or long (500+) with 75% accuracy. Is this useful for scheduling?
Yes, very useful. Even a noisy predictor that correctly identifies the shortest 25% and longest 25% enables SJF-like scheduling with 2-3× reduction in average latency for short requests. You don't need exact token counts — you need relative ordering. Add aging (priority boost with wait time) to prevent long-request starvation: effective_priority = shortness_score + aging_factor × wait_time.

TensorRT compilation — what it does

TensorRT compiles a neural network into an optimized inference engine through:

  • Layer/operator fusion: Linear → Bias → ReLU becomes a single CUDA kernel. Eliminates HBM round-trips between operations.
  • Kernel auto-tuning: Benchmarks multiple kernel implementations and selects the fastest for the specific GPU, batch size, and tensor dimensions. GPU-specific — an A100 engine won't be optimal on H100.
  • Mixed precision: Selectively quantizes insensitive layers to INT8/FP8, keeps sensitive layers in FP16.

Trade-off: TRT-LLM engines achieve highest throughput but are inflexible — changing max_batch_size or adding a LoRA adapter requires recompilation (30-60 min). torch.compile (PyTorch 2.x) is a lighter-weight alternative with more flexibility.

Model validation
  • Numerical: Compare output logits between original and quantized models. Measure KL divergence (<0.01 for INT8/FP8, <0.05 for INT4) and perplexity degradation (<0.5% for INT8, <2% for INT4).
  • Task-specific: Run MMLU, HumanEval, GSM8K, MT-Bench. Flag any drop >1 point.
  • Production shadow: Run quantized model alongside production in shadow mode. Use LLM-as-judge for automated quality comparison at scale.

  • SGLang: ~2,000-4,500 output tok/sec. Within 5-10% of vLLM on standard; 2-5× faster for structured generation. RadixAttention gives 30-80% TTFT reduction for shared-prefix workloads.
  • Dynamo: Depends on underlying engine. Core benefit is disaggregation, not raw single-GPU perf.
When to choose each
vLLM: Default choice. Broadest model support, largest community, fastest feature iteration, multi-hardware. Start here.

TRT-LLM: Maximum NVIDIA throughput justifies operational complexity. NVIDIA NIM. Dedicated MLOps team available.

SGLang: Structured generation is primary use case. Multi-turn workloads where prefix caching is critical. Easiest path to high performance.

Dynamo: Need disaggregation at 50+ GPU scale. Strict TBT SLOs. High-bandwidth interconnect available.

Pragmatic default: Start with vLLM. Once you've identified specific bottlenecks, switch to the specialized engine. Same principle as AWS: don't start with a custom Spot placement strategy. Start with on-demand, prove the workload, then optimize.

Open-loop vs closed-loop — the critical distinction

Closed-loop: Send request, wait for completion, send next. With N clients, always exactly N in-flight. When the system slows down, request rate drops automatically. This hides the real overload behavior.

Open-loop: Send requests at a fixed rate (Poisson process), regardless of system speed. When the system slows, requests pile up. You see the real queueing latency. This is how real production traffic works — users don't wait for other users' requests to finish.

A system benchmarked closed-loop at 50 concurrent clients might show 200ms P99. The same system open-loop at equivalent request rate might show 2000ms P99 — 10× worse. The difference is queueing delay, which closed-loop hides by construction. Always use open-loop for production capacity planning.

Coordinated omission

In a closed-loop benchmark, when a request takes 5 seconds instead of 50ms, the next request is delayed 5 seconds. During those 5 seconds, no measurements are recorded. But in reality, ~100 users would have sent requests during those 5 seconds, all experiencing multi-second latency.

The benchmark records one 5s measurement. Reality would record ~100 measurements of 5+ seconds. P99 is drastically under-reported.

Fix: Use open-loop benchmarking (vLLM's benchmark_serving.py in Poisson mode avoids this by design), or apply Gil Tene's HdrHistogram correction.

Load test design — graduated ramps

Don't benchmark at a single flat rate. Use a graduated ramp: start at 5 req/s, increase by 5 every 2 minutes. Plot latency vs. throughput at each step. This reveals:

  • Linear region: Latency is stable, system has headroom.
  • The knee: Latency starts climbing — saturation begins. This is your practical capacity.
  • Overload region: Latency explodes, throughput may decrease.

AWS analogy: This is exactly a step-scaling stress test. You wouldn't set target tracking to 80% CPU without first knowing what load corresponds to 80%. The graduated ramp gives you the load-to-utilization curve.

Common pitfalls
  • Cold cache: First requests are always slower (CUDA compilation, KV block allocation). Send 50+ warmup requests, discard from measurement.
  • Synthetic prompts: "Write a 500-word essay" produces predictable lengths. Use ShareGPT or production replays.
  • Fixed max_tokens: Makes every request the same "size." Real traffic has heavy-tailed output distributions.
  • Ignoring GPU thermal throttling: GPUs throttle at high temperatures. Long benchmarks show decreasing throughput over time. Monitor temperature.
  • Network contamination: Benchmarking a remote API includes network RTT in TTFT. Benchmark locally for engine perf, remotely for user-perceived latency.

Inference cost economics new

$/token math — how optimization decisions translate to dollars

The fundamental formula

Every inference cost calculation reduces to one equation:

$/Mtok = GPU_cost_per_hour / (tokens_per_second × 0.0036)

Or equivalently: $/Mtok = GPU_cost_per_hour × 1,000,000 / (tokens_per_second × 3,600)

Concrete example — LLaMA 3 70B on H100 (FP16, continuous batching):

  • GPU cost: $2.50/hr (reserved). Throughput at batch ~64: ~2,000 output tokens/sec → $0.35/Mtok output
  • Same model, single request (no batching): ~35 tokens/sec → $19.84/Mtok output

That's a 57× cost difference between batched and unbatched — illustrating why continuous batching is the single most important optimization for inference economics.

Worked example: cost per million tokens
1Setup: 2× H100 GPUs serving LLaMA 70B with tensor parallelism. GPU cost: $2.50/hr per GPU = $5.00/hr total.
2Throughput (batched): Continuous batching at batch ~64 achieves ~2,500 output tokens/sec.
3Apply formula: $/Mtok = $5.00 / (2,500 × 0.0036) = $5.00 / $9.00 = $0.56/Mtok
4Adjust for utilization (70%): $0.56 / 0.70 = $0.80/Mtok
5Adjust for goodput (85% SLO compliance): $0.80 / 0.85 = $0.94/Mtok
Effective cost: $0.94/Mtok output. Compare: Claude Sonnet 4 charges $15/Mtok output. The ~16× margin covers R&D, safety, RLHF, API infrastructure, and peak capacity headroom.
Including utilization and goodput

Utilization adjusts for idle GPUs: Effective $/Mtok = base $/Mtok / utilization_fraction. At 60% utilization: $0.35 / 0.60 = $0.58/Mtok. Idle time is the silent killer — at $2.50/hr per H100, every idle hour is pure waste. This is why autoscaling (your Phase 3-4 work) is so critical.

Goodput adjusts for wasted work (preempted requests, speculative decoding rejections, timeouts, thinking tokens). A system running 3,000 raw tok/sec with 15% eviction and 5% timeout: effective goodput = 3,000 × 0.85 × 0.95 = 2,423 useful tok/sec. Effective $/Mtok = $0.35 / 0.808 = $0.43/Mtok.

Input vs output cost asymmetry

Input (prefill) tokens are ~10-30× cheaper to process than output (decode) tokens. Prefill is compute-bound and processes thousands of tokens in parallel. Decode is memory-bandwidth-bound, generating one token at a time per sequence. This is why API providers charge 3-5× more for output tokens.

Reasoning models (o1/o3, Claude extended thinking, DeepSeek-R1) generate internal chain-of-thought tokens — sometimes 10-100× the visible output length — before producing the final answer. A request generating 500 visible tokens might consume 5,000-50,000 thinking tokens internally, making effective compute cost 10-100× higher than non-reasoning inference. Providers typically bill thinking tokens at output token rates, creating strong economic pressure for thinking token optimization (pruning redundant reasoning, caching common reasoning patterns, early termination on high confidence).

The cost formula connects directly to your Phase 3-4 work: autoscaling maximizes utilization (denominator), admission control maximizes goodput (numerator). Both directly reduce effective $/Mtok. Phase 7's scheduling work will optimize at the micro level — given fixed GPUs, maximize the useful work per dollar.

MFU, SOL, and unhobblers new

How to measure GPU utilization, what limits it, and the concept of breakthroughs that remove ceilings rather than improve constants

MFU — Model FLOP Utilization

MFU (Model FLOP Utilization) is the ratio of useful model computation actually being performed to the maximum theoretical computation the hardware could perform. It answers: "Of all the arithmetic operations my GPU is capable of per second, what fraction is actually going toward useful model computation?"

An H100 SXM has a peak of ~494 TFLOPS for BF16 (Brain Float 16 — a 16-bit format with wide dynamic range, standard for training; see Number Formats section for details) (dense, without structured sparsity). If a training run achieves 200 TFLOPS of useful model computation, MFU = 200/494 ≈ 40%. State-of-the-art training runs achieve 35-50% MFU. Getting above 50% is considered excellent. Most naive implementations fall below 30%.

Why MFU is almost never 100% — the sources of waste
  • Memory bandwidth bottleneck (the biggest one for inference): For memory-bandwidth-bound operations like decode, the GPU's arithmetic units complete their computation and then sit idle waiting for the next batch of data to arrive from HBM. The GPU is literally waiting for data, not computing. No amount of TFLOPS helps here — you need more HBM bandwidth.
  • Communication overhead: In tensor parallelism, the all-reduce operations require all GPUs to stop computing and exchange results. More GPUs in the TP group = more communication overhead = lower MFU. There is an optimal TP degree beyond which the communication cost exceeds the parallelism benefit.
  • Kernel launch overhead: Launching a GPU kernel (a unit of computation) has fixed overhead regardless of how much work it does. Many small sequential operations have disproportionate overhead. Kernel fusion (combining multiple operations into one kernel) directly addresses this.
  • Pipeline bubbles: In pipeline parallelism, GPUs sit idle at the start and end of each batch waiting for adjacent stages. Each bubble is wasted compute time. For inference with small batches, bubbles dominate.
  • Attention quadratic scaling at long sequences: Standard attention becomes memory-bandwidth-bound as sequence length grows — you're spending more time reading the attention matrix from HBM than doing arithmetic. FlashAttention's tiled SRAM algorithm directly improves MFU for attention by reducing HBM reads.
SOL — Speed of Light

SOL is Jensen Huang's first-principles performance concept. Before asking "why is this slow?", ask "what is the theoretical fastest this could possibly be given the physics?" That ceiling is the Speed of Light for this system. For a GPU: 100% peak TFLOPS with no overhead. MFU then measures how close to SOL you're achieving.

For an inference system: the SOL would be if every request was instantly prefilled and decoded with zero scheduling overhead, zero memory fragmentation, zero communication latency, and 100% arithmetic throughput. Everything else is friction between the real system and SOL.

The value of SOL thinking: it separates "fundamental physics limits" from "engineering inefficiencies we can fix." A 40% MFU means 60% of your GPU's potential is being consumed by things that aren't useful model computation. Some of that 60% is unavoidable (communication is physically necessary). Much of it can be attacked — and every optimization technique in this guide is an attack on some specific source of that gap.

Deep Dive — Inference MFU is misleading; use MBU instead

Typical inference MFU: Prefill achieves 30-50% MFU (comparable to training — large batch of prompt tokens drives compute). Decode achieves 1-5% MFU — extremely low because each decode step processes one token per request, making weight loads dominate over FLOPs. Combined serving MFU across a mixed workload: typically 5-15%.

Why MFU is the wrong metric for decode: MFU measures how close you are to peak FLOP/s. But decode is bottlenecked by HBM bandwidth, not compute. A GPU at 1% MFU during decode can be at 95% memory bandwidth utilization — which is the actual binding constraint. You're measuring the wrong resource.

Better metrics for inference: (1) MBU (Model Bandwidth Utilization) — actual HBM bandwidth used / peak HBM bandwidth. A well-tuned decode system should achieve 70-90% MBU. (2) Tokens/second/dollar for cost efficiency. (3) TTFT and TBT at P50/P99 for SLO compliance. (4) KV cache utilization % — like capacity pool utilization in Auto Scaling: if KV cache is full, you're blocking new requests regardless of GPU compute availability.

At NVIDIA, SOL thinking is used culturally at every level — frontline engineers use it as naturally as managers. When someone proposes a timeline or a performance number, the immediate question is "what's the SOL here, and why are we not at it?"

Unhobblers — the concept that explains technological step-changes

An "unhobbler" (term from Leopold Aschenbrenner's Situational Awareness essay) is a scientific or engineering discovery that removes a constraint that was previously preventing further scaling or progress — not just improving efficiency by a constant factor, but changing the shape of the scaling curve entirely. It's what differentiates a "10% speedup" from "the entire paradigm is now possible."
