Alex: So Jenny, I want to start with a question. You know how at AWS you'd treat a stateless web service behind an ALB completely differently from a WebSocket service with long-lived connections?

Jenny: Totally different beasts. The ALB stuff you can shard, round-robin, scale horizontally without thinking. WebSockets — you've got sticky sessions, connection state, idle clients holding resources. It's a whole different operational model.

Alex: Right. So here's the punchline for today: standard chat inference is the ALB model. Agentic inference — Claude Code, computer use, multi-step reasoning agents — that's the WebSocket model. And almost every assumption the serving stack was built on breaks when you make that jump.

Jenny: Okay, give me the contrast. What actually changes?

Alex: Pretty much every dimension. A standard chat request lives for five to thirty seconds. An agentic session can run for minutes to hours. One turn versus twenty to fifty tool calls. Context is fixed in chat — in an agent, it grows monotonically because every tool result gets appended back in. And the GPU is idle thirty to sixty percent of the session, just waiting on tool execution.

Jenny: Wait, hold on. Thirty to sixty percent idle? That's catastrophic for a fleet of H100s. That's like running EC2 instances at forty percent utilization and calling it a day.

Alex: Exactly the right reaction. And it's worse than that — the GPU is idle, but the KV cache memory is still occupied the whole time. So you're paying for the most expensive resource on the box and getting no work out of it.

Jenny: Okay so before we get to the cache problem, walk me through the mechanics. When the model "calls a tool" — what is that, actually? Is there some special hook in the GPU?

Alex: This is the part that surprises people. There is no special hook. A tool call is just tokens. The model generates regular output tokens in some structured format — JSON, XML, a special markup — and the serving system watches the token stream and recognizes it.

Jenny: Wait, so the GPU has no idea it just emitted a tool call?

Alex: None. It's the same autoregressive decode loop. The trick is the model is trained to emit a stop sequence — like a closing tag, or a specific JSON terminator — when it wants to invoke a tool. And the sampler on the serving side checks every generated token against a list of configured stop sequences.

Jenny: Every single token? That sounds like it'd be expensive.

Alex: It's cheap, but it creates a subtle problem. Imagine the stop sequence is `</tool>`. The model generates `</too`. Is that the start of the stop, or is the model about to write the word "tooth"? You don't know yet.

Jenny: Oh. So you can't stream those tokens to the client.

Alex: Right. You have to buffer them. If the next token is `l>`, it was a stop — discard the buffer and halt decode. If the next token is `th`, flush the buffer and keep going.

Jenny: That's kind of beautiful and also kind of horrifying. You're doing string matching on the hot path of every generated token.

Alex: Every token. And the streaming output stutters slightly at every potential stop prefix. Usually negligible, but it's there.

Jenny: Okay, so the model emits a tool call. The serving system catches it. Now what? The GPU just... sits there?

Alex: This is where it gets interesting. The scheduler now has a sequence in a state that didn't exist in the old world. It's "alive" — it has a KV cache, it's part of an active session — but it's "not active" — it's not contributing tokens to the batch, not doing GPU work. Every batching optimization assumes sequences are either active or done. Tool calls invent a third state: suspended.

Jenny: Suspended. Like a paused EC2 instance that's still holding its EBS volume and its IP.

Alex: That's actually a perfect analogy. And the question is: what do you do with that "EBS volume" — the KV cache — while you wait?

Jenny: How long are we waiting?

Alex: Anywhere from a hundred milliseconds for a fast local function call, up to sixty seconds or more if it's hitting an external API or running code in a sandbox.

Jenny: Sixty seconds with a chunk of GPU memory pinned. Okay so what are the options?

Alex: Four basically. One — hold it in GPU memory. Simplest, but you're wasting your most expensive resource. Two — swap it out to CPU memory. Frees the GPU for other requests, but resume costs you a hundred to five hundred milliseconds. Three — push it to a disaggregated KV store, like Mooncake. Now any GPU in the fleet can resume the session. Maximum flexibility, fifty to two hundred milliseconds to retrieve. Four — just drop it and re-prefill when the tool result comes back, leaning on prefix caching for the shared parts.

Jenny: That last one feels wasteful. Why would you ever throw away the cache?

Alex: Because the alternative might be worse. Let me show you with numbers. Say you're at turn twenty of an agent session. Context is eighty thousand tokens. The KV cache for that one session, on a 70B model with grouped-query attention, is twenty-five gigabytes.

Jenny: Twenty-five gigs for one session.

Alex: One session. And if you tried to re-prefill all eighty thousand tokens at five thousand tokens per second, that's sixteen seconds before the model generates a single new output token.

Jenny: Sixteen seconds of dead air on every tool call round? That's unshippable.

Alex: Right. So you have two choices: either hold that twenty-five gigs across the entire idle period — which means at scale your GPU memory budget is dominated by suspended sessions — or you use prefix caching aggressively and only re-prefill the new tokens since the last turn. The shared prefix from turns one through nineteen hits the cache and costs almost nothing.

Jenny: Oh interesting. So prefix caching isn't just a nice optimization for chat — it's load-bearing for agents.

Alex: It's the difference between a viable system and an unviable one. Without it, prefill cost compounds quadratically across an agent session and it falls over by turn ten.

Jenny: Okay, I want to push on something. You said context grows monotonically — every tool result gets appended. Why? Why not summarize, prune, evict old turns?

Alex: People do try. But the model was trained to use the full conversation history, and any time you compress or evict, you're trading correctness for cost. The frontier right now is: keep the full context, make the serving system fast enough to handle it.

Jenny: That's a "throw hardware at it" answer.

Alex: It is. But it's also why prefix caching and disaggregated KV stores are getting so much attention.

Jenny: Alright, switch me to extended thinking. How does that fit in?

Alex: Thinking tokens are real tokens. Each one goes through the same decode forward pass, consumes the same compute, extends the KV cache the same way. So a response with ten thousand thinking tokens and two thousand visible tokens has a twelve-thousand-token KV cache footprint, not two.

Jenny: And from the user's perspective?

Alex: This is where it bites operationally. You now have two latency metrics. Time to first thinking token — fast, like normal TTFT. Time to first visible token — could be thirty seconds, sixty seconds. If your autoscaler is watching latency to decide when to scale out, it'll see a forty-five second delay and think the fleet is degraded.

Jenny: Oh god. So your latency-based scaling policy panics during normal operation.

Alex: Constantly. You need separate metrics for "is the system actually slow" versus "is the model thinking hard." Different alarms, different thresholds.

Jenny: Okay, last thing I want to hit. You've been saying "the LLM" like it's the whole system. But an agent isn't just an LLM, right?

Alex: Not even close. A typical agent turn touches the LLM, a retriever or vector DB, a reranker, a code execution sandbox, and one or more external tool servers. Each one is its own fleet, scales on its own metric, fails for its own reasons.

Jenny: So if I size everything proportional to "agent sessions," I'm wasting money on whichever component is under-utilized.

Alex: Exactly. The vector DB scales with queries per second and index size. The sandbox pool scales with tool-call rate and is dominated by container startup cost — so you pre-warm. Tool servers are I/O-bound and rate-limited by upstream. They're all independent autoscaling groups.

Jenny: This is just microservices with an ML core in the middle.

Alex: That's exactly what it is. And here's the operational rule that catches everyone — the forty millisecond rule. Cross-cluster network hops cost roughly thirty to fifty milliseconds each. An agent turn might do retrieval, rerank, prefill, tool call, decode — ten hops easily. At forty milliseconds each, that's four hundred milliseconds of pure network latency on a turn that's supposed to feel instant.

Jenny: And every individual component looks fast in isolation.

Alex: Every component looks fast. The user feels a slow agent. The fix is co-location — same VPC, same AZ. Don't span regions per turn. If you must span, do it once per session.

Jenny: So where does this lead? What's the next thing I should be thinking about?

Alex: Two threads. One — disaggregation. We touched on it with KV stores, but the bigger pattern is splitting prefill from decode entirely, onto different instance types. Compute-heavy versus memory-heavy. Like read replicas versus write masters.

Jenny: That's a serving topology question.

Alex: Right. And the second thread — once you accept that an agent is a distributed system, the routing decisions get really interesting. KV-aware routing, session affinity, where do you place the next turn given which GPUs already have warm cache. That's the next frontier of serving optimization, and it looks a lot more like content-aware load balancing than traditional ML serving.

Jenny: So the takeaway is: agent inference forced the ML serving stack to grow up and become a real distributed system.

Alex: That's the whole story. And the people who'll build the best agent platforms are the ones who already know how to run distributed systems at scale.

Jenny: That's a good place to leave it. See you next episode.

Alex: See you next time.
