Alex: So I want to start today with a number that I think will land for you. In 2023, the cost of serving LLMs dropped by something like 10x. Not because the GPUs got cheaper. Not because the models got smaller. One scheduling change.

Jenny: One change? That's a Werner Vogels keynote slide right there. What was it?

Alex: Continuous batching. And the reason I want to start there is because the intuition maps almost perfectly onto something you already think about every day — bin-packing requests onto EC2 capacity.

Jenny: Okay, I'm listening. But before you go there — batching is not a new idea. We've been batching ML inference for a decade. What's special about LLMs?

Alex: That's exactly the right question. So in classical ML serving — think image classification, embeddings, rerankers — every request takes basically the same amount of time. You batch 32 images, they all finish in roughly the same forward pass, you return all 32 answers, you grab the next 32. Clean.

Jenny: Right, uniform-cost requests. That's why dynamic batching in Triton works — wait ten milliseconds, grab whatever showed up, run it as one batch.

Alex: Exactly. Now LLMs break that assumption catastrophically. One user asks "what's the capital of France" — five output tokens. Another user asks for a detailed explanation of the tax code — eight hundred output tokens. Same batch.

Jenny: Oh no. So if I naively batch those together...

Alex: The five-token request finishes in maybe fifty milliseconds. The eight-hundred-token request takes thirty seconds. And in classical batching, the whole batch is locked together until everyone finishes.

Jenny: Wait wait wait. So the GPU is sitting there for thirty seconds, serving one request, with thirty-one empty slots?

Alex: Thirty-one empty slots that it cannot refill until the slow one finishes. GPU utilization in the thirty to forty percent range. And every new request that shows up — even a five-token classification — has to wait the full thirty seconds before it even starts.

Jenny: That's brutal. That's like — okay, here's my analogy. That's a charter bus. You board, the driver waits for everyone, then drives to every passenger's final destination, then comes back to the depot before picking up new passengers.

Alex: That is literally the analogy people use. And continuous batching is the city bus. Every stop, people get off, new people get on, the bus is always full, it never goes back to a depot.

Jenny: Okay but here's where my infrastructure brain gets suspicious. Why was this hard? Why didn't somebody just... do this from day one?

Alex: Because to understand why it was hard, you have to understand the two phases of LLM inference. They're radically different workloads sharing the same GPU.

Jenny: Two phases — prefill and decode, right?

Alex: Right. Prefill is when you process the input prompt. The user types "explain continuous batching" — that's, what, four tokens? The model processes all four in one forward pass, in parallel, because every token is already known. Prefill is compute-bound. You're hammering the GPU's matrix units.

Jenny: Okay, so prefill is the burst. What's decode?

Alex: Decode is where it generates the response, one token at a time. And here's the thing — you cannot generate token N+1 until you know token N. It's inherently sequential.

Jenny: Why? Why can't I parallelize that?

Alex: Because the next token depends on every token that came before it, including the ones the model just generated. There's no way to predict token five hundred without first generating tokens one through four hundred ninety-nine.

Jenny: Right, autoregressive. Okay.

Alex: And here's the kicker — decode is memory-bandwidth-bound, not compute-bound. Every single decode step, you have to load the entire model weights from HBM into the compute units, do a tiny amount of arithmetic for one token, write the result back. The GPU's matrix units are mostly idle. You're bottlenecked on memory bandwidth.

Jenny: Oh. Oh that's important. So the GPU is wildly underutilized during decode unless you have a lot of sequences in flight at once, all sharing the same weight load.

Alex: Now you've got it. That's why batching matters so much for LLMs — it's the only way to amortize the cost of loading weights across multiple users.

Jenny: So we need batching, but the requests have wildly different lengths, so static batching wastes the GPU. Continuous batching is the answer. How does it actually work?

Alex: At the end of every single decode step — and a decode step is somewhere between five and fifty milliseconds — the scheduler wakes up and asks two questions. Which sequences just emitted an end-of-sequence token? Free those slots. And — are there requests waiting in the queue? Admit them right now, into the freed slots, this very step.

Jenny: So the batch composition is changing every five to fifty milliseconds.

Alex: Every step. The classical view was: a batch is a set of requests, you pick them, you commit, they run together to completion. Continuous batching throws that out. The unit of scheduling is no longer the request — it's the token. Every decode step is a fresh batching decision.

Jenny: Ohhh. That's the whole insight, isn't it. Request-granularity to token-granularity scheduling.

Alex: That's the whole insight. The paper that introduced this was called Orca, OSDI 2022, Yu and collaborators. They called it iteration-level scheduling. Then vLLM picked it up in 2023, paired it with paged KV cache management, and that's when costs collapsed.

Jenny: Okay, I want to push on the scheduler. Because what you're describing sounds exactly like an EC2 Auto Scaling problem. You've got a fixed pool of capacity — the GPU's HBM — and you're packing variable-sized workloads into it in real time.

Alex: It is exactly that. The scheduler is solving a bin-packing problem under two simultaneous constraints. Constraint one — KV cache memory. Every active sequence is holding pages of KV cache in HBM, and every new token it generates adds more pages.

Jenny: So the bin is HBM, and the items growing inside the bin are KV cache pages.

Alex: Yes. And constraint two — compute. There's a batch size beyond which adding more sequences doesn't help, because the GPU is already saturated on the matmuls. So you're balancing memory pressure against compute efficiency, every five to fifty milliseconds, in real time.

Jenny: This is just admission control with extra steps. What happens when you guess wrong? Like, you admit a request thinking it'll be short, and it just keeps generating?

Alex: That is the exact failure mode. And the scheduler has a tool for it — preemption. It can take a running sequence, save its KV cache to CPU RAM over PCIe, free up the HBM slot, and restore the sequence later when memory permits.

Jenny: That's literally OS virtual memory paging. Swap.

Alex: It is literally swap. Same idea, same mechanism. But — and this is where I'd correct the textbook version of the story — swap preemption is rarely used at scale in production.

Jenny: Wait, really? Why not?

Alex: Let's do the numbers. LLaMA-3 70B, KV cache per token is about 320 kilobytes. A ten-thousand-token sequence is roughly 3.3 gigabytes of KV cache. Push that over PCIe 5.0 at 64 gigabytes per second — that's about 51 milliseconds to swap out, another 51 to swap back in. A full round trip is over 100 milliseconds.

Jenny: That's like two full decode steps just for the swap.

Alex: And under sustained load, the CPU memory itself becomes a bottleneck. So vLLM V1 actually defaults to recompute preemption — they just throw away the KV cache and re-run prefill when the request gets rescheduled.

Jenny: Throwing away work and redoing it is cheaper than swapping?

Alex: For moderate-length sequences, often yes. PCIe is slow, prefill is parallel and fast on the GPU. The real production answer is don't get into this situation in the first place. Reject new requests via admission control before you OOM. Use GQA or MLA to shrink the KV footprint per token. Use FP8 KV quantization to halve the memory. Cap max sequence length.

Jenny: So preemption is the fallback, not the strategy.

Alex: Exactly. It's there for unexpected spikes, not for steady state.

Jenny: Okay. So zooming out — continuous batching is the scheduling change. But everything you just said about KV cache pressure being the binding constraint... that's the next conversation, isn't it?

Alex: That's exactly the next conversation. Because once you accept that the scheduler is bin-packing KV cache pages into HBM, the obvious next question is — how do you actually manage that memory? If you allocate KV cache in big contiguous chunks, you get fragmentation, and you waste twenty, thirty percent of your HBM to internal fragmentation alone.

Jenny: Which would mean fewer concurrent sequences, smaller batches, lower throughput. The whole win evaporates.

Alex: The whole win evaporates. So next time we're going to talk about PagedAttention — vLLM's other big innovation — which is essentially virtual memory paging for the KV cache. Fixed-size blocks, no fragmentation, you can even share blocks across requests that have the same prefix.

Jenny: Shared blocks across requests? Like copy-on-write for prompts?

Alex: Like copy-on-write for prompts. And after that we'll get into chunked prefill, which is how you stop a long prompt from starving the decode requests already in the batch — basically rate limiting at the GPU.

Jenny: Admission control for bursty workloads. I'm in. Same time next week?

Alex: Same time next week.
