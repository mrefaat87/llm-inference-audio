Alex: So Jenny, I want to talk about something that I think is going to feel very familiar to you, but with a twist that trips up almost everyone coming from traditional infrastructure.

Jenny: Okay, I'm intrigued. What are we getting into?

Alex: Benchmarking. Load testing your inference endpoint. And I know what you're thinking — "I've been load testing services for years, I know how this works." And that's exactly the problem.

Jenny: Oh no. What am I doing wrong?

Alex: Okay, let me set this up. When you load test, say, an API Gateway backed by some Lambda functions, what do you typically do?

Jenny: Pretty standard. I spin up a bunch of concurrent clients, each one sends a request, waits for the response, then sends the next one. Measure latency, find the breaking point.

Alex: Right. And that approach has a name in the benchmarking world — it's called closed-loop testing. You have N clients, always exactly N requests in flight. And here's the thing that's subtle but devastating: when the system slows down, your request rate automatically drops.

Jenny: Well, yeah. If my client is waiting for a response and the response takes longer, it can't send the next one yet. That's just... how it works.

Alex: Exactly. And for a lot of traditional services, that's fine because your clients actually do wait. But think about inference in production. When a user sends a chat message to an LLM endpoint, are they waiting for someone else's request to finish before their request goes in?

Jenny: No, of course not. Users show up whenever they show up. It's like... oh. It's like real traffic hitting an auto scaling group. Users don't coordinate. They don't say "oh, the server's busy, I'll come back later."

Alex: Exactly right. Real traffic is what we call open-loop — requests arrive at a fixed rate following a Poisson process, completely independent of how fast the system is processing them. And here's the number that should scare you: I've seen systems that benchmark at 200 milliseconds P99 under closed-loop testing with 50 concurrent clients, and then you hit them with the equivalent open-loop request rate and the P99 is 2000 milliseconds. Ten times worse.

Jenny: Ten times? Where does that extra latency come from?

Alex: Queueing. When you test closed-loop and the system gets slow, you're automatically easing off the gas. Fewer requests arrive, so the queue stays short. Open-loop? You keep slamming requests in at the same rate. The queue builds. And queue wait time is real latency that your users feel.

Jenny: So closed-loop testing is basically lying to you about your capacity.

Alex: That's a strong way to put it, but yeah. It's hiding the overload behavior. It's like — imagine you're testing an auto scaling group, but your load generator automatically backs off whenever the target group gets stressed. You'd never see the scaling event. You'd never see the queue depth spike. You'd walk away thinking "great, my system handles this load fine," and then real traffic hits and everything falls over.

Jenny: Okay, so open-loop, always. But there's something else lurking here, isn't there? I've heard you mention coordinated omission before and I never fully got what that was.

Alex: Oh, this is the really insidious one. So let's say you're running a closed-loop benchmark and one request gets stuck — takes 5 seconds instead of the usual 50 milliseconds.

Jenny: That happens. Some requests just get unlucky.

Alex: Right. Now, during those 5 seconds, your client is blocked. It's not sending new requests. So you record one measurement: 5 seconds. One data point. But in reality, how many users would have shown up during those 5 seconds?

Jenny: At, say, 20 requests per second... that's about 100 users.

Alex: And every single one of those 100 users would have experienced multi-second latency because they'd be stuck behind that same backlog. But your benchmark only recorded one bad measurement instead of a hundred. Your P99 looks fine. Your real P99 is catastrophic.

Jenny: That's... that's terrifying actually. You're systematically undercounting exactly the moments when things are worst. It's like if your CloudWatch metrics stopped reporting during an outage.

Alex: That's a perfect analogy. The observations disappear precisely when they'd be most alarming. The fix is simple in principle — use open-loop benchmarking. vLLM's benchmark_serving.py has a Poisson mode that avoids this by design. Requests arrive on a schedule regardless of what the system is doing. You can also apply a statistical correction called HdrHistogram, developed by Gil Tene, but honestly, just go open-loop.

Jenny: Okay. So we know how to test. What exactly are we measuring? Because inference isn't just "request in, response out" like a normal API call.

Alex: No, and this is where it gets interesting. There are really two distinct phases in generating a response. The prefill phase — that's where the model processes your entire input prompt — and the decode phase, where it generates tokens one at a time. And each phase has its own latency characteristic.

Jenny: So what's the headline metric for each?

Alex: For prefill, it's TTFT — Time to First Token. That's your responsiveness metric. How long does the user stare at a blank screen before they see anything? Think of it like Time to First Byte in web performance.

Jenny: Okay, and for decode?

Alex: TBT — Time Between Tokens, sometimes called Inter-Token Latency. That's how smooth the streaming experience feels. If TBT spikes, the text stutters. And then there's the total picture — end-to-end latency, and output throughput measured in tokens per second across all concurrent requests.

Jenny: And I assume we're reporting percentiles, not averages?

Alex: Thank you for saying that. Yes. Always P50, P95, P99. A system that averages 50 milliseconds but has a 5-second P99 is dramatically worse than one averaging 80 milliseconds with a 120-millisecond P99. The average hides the pain.

Jenny: Preaching to the choir. We learned that the hard way in auto scaling — average CPU utilization is meaningless when you've got hot spots.

Alex: But here's the metric I really want you to remember: goodput. Not throughput — goodput. That's the number of requests that actually meet your SLO divided by total requests. Because you could have amazing throughput numbers while half your users are getting responses too slow to be useful.

Jenny: Oh, I like that. It's like... it's the difference between "how many requests per second can we process" and "how many requests per second can we process well." That's the metric an engineering manager would actually care about.

Alex: Exactly. It's the one that maps to customer experience.

Jenny: Alright, so I've got open-loop testing, I've got the right metrics. How do I actually design the load test? Do I just pick a request rate and let it rip?

Alex: No! And this is another classic mistake. Don't benchmark at a single flat rate. Use a graduated ramp. Start at, say, 5 requests per second. Increase by 5 every two minutes. Plot latency against throughput at each step.

Jenny: Oh, that's literally a step-scaling stress test. We do this all the time to characterize auto scaling groups.

Alex: It's the exact same idea. And what you'll see is three distinct regions. First, a linear region where latency is flat and stable — the system has headroom. Then you hit the knee — latency starts climbing, that's saturation beginning. That's your real practical capacity. And then the overload region where latency explodes and throughput might actually decrease.

Jenny: Throughput can decrease? How?

Alex: When the system is totally overwhelmed, it spends so much time managing the queue and swapping memory that it's doing less actual useful work. Same thing happens when an EC2 instance starts thrashing swap — the CPU is busy, but it's not making progress.

Jenny: So the knee in that curve — that's the number I take to capacity planning. Not the peak throughput, but the point right before things start degrading.

Alex: Right. You wouldn't set target tracking to 80% CPU without knowing what load corresponds to 80%. The graduated ramp gives you that load-to-utilization curve.

Jenny: Okay, before we wrap the methodology piece — what are the gotchas? The things that make your benchmark results garbage without you realizing it?

Alex: Oh, I've got a list. Number one: cold cache. The first batch of requests is always slower — CUDA kernels need to compile, KV cache blocks need to be allocated for the first time. Send at least 50 warmup requests and throw those measurements away.

Jenny: Like warming up a JVM. You don't benchmark during class loading.

Alex: Exactly. Number two: synthetic prompts. If every request is "write a 500-word essay," every response is roughly the same length. But real traffic has a heavy-tailed distribution — some responses are 10 tokens, some are 2000. Use real conversation datasets like ShareGPT, or replay production logs.

Jenny: Because uniform request sizes hide all the scheduling edge cases.

Alex: Yes. Number three, and this is one people forget — GPU thermal throttling. GPUs get hot under sustained load and they will clock down. A 30-minute benchmark might show steadily decreasing throughput, and it's not your software, it's physics. Monitor the temperature.

Jenny: Ha, we don't usually worry about CPU thermal throttling in the cloud because AWS manages that. But when you're running your own GPU workloads...

Alex: You're closer to the metal than you're used to. And number four: network contamination. If you're benchmarking a remote API, your TTFT includes network round-trip time. That's fine if you want user-perceived latency, but if you're evaluating the engine itself, benchmark locally.

Jenny: So two benchmarks: one local for engine performance, one remote for the experience your users actually get.

Alex: Exactly. And quick note on tools — vLLM's benchmark_serving.py is the community standard. Open-loop Poisson mode, ShareGPT dataset support, reports all the metrics we talked about. NVIDIA has GenAI-Perf which auto-generates those latency-throughput curves. And MLPerf Inference added LLM scenarios in v4.0 with built-in SLO compliance — it's basically addressing coordinated omission by design.

Jenny: So where does this all lead? We've got this rigorous benchmarking methodology — what do we actually do with the results?

Alex: This is the foundation for everything that comes next. Once you have a real load-to-latency curve, you can make informed decisions about cost economics — cost per token at different utilization levels. You can compare engines like vLLM versus TensorRT-LLM on your actual workload, not synthetic numbers from a blog post. And you can set scaling policies that are grounded in measured behavior, not guesswork.

Jenny: So it's like — you can't do capacity planning without a load test, and you definitely can't do inference capacity planning without one that accounts for all these inference-specific gotchas.

Alex: That's the takeaway. The tools exist, the methodology is well-understood. The mistake is reaching for the tools before understanding what they're actually measuring and what they're hiding from you. Get the methodology right, and everything downstream — engine selection, cost optimization, scaling policy design — gets dramatically better.

Jenny: I love it. Measure right, then optimize. Same as always, just with some new traps to avoid.

Alex: Some very expensive new traps.
