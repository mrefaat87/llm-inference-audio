Alex: So Jenny, picture this. You're running a fleet at AWS, and you've got two completely different workload profiles sharing the same EC2 instances. One is this CPU-pegged batch job that runs for thirty seconds and saturates every core. The other is a latency-sensitive API server where p99 actually matters. What do you do?

Jenny: Oh, that's a no-brainer. You split them. Different instance groups, different scaling policies, probably different instance families even. You don't let the batch job starve your API.

Alex: Right. And yet, for years, that's exactly what we did with LLM inference. Prefill and decode — two fundamentally different workloads — running on the same GPUs, fighting for the same resources.

Jenny: Wait, hold on. I want to make sure I have the shapes right. Prefill is when you ingest the prompt, decode is when you generate tokens. Why are those so different in terms of resource profile?

Alex: Great question. Prefill is compute-bound. You're doing these massive matrix multiplications across the entire prompt in parallel — thousands of tokens at once. The GPU's streaming multiprocessors light up to ninety, ninety-five percent utilization. It's a beast of a compute job.

Jenny: Okay, so prefill is like the batch job — pegging the cores.

Alex: Exactly. Now decode. Decode generates one token at a time. Every single token, you have to load the entire model's weights from HBM — high-bandwidth memory — to do one tiny matmul. The compute is trivial. The bottleneck is memory bandwidth. SM utilization on decode is twenty to forty percent. The cores are basically waiting around while bytes get pulled across the bus.

Jenny: So prefill is compute-bound, decode is bandwidth-bound. And you're telling me we used to run these on the same instance.

Alex: Same instance, same GPU, same scheduler. And here's where it gets ugly. A thirty-two-thousand-token prefill comes in. That single request now occupies all the compute on that GPU for, let's say, two seconds. During those two seconds, every decode that was happily streaming tokens to a user — they all stall.

Jenny: Oh no. That's a head-of-line blocking nightmare.

Alex: DistServe measured it. Decode latency inflates two to thirty times during large prefills. Your time-between-tokens — the metric that determines whether a chat feels smooth or janky — it just falls off a cliff.

Jenny: Hang on, why not just chunk the prefill? Break the big prompt into smaller pieces, interleave them with decodes?

Alex: That's chunked prefill, and people do it. It mitigates. It doesn't eliminate. Each chunk is still competing for compute. You're smoothing the spikes but you're still mixing two workloads that want different things from the hardware.

Jenny: So the cloud-engineer answer is: stop trying to make them coexist. Separate fleets.

Alex: Separate fleets. That's disaggregation. You build a prefill fleet — high-TFLOPS GPUs, optimized for compute throughput. And a decode fleet — high-HBM-bandwidth GPUs, optimized for memory throughput. Each fleet has its own autoscaling group, its own scaling signal, its own SLO.

Jenny: What scaling signals?

Alex: Prefill fleet scales on TTFT — time to first token — and queue depth. Decode fleet scales on TBT — time between tokens — and KV cache utilization. A burst of long-context RAG requests comes in? Prefill fleet scales out. Decode is untouched. It's the web tier slash worker tier pattern, basically.

Jenny: Okay but — and this is the part that's going to bug me — if prefill happens on one machine and decode happens on another, prefill produces this big chunk of state, the KV cache. How does that get to the decode worker?

Alex: That is the Achilles' heel. You nailed it. The KV cache for a thirty-two-thousand-token prompt on a seventy-billion-parameter model? About thirty-two gigabytes, even with grouped-query attention and FP16.

Jenny: Thirty-two gigs. Per request. You're shipping that across the network?

Alex: Across InfiniBand, ideally. GPUDirect RDMA, fifty gigabytes per second on a four-hundred-gig link. So roughly six hundred forty milliseconds for that transfer.

Jenny: Six hundred forty milliseconds is a lot. That's longer than most people's entire tolerable TTFT budget.

Alex: It is. So the systems get clever. DistServe does layer-by-layer pipelining — you start transferring layer zero's KV while you're still computing layer one. Overlap the transfer with the compute. FP8 KV cache halves the volume. And if you can keep it intra-node over NVLink at nine hundred gigabytes per second, that same transfer drops to forty-four milliseconds.

Jenny: So the whole architecture only makes sense if you've got serious interconnect. If you're trying to do this over plain TCP —

Alex: You're done. TCP adds a hundred milliseconds to a full second of transfer latency. That eats every benefit. This is one of the reasons disaggregation isn't free — you need the InfiniBand or the NVLink fabric. Without it, stay colocated.

Jenny: This is starting to feel like one of those classic infrastructure trade-offs where the fancy architecture only pays off above a certain scale. What's the threshold?

Alex: Roughly a hundred million to a billion tokens per day. Models a hundred billion parameters or larger. And prefill-heavy workloads — long inputs, like RAG over big documents, code editing, agent loops where context keeps growing.

Jenny: And below that?

Alex: Chunked prefill on a single fleet. Berkeley actually published a retrospective showing chunked prefill closes sixty to eighty percent of disaggregation's latency benefit at way less complexity. The real reason you disaggregate isn't per-request latency — it's independent scaling.

Jenny: That's a really important distinction. People sell it on latency, but the actual win is operational.

Alex: Right. Now here's where it gets fun. Once you've separated the fleets, you can size them independently. There's a notation — xPyD. X prefill replicas, Y decode replicas. So 5P3D is five prefill, three decode.

Jenny: So 1P1D is the symmetric default, and you skew based on workload shape?

Alex: Exactly. RAG-heavy traffic with long inputs? You go 2P1D, 3P1D — more prefill capacity. Creative writing where prompts are short and outputs are long? 1P2D, 1P3D — bias toward decode.

Jenny: Okay this connects to something I saw earlier. You're routing every request through prefill, then over the network, then to decode. What about a tiny request? Like, a one-line prompt with a fully cached prefix? Are you really paying a hundred milliseconds of KV transfer for that?

Alex: You just invented conditional disaggregation. That's the optimization. The router estimates net prefill compute — prompt length minus prefix-cache hits — and if it's below some threshold, like two thousand tokens, it keeps the request on the decode worker. No transfer, no fleet hop. The decode worker just does the small prefill locally.

Jenny: Right. Pay the transfer cost only when the prefill actually justifies it.

Alex: Exactly. Naive disagg pays it every time. Conditional disagg only pays when it's worth paying.

Jenny: Now I want to come back to something. You said the fleets can run different tensor parallelism degrees. TP4 prefill, TP8 decode. Why?

Alex: Because compute-heavy and bandwidth-heavy want different things. Prefill is compute-bound, so you want low TP — fewer GPUs per replica means more replicas, more aggregate compute throughput. Decode is bandwidth-bound, so you want high TP — more GPUs per replica means more aggregate HBM bandwidth per token.

Jenny: But hold on — if prefill produces a KV cache sharded across four GPUs, and decode expects it sharded across eight, those layouts don't match.

Alex: That's the catch. NVIDIA Dynamo solves it with a transpose kernel embedded in the KV transfer path. The cache gets reshaped on the fly between fleets, and the reshape is overlapped with the RDMA transfer so it's effectively free. Without that transpose, you'd be stuck running the same TP on both fleets — which kills one of the biggest reasons you disaggregated in the first place.

Jenny: That's wild. So the network transfer isn't just a dumb copy, it's actually doing layout transformation in flight.

Alex: It has to. And one last operational thing — when you split the fleets, your failure modes split too. Prefill queue saturation: TTFT spikes, prefill queue grows, decode workers sit idle waiting for KV deliveries. That means you're under-provisioned on prefill. Scale X up.

Jenny: And the other direction?

Alex: Decode-side KV cache exhaustion. Decode workers start preempting or rejecting. KV utilization pinned at a hundred percent. New requests stall after prefill completes because there's nowhere to land them. Long outputs are eating your HBM. Scale Y up, or enable KV quantization, or demote some KV to slower memory tiers.

Jenny: So you've doubled your alerting surface. Two dashboards, two SLO burn-rate alerts, two capacity plans.

Alex: Welcome to the cost of independent scaling. It's the price of admission.

Jenny: Okay, so where does this lead? If we've separated prefill and decode, what's the next move?

Alex: Two threads to pull on. One: Mooncake out of Moonshot AI took disaggregation a step further — they made the KV cache itself a separate storage tier. CXL memory pools, DRAM, NVMe. Neither fleet owns the cache. It's stateless workers around a shared cache substrate. That eliminates the locality-versus-statelessness tension entirely and lets you do prefix deduplication across thousands of concurrent requests.

Jenny: That's basically the S3-for-KV pattern. Compute is ephemeral, state lives in the storage tier.

Alex: Exactly. And the second thread — once you've decoupled compute from state, you start asking: what other parts of the inference pipeline could be their own fleet? Embeddings? Speculative draft models? Long-context attention? Disaggregation is the first cut. The next chapters get into how the routing layer above all this gets smart about it — prefix-cache-aware routing, load-aware routing, where the scheduler stops being a round-robin and starts being a real distributed-systems brain.

Jenny: So today's episode was: stop running two workloads on one GPU. Next up: what to build above all those fleets so requests actually land in the right place.

Alex: That's the arc. Disaggregation gives you the fleets. Routing decides who goes where. And once you have both, you can finally start treating LLM serving like the distributed system it actually is.
