Alex: So Jenny, I want to start today with a thought experiment. Imagine you're running a service where every single API call has to replay every previous API call from that session before it can respond. Token one, token two, token three — to generate token four, you re-execute one, two, and three from scratch.

Jenny: That sounds like the worst-designed service I've ever heard of. That's quadratic. That's O of N squared on the response length.

Alex: Exactly. And that is literally what naive transformer decoding looks like. Every new token has to run attention against all the previous tokens, which means it needs the K and V vectors — the key and value projections — for every token that came before it.

Jenny: Okay, so K and V are just intermediate computations the model uses for attention. Got it. And you're saying without caching, you recompute them every step?

Alex: Right. For a five-hundred-token response, you'd recompute token one's K and V vectors four hundred and ninety-nine times. It's completely infeasible. So the very first thing any real inference engine does is cache them. You compute K and V once during prefill, you stash them in GPU HBM, and on every decode step you just append the new token's vectors and run attention once. That brings you from N-squared down to linear.

Jenny: So this isn't an optimization. This is the thing that makes LLM serving possible at all.

Alex: Correct. The KV cache is mandatory. Think of it like a warm instance pool — you pre-computed state, you hold onto it, you don't re-bootstrap from scratch on every request to the same session.

Jenny: Okay but here's where my infra brain starts itching. You're holding state in GPU memory that scales with sequence length. Across thousands of concurrent sessions. How do you not just immediately fragment HBM into uselessness?

Alex: That is exactly the right question, and it's the question vLLM was built to answer. So the naive approach is: when a request comes in, you allocate a contiguous block of HBM sized for its maximum possible sequence length.

Jenny: Wait, the maximum possible? You don't know how long the response is going to be.

Alex: You don't. So you over-allocate, every time. And then requests finish at different lengths, leaving little gaps everywhere. vLLM measured this — sixty to eighty percent of HBM was wasted on fragmentation.

Jenny: Sixty to eighty? That's catastrophic. That's like running EC2 where most of your instance memory is permanently stranded.

Alex: It's exactly that. So the vLLM team made a beautiful move. They said — what does an operating system do when it has the same problem with process memory? It paginates. So they built PagedAttention.

Jenny: Oh. Oh, that's nice. So instead of contiguous allocation per sequence, you split HBM into fixed-size blocks, and you have a page table mapping logical token positions to physical blocks?

Alex: Exactly. Each block holds, say, sixteen tokens worth of K and V across all layers. Blocks are allocated on demand as the sequence grows. They don't have to be contiguous. A single sequence can occupy scattered blocks all over physical memory.

Jenny: And the page table is just a lookup so the attention kernel knows where to find each token's K and V.

Alex: Right. Fragmentation drops from sixty percent to nearly zero. Same HBM now holds way more concurrent sequences, which directly bumps your batch size, which directly bumps throughput.

Jenny: Hang on, there's a second thing virtual memory gives you that I bet they exploited. Page sharing. If two processes have the same library mapped, they share the physical pages.

Alex: You're getting ahead of me, but yes. And that's the entire reason prompt caching becomes natural here. If two sequences share a prefix — say, the same two-thousand-token system prompt — those blocks can literally be the same physical blocks. Shared, refcounted, zero marginal cost.

Jenny: So this is where caching jumps from within-session to cross-session. The KV cache for token positions zero through two thousand is the same physical memory regardless of which request is reading it.

Alex: Right. Customer support bots always start with the same system prompt. RAG pipelines always inject the same retrieved documents at the front. Without prompt caching, every single request runs prefill on that shared prefix and generates the exact same K and V vectors. Pure compute waste.

Jenny: So the scheduler hashes the incoming prompt's prefix, looks up whether those blocks are already in cache, and if yes, skips prefill for those tokens entirely?

Alex: Exactly. For a two-thousand-token system prompt on LLaMA-3 70B, that's roughly a hundred milliseconds of prefill saved on every single request. Anthropic exposes this as a first-class API feature — you mark a prefix as cacheable and you pay way less for it on subsequent calls.

Jenny: Okay but now I see the next problem. You said this caching is per worker. I have a fleet. Worker A has the system prompt cached, worker B doesn't. If my load balancer sends the request to B, the cache hit was useless.

Alex: And that, Jenny, is where this stops being an ML problem and becomes a distributed systems problem. The load balancer has to be cache-aware.

Jenny: Consistent hashing on the prefix?

Alex: That's the naive answer. Hash the prompt prefix, route to the worker that owns that hash range. Great cache hit rate. Terrible load distribution.

Jenny: Right, because if everyone's using the same system prompt, one worker gets all the traffic and the rest sit idle. That's a hot shard.

Alex: Exactly. The opposite extreme — pure least-connections or round-robin — distributes load perfectly but cache hit rate goes to zero. So production systems run hybrid policies. Consistent hashing as the primary signal, but with overflow when the primary worker exceeds some utilization threshold.

Jenny: So it's basically sticky routing with backpressure.

Alex: That's a great way to put it. And there's no settled best approach. The threshold, the fallback logic — that's all tuned per deployment. Active research area.

Jenny: Okay, so now I want to push on the data structure. You said vLLM uses block-level hashing — sixteen tokens per block, content-addressed. What happens when prefixes branch? Like, I have one system prompt but five different few-shot example sets.

Alex: Now you're asking the right question. Hash-based caching treats each branch as an independent entry. The shared root — the system prompt — gets duplicated in every branch's hash chain. Wasteful.

Jenny: So somebody built a tree.

Alex: SGLang did. It's called RadixAttention. They store cached KV blocks in a radix tree — a prefix trie. Root is the shared system prompt. Each node is a segment. Branches fork at the divergence point. When a new request comes in, you walk the tree from the root, following the token sequence, and you match as far as the tree goes.

Jenny: Oh, that's much nicer for branching workloads. The shared root is stored exactly once, and reference-counted across all the branches that depend on it.

Alex: Right. And SGLang's router is built around this — it routes requests with similar prefixes to the same worker to maximize tree hit rates. They've reported one-point-nine-x throughput improvement from cache-aware routing alone.

Jenny: Almost two-x just from being smart about where requests land. That's wild. Okay, last thing I want to nail down. You keep saying "in HBM." But HBM per node is what — a hundred gigs? Two hundred? At cluster scale with long conversations, that's not enough.

Alex: It is not enough. So in production, KV cache spills across a four-tier hierarchy. We call them G1 through G4. G1 is GPU HBM, one to eight terabytes per second of bandwidth, tens to hundreds of gigs of capacity. That's where active sequences and hot prefixes live.

Jenny: And G2 is host RAM?

Alex: Host CPU RAM, reachable over PCIe or NVLink-C2C. Tens to hundreds of gigs per second of bandwidth, but multi-terabyte capacity. That's where you demote idle conversations and evicted hot caches. G3 is local NVMe — five to ten gigs per second, terabytes of capacity, that's your cold cache. G4 is networked SSD or an object store. Roughly a gig per second, tens of terabytes per node.

Jenny: So this is literally a memory hierarchy. Each tier roughly an order of magnitude slower and bigger than the one above.

Alex: Exactly. And the engine decides where to demote a block based on access frequency, conversation idle time, remaining HBM budget. The key insight is the cost of a cache miss differs per tier. A G1 hit is free. G2 is PCIe latency. G3 is SSD I/O. G4 is network I/O. But even G4 is dramatically cheaper than re-prefilling from raw text.

Jenny: So the cache never really dies, it just gets demoted to colder storage. You can resume a conversation from hours ago without recomputing.

Alex: Right. And NVIDIA's Dynamo KV Block Manager — KVBM — is the productized version of this. One manager owns G1 through G4 placement across a whole cluster. Any worker can resume any session. They use NIXL-based RDMA to ship blocks around.

Jenny: That's a complete reframing. KV cache isn't ephemeral per-replica memory anymore. It's a first-class storage tier. Like an object store, but for token state.

Alex: That's exactly the trajectory. We started this episode with no cache at all — quadratic compute, infeasible. Then per-request KV cache. Then PagedAttention, which gave us per-replica prefix sharing. Then radix trees for branching reuse. Then multi-tier storage. The endpoint is a cluster-wide global KV cache with explicit storage management.

Jenny: Okay so where does this lead? What's next?

Alex: Next we go from caching to scheduling. We've been treating prefill and decode as if they happily coexist on the same worker. They don't. Prefill is compute-bound, decode is memory-bound, and when you mix them naively, long prompts starve short ones. That's where chunked prefill and disaggregated serving come in — splitting prefill and decode across different machines tuned for each phase.

Jenny: So we're about to take the same workload and shard it not just across data, but across the lifecycle stages of a single request.

Alex: Exactly. Same way you'd separate read and write replicas, except the boundary is the phase of the inference itself. That's the next episode.
