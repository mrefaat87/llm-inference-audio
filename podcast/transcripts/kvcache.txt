Alex: So Jenny, I want to start today with something that might sound familiar. Imagine you're running an auto scaling group, and every single time a new request comes in, you tear down every instance in the fleet and rebuild them from scratch before handling the request.

Jenny: That's insane. Nobody would do that.

Alex: Right? It's obviously insane. But that's essentially what LLM inference would look like without a KV cache. And I think understanding why is the key to understanding everything else we're going to talk about today.

Jenny: Okay, I'm hooked. Walk me through it.

Alex: So when a language model generates text, it works one token at a time — basically one word or word-piece at a time. And each new token needs to "look at" every previous token through this mechanism called attention. To do attention, you need these things called K and V vectors — key and value vectors — for every single previous token.

Jenny: And let me guess — computing those vectors isn't cheap.

Alex: Not cheap at all. So you have two options. Option one: every time you generate a new token, recompute the K and V vectors for every previous token from scratch. Option two: compute them once, store them in GPU memory, and just look them up.

Jenny: That's your warm instance pool analogy. You're keeping pre-computed state around instead of cold-starting every time.

Alex: Exactly. And here's where the math gets brutal without that warm pool. Without caching, generating token number 500 means recomputing K and V for all 499 previous tokens. Then for token 501, you do it again for all 500. The total work scales as O(N-squared) in the output length. For a 500-token response, you'd recompute token one's K and V vectors 499 separate times.

Jenny: That's like... rebuilding your entire capacity pool from scratch on every single request, and each rebuild gets more expensive than the last.

Alex: That's exactly what it is. So the KV cache isn't an optimization. I want to be really clear about this. It's not a nice-to-have. It's what makes inference computationally feasible at all. You compute each token's K and V vectors once during the initial processing of the prompt — that phase is called prefill — you store them in GPU high-bandwidth memory, and then each new token just appends to the cache. Each decode step goes from O(N-squared) down to O(N).

Jenny: Okay, so the KV cache is mandatory. You always have it. What's the problem then?

Alex: The problem is managing the memory. And this is where it gets really interesting for someone with your background. So the naive approach is: a request comes in, you allocate a big contiguous block of GPU memory for its KV cache, sized for the maximum possible sequence length.

Jenny: Oh no. You don't know how long the response is going to be.

Alex: You don't. So you massively over-allocate. And worse — because you're doing contiguous allocation, you get fragmentation. Requests finish at different times, at different lengths, and you end up with tons of small unusable gaps between allocations. vLLM measured 60 to 80 percent memory waste from this.

Jenny: Sixty to eighty percent? That's like running an EC2 fleet where you're paying for five times the instances you actually need because your memory allocator can't defrag.

Alex: And here's why that matters so much — GPU HBM is the single most precious resource in inference. Every megabyte of waste means fewer concurrent requests, which means lower throughput, which means you need more GPUs. Memory waste directly becomes dollar waste.

Jenny: So how does vLLM fix this? I'm guessing from the name PagedAttention that we're about to talk about virtual memory.

Alex: You're going to love this because it's literally the same idea. PagedAttention manages the KV cache exactly like an operating system manages virtual memory with paging. Physical KV cache memory gets divided into fixed-size blocks — think of them as pages. Each block holds, say, 16 tokens worth of K and V vectors across all the model's layers.

Jenny: So instead of one giant contiguous allocation per request, you're giving each request a page table that maps its logical token positions to these physical blocks.

Alex: Exactly. Each sequence gets a page table, just like a process in an OS. The blocks don't need to be contiguous in physical memory. A sequence can occupy scattered blocks all over HBM, and the page table handles the mapping.

Jenny: And you allocate on demand as the sequence grows, not upfront.

Alex: Right. No upfront reservation. You generate a token, you need a new block, you grab one from the free list. When a sequence finishes, its blocks go back to the free list immediately. No fragmentation.

Jenny: That's so clean. It's the exact same insight that solved memory fragmentation in operating systems decades ago, just applied to a completely different substrate.

Alex: And the results are dramatic. Memory fragmentation drops from that 60 percent range to near zero. The same physical HBM can now hold way more active sequences. More active sequences means bigger batches. Bigger batches means higher throughput. This was the core innovation that made vLLM so much faster than everything else when it launched.

Jenny: Okay, but I want to push on something. You said blocks can be shared between sequences with a common prefix. What does that mean in practice?

Alex: This is where we get into prompt caching, and it's a different level of caching from the KV cache itself. Think about a customer support chatbot. Every single request starts with a 2,000-token system prompt — "You are a helpful customer service agent for Acme Corp, here are our policies..." — same tokens every time.

Jenny: And without caching, every request independently runs prefill on that identical prefix, generating the exact same K and V vectors over and over.

Alex: Pure compute waste. On a model like LLaMA-3 70B, that's roughly 100 milliseconds of prefill time thrown away on every single request. Prompt caching stores those computed KV vectors and reuses them. New request comes in, the scheduler hashes the first N tokens, checks if there's a match, and if so, skips prefill for those tokens entirely.

Jenny: That's like having a pre-warmed AMI instead of bootstrapping from a base image every time you launch an instance.

Alex: Great analogy. And because of PagedAttention, the cached prefix blocks can be physically shared between sequences. The page tables for different requests just point to the same physical blocks for their common prefix. Zero marginal memory cost for the shared part.

Jenny: Hang on, this creates a distributed systems problem, doesn't it? If you have multiple GPU workers in a cluster, the cache is local to each worker.

Alex: And now you've arrived at routing-aware scheduling, which is honestly one of the most interesting unsolved problems in this space. Worker A has your system prompt cached. Worker B doesn't. If you route to Worker B, you pay the full prefill cost. Route to Worker A, it's free.

Jenny: So you need your load balancer to be cache-aware. The obvious answer is consistent hashing on the prompt prefix, right? Route all requests with the same prefix to the same worker.

Alex: That's the obvious answer, and it works great for cache hits. But what happens when that prefix is very popular?

Jenny: All your traffic goes to one worker. You've created a hotspot. It's the exact same problem we see with consistent hashing in any distributed system — you get perfect locality but terrible load distribution on hot keys.

Alex: Exactly. And the other extreme — pure load balancing, round robin, least connections — distributes load perfectly but completely destroys cache locality. Your hit rate drops to basically zero.

Jenny: So it's the classic tension between locality and load balancing. Where do production systems land?

Alex: Hybrid policies. Consistent hash routing as the primary signal, with overflow to other workers when the primary exceeds some utilization threshold. But the threshold, the fallback logic, the eviction policies — all of that is tuned per deployment. It's genuinely an active research area.

Jenny: That's fascinating. It's essentially the same problem as session affinity versus even load distribution that we deal with in every distributed system, just with a different cost function.

Alex: And there's one more evolution I want to cover. SGLang took this further with something called radix attention. vLLM's hash-based caching works in fixed 16-token blocks. Great for linear shared prefixes. But real workloads have branching patterns.

Jenny: What do you mean by branching?

Alex: Say you have a chatbot with five different system prompts, and each one has three different few-shot example sets. That's 15 different prefix branches, but they all share structure. Or multi-turn conversations that share early turns but diverge later.

Jenny: So it's like a tree.

Alex: It's literally a tree. SGLang stores cached KV blocks in a radix tree — a prefix tree. The root might be your shared system prompt. Then it branches into different few-shot example sets, and each of those branches into individual conversations. When a new request comes in, you walk the tree, matching as far as you can. You get cache hits on every shared segment, and you only need to prefill from the point where your request diverges from anything in the tree.

Jenny: That's much more memory-efficient than vLLM's approach for branching workloads, right? Because vLLM would store the shared root separately in every branch's hash chain.

Alex: Right. In hash-based caching, branch A and branch B each store their own copy of the system prompt blocks. In the radix tree, the root is stored once and branches fork naturally. SGLang's router exploits this by sending requests with similar prefixes to the same worker, maximizing tree hit rates. They report 1.9x throughput improvement from cache-aware routing alone.

Jenny: One-point-nine-x just from smarter routing. That's not a kernel optimization, that's not a new algorithm — it's a scheduling decision.

Alex: And that's what makes this space so fascinating right now. The biggest gains aren't always in the math. Sometimes they're in the systems engineering — how you manage memory, how you schedule work, how you route requests.

Jenny: Okay, so let me connect this forward. We've talked about how the KV cache makes inference possible, how PagedAttention manages that cache memory efficiently, how prompt caching reuses work across requests, and how all of this creates interesting routing problems at the cluster level.

Alex: And every one of these decisions feeds into what we'll cover next — the actual serving-level optimizations. When you start thinking about continuous batching, chunked prefill, speculative decoding — all of those interact with the KV cache and with memory management. The batch size you can run depends on how efficiently you manage KV cache memory. The prefill scheduling depends on prompt caching decisions. It's all connected.

Jenny: So the KV cache isn't just one component. It's the central resource that every other optimization in the inference stack is either feeding, managing, or competing for.

Alex: That's exactly right. It's the memory hierarchy problem that everything else revolves around. And next time, we're going to look at what happens when you start pushing on the other side — making the actual computation faster, not just the memory management. That's where quantization and custom kernels come in.

Jenny: Can't wait. This is one of those areas where the systems thinking transfers perfectly — if you understand memory hierarchies and cache management, you already have the mental model. You just need to map it onto new hardware.

Alex: And that's the whole game. Same principles, different substrate. See you next time.
