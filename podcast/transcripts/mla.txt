Alex: So Jenny, last episode we talked about the KV cache being the silent killer of long-context serving. I want to pick up exactly there, because there's an architectural innovation that basically broke that wall.

Jenny: Okay, set the stage for me again. We had this problem where the KV cache grows linearly with sequence length, right? And at some point it eats more memory than the model itself.

Alex: Exactly. Take a 70B model with standard multi-head attention. KV cache per token is around 4.7 megabytes. Sounds tiny. Now serve a 100k-token context.

Jenny: 4.7 megs times 100,000... that's 470 gigabytes. For one request.

Alex: For one request. And the model weights in FP16 are only 140 gigs. So the cache, the scratch space, is more than three times bigger than the actual program.

Jenny: That's wild. That's like running a microservice where the session state per user is bigger than the binary. So how have people been coping? Because we've been serving long contexts for a while now.

Alex: The first wave was GQA and MQA — group-query and multi-query attention. The idea is, instead of every query head having its own dedicated K and V heads, you share. Maybe 64 query heads share 8 K/V heads. That's an 8x reduction.

Jenny: So it's basically deduplication. Same logical cache, fewer physical replicas.

Alex: Right. You're sharing pointers. But there's a ceiling — even MQA, the most aggressive version with one K/V head for all 64 query heads, only gets you 64x reduction. And quality starts to degrade if you push too far.

Jenny: So sharing has diminishing returns. What did DeepSeek do differently?

Alex: This is where it gets interesting. DeepSeek looked at the problem from a completely different angle. They said: forget sharing. Let's compress.

Jenny: Compress how? Like, gzip the cache?

Alex: Conceptually similar, but learned. Their observation was — if you have 64 heads each with a 128-dimensional K vector, that's 8,192 numbers per token per layer. But those numbers aren't independent. They all came from the same token embedding, projected through related matrices. There's massive redundancy.

Jenny: Oh wait. That's exactly like... you know how when you cache a bunch of derived views of the same underlying record, you don't actually need to cache all the views — you can cache the source and re-derive on read?

Alex: That is exactly the insight. MLA — Multi-head Latent Attention — learns to project all the K and V information into one tiny latent vector per token. Then at attention time, when you actually need the per-head K and V, you reconstruct them on the fly.

Jenny: So the cache stores the compressed source, and you pay a little compute to expand it back when you need to read.

Alex: Right. And the numbers are stunning. DeepSeek-V2 reported 93% KV cache reduction versus their MHA baseline. With no meaningful quality loss on benchmarks.

Jenny: 93%. That 470 gig number we started with — what does it become?

Alex: Roughly 30 gigs. For the same 100k-token context.

Jenny: Hold on. That's not an optimization, that's a regime change. You go from "we need a multi-GPU pod just for the cache" to "this fits comfortably on a single H100."

Alex: That's why this matters. Long-context serving was economically punishing because of memory, not compute. MLA didn't make the model smarter — it made very long context economically viable.

Jenny: Okay but I want to push on the compute side. You said you reconstruct K and V at attention time. That's matrix multiplications you didn't have before. How is that free?

Alex: Great question. For DeepSeek-V2 with 80 layers, you're adding about 1.3 billion extra FLOPs per decode step. Sounds bad.

Jenny: Yeah, that sounds bad.

Alex: It's not. Because decode is memory-bandwidth-bound, not compute-bound. The arithmetic units on the GPU are sitting idle waiting for HBM to deliver the cached KV.

Jenny: Oh. Oh that's beautiful. So you're using spare capacity that was being wasted anyway.

Alex: Exactly. The bottleneck was loading cached KV from HBM. You just cut that load by 93%. The extra arithmetic to decompress fits in the slack the memory wait was already creating.

Jenny: That's like... in autoscaling terms, you had a fleet that was CPU-idle but network-saturated. So you trade some idle CPU to compress the payload, and your effective throughput goes up.

Alex: Perfect mapping. And there's a crossover point worth knowing about. For very short sequences — say batch one, fewer than 100 tokens — the decompression overhead is non-trivial relative to the tiny attention matmul. Below that, plain GQA can actually be faster.

Jenny: But production serving basically never sits down there.

Alex: Almost never. Once you're at any reasonable batch size or context length, MLA wins. So in practice it's just always on.

Jenny: Now I have to ask the obvious question. KV cache quantization. People have been talking about that forever — store the cache in INT8 or FP8 instead of FP16. Isn't that the same idea?

Alex: It sounds like the same idea, and this is actually the most common point of confusion. They're orthogonal axes. They compose multiplicatively.

Jenny: Walk me through it.

Alex: MLA changes how many numbers you store per token. It's an architectural change — you have to train it in. You can't bolt MLA onto an existing GQA model after the fact. Quantization changes how many bits per number. It's a post-training compression — same architecture, different precision.

Jenny: So one shrinks the count, one shrinks the size of each entry.

Alex: Right. And because MLA's cache is still just tensors, you can quantize those tensors. DeepSeek-V2 and V3 production deployments do exactly this — MLA for the architectural shrink, then FP8 on the latent for another multiplicative reduction.

Jenny: Is there a catch? Because compression on top of compression usually has a catch.

Alex: There is. MLA's latent is already information-dense — there's not much redundancy left for quantization to safely throw away. So aggressive quantization hurts it more per bit than it hurts a fat MHA cache. In practice people stop at FP8 rather than pushing INT4 without careful calibration.

Jenny: That makes sense. You squeezed out the slack with MLA, so the remaining bits matter more.

Alex: Exactly. Mental model: MLA reduces how many numbers you store. Quantization reduces how many bits per number. Different axes, multiply together.

Jenny: Okay, last question on this. Why is everyone adopting it? Like, Kimi K2, others — what's driving the consolidation?

Alex: It's a co-design philosophy. The parts of the architecture that scale badly with context — attention heads, KV cache memory — you shrink. The parts that scale well — MoE experts, sparse compute — you grow. Kimi K2 combines MLA with reduced attention head count and aggressive expert sparsity. The result is they can serve 128k contexts at costs competitive with much shorter-context models.

Jenny: So it's not just MLA in isolation. It's MLA as part of a coherent rebalancing of the architecture.

Alex: Right. I think of MLA as what FlashAttention was for attention memory. FlashAttention didn't change the algorithm, it changed how memory was used. MLA doesn't change attention either — it changes the memory cost from order num-heads times d-head times context, down to order d-latent times context. And d-latent is a tiny number.

Jenny: That's the kind of change where five years from now we'll look back and say of course it works that way.

Alex: I think that's right. The industry is converging on MLA-style compression for any frontier long-context model.

Jenny: So where does this lead us next? If KV cache is no longer the wall, what is?

Alex: Two directions, and they're both fascinating. One — if you can shrink the cache 93%, you start asking, why have a growing cache at all? That's where state-space models like Mamba come in. They replace the per-token cache with a fixed-size recurrent state. Imagine if instead of per-session storage that grows forever, you had a constant-size session token that summarizes everything.

Jenny: That's a wildly different memory model.

Alex: Wildly different. And the second direction is about decode latency. We've been talking about memory, but even with a tiny cache you still decode one token at a time. What if you could speculate — predict multiple future tokens in parallel?

Jenny: Like speculative execution in a CPU pipeline.

Alex: Exactly that. Multi-token prediction is the inference world's version of branch prediction and speculative execution. You guess ahead, verify cheaply, and roll back if you're wrong.

Jenny: Okay, I'm hooked. So next episode we're going from "how do we store less" to "how do we predict more."

Alex: That's the arc. From attention variants to state-space models to speculative decoding. Each one is the natural next question once you've solved the previous bottleneck.
