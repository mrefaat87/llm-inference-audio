Alex: So Jenny, last time we talked about attention — how it's basically a load balancer that routes each token's query to the most relevant keys across the sequence. One set of queries, keys, and values, and you get this beautiful relevance-weighted routing. But here's the thing — what if I told you that one load balancer isn't enough?

Jenny: Okay, I'll bite. Why not? If the attention mechanism already figures out which tokens are relevant to which, what's missing?

Alex: Let me give you a sentence. "The animal didn't cross the street because it was too tired." Now think about the word "it." What does "it" refer to?

Jenny: The animal. That's obvious.

Alex: Right. Now think about "cross" — what's the subject of that verb?

Jenny: Also the animal.

Alex: And "tired" — what does that modify?

Jenny: The animal again, but through "it."

Alex: And "didn't" — what's its scope? What's being negated?

Jenny: The crossing. "Didn't cross."

Alex: So you just identified four completely different relationship types in a single sentence. Coreference — what does a pronoun point to. Syntactic parsing — subject-verb binding. Modifier attachment — what does an adjective describe. Negation scope — what's being negated. Four independent routing decisions, all happening simultaneously.

Jenny: Oh, I see where this is going. A single attention operation is like having one load balancer with one routing policy. You can route by latency, or you can route by session affinity, but you can't do both with the same rule set.

Alex: Exactly. A single attention head will learn to specialize in one of those patterns — maybe coreference, maybe syntax — but it physically cannot learn all four simultaneously. It has one set of Q, K, V weight matrices, so it learns one projection of the data, one way of defining "what's relevant to what."

Jenny: So multi-head attention is... running multiple load balancers in parallel, each with its own routing policy?

Alex: That's it. Instead of one set of W_Q, W_K, W_V matrices, you have H sets. Each head gets its own projection matrices, runs its own independent attention computation, and can specialize in a completely different relationship type.

Jenny: Okay, but hang on — that sounds expensive. If I'm running, say, 96 independent attention operations instead of one, haven't I just multiplied my compute by 96?

Alex: This is the clever part, and it maps perfectly to something you'd recognize from capacity planning. You're not adding capacity — you're partitioning it. Each head doesn't operate on the full d_model dimension. If d_model is 12,288 and you have 96 heads, each head works in a subspace of size 128. That's d_model divided by H.

Jenny: So it's like... instead of one giant instance handling all traffic, you shard into 96 smaller instances, each handling a slice of the feature space?

Alex: Precisely. The total compute is identical to running one big attention operation. You're splitting the representational space, not duplicating it. Each head gets a narrow view — 128 dimensions out of 12,288 — but within that narrow view, it can specialize completely.

Jenny: And then what? You have 96 little output vectors — how do they come back together?

Alex: Concatenation. Each head produces a vector of size d_head — 128 in our example. You line up all 96 of them end to end, and you're back to a 12,288-dimensional vector. Then there's one more matrix — W_O, the output projection — that mixes across all those head outputs. Think of it as the final aggregation layer that lets the heads' findings interact with each other.

Jenny: That W_O step is interesting. Without it, the heads would be completely independent, right? They'd never share information.

Alex: Right. The concatenation alone just stacks results. W_O is what lets the model learn "when head 17 found a strong syntactic link AND head 42 found a semantic similarity, that combination means something specific." It's the cross-head communication channel.

Jenny: So does this specialization actually happen? Or is it just a nice theory? Like, do heads really end up learning different things, or is it more like they all learn vaguely similar patterns and you just get redundancy?

Alex: Great question, and the answer is yes — real, measurable specialization emerges. Researchers have probed trained models and found heads that consistently do specific jobs. Some track syntactic dependencies — subject to verb, verb to object. Some do coreference resolution. Some are positional — they literally just attend to the previous token or the next token. Some find semantic similarity. Some even specialize in rare or unusual tokens.

Jenny: Wait — nobody programs that? Nobody says "head 17, you do syntax"?

Alex: Nobody. It's entirely emergent. Gradient descent discovers that specializing heads produces better predictions, so it pushes the weight matrices apart. You start with random initialization, and training pressure carves out these specialized roles. It's like how in a distributed system, you might not explicitly assign roles to nodes, but under load, certain nodes naturally end up handling certain traffic patterns based on how the routing evolves.

Jenny: That's kind of wild. Okay, so we've got heads adding width — parallel specialization within a single layer. But there are also multiple layers stacked. How does that interact?

Alex: This is an important distinction. Heads give you width — multiple perspectives at the same level of abstraction. Layers give you depth. Each transformer layer has its own complete set of multi-head attention matrices. Layer 1's heads are completely independent from layer 50's heads — different weights, different learned patterns, different everything.

Jenny: And that matters because...

Alex: Because the input to layer 50 is nothing like the input to layer 1. By the time you're 49 layers deep, the representation has been refined and abstracted so many times that the "tokens" are no longer anything like words. They're high-level semantic constructs. So the heads in early layers tend to learn surface-level patterns — positional, syntactic — while heads in deep layers learn abstract semantic relationships. It's like a processing pipeline. Your first middleware parses headers. Your last middleware makes business logic decisions. They're doing fundamentally different jobs because the data they see is at different levels of processing.

Jenny: That's a beautiful analogy. So for GPT-3 with 96 layers and 96 heads per layer, you've got...

Alex: 9,216 total attention heads. An enormous space for diverse specialization across both the width and depth of the network.

Jenny: Alright, so now I want to talk about the elephant in the room. KV cache. Every head needs to store its K and V vectors for every token in the sequence, right?

Alex: And this is where multi-head attention goes from elegant to expensive. Let's do the math for GPT-3 in FP16. Each token needs 2 vectors — K and V — per head, per layer. That's 2 times 96 heads times 128 dimensions per head times 96 layers times 2 bytes per value. That's 4.7 megabytes per token.

Jenny: Per token! So for a 100K context window...

Alex: You're looking at hundreds of gigabytes of HBM just for the KV cache. Not the model weights — just the cache of intermediate attention state.

Jenny: That's like... every active request in your system needing its own dedicated memory pool that scales linearly with session length. That's a capacity nightmare.

Alex: And that's exactly why the industry developed variants to attack this. There's a spectrum. Full multi-head attention — MHA — is the baseline. Every query head has its own dedicated K and V head. Maximum quality, maximum memory.

Jenny: What's the alternative?

Alex: The key insight is that K and V information is more redundant across heads than Q information. Think about it this way — queries are asking different questions, so they need to be diverse. But the keys and values — the things being queried — are more compressible. Multiple query heads can share the same keys and values without losing much.

Jenny: That's like... a fleet of load balancers that each have their own routing rules but all consult the same backend health check data. The routing logic needs to be independent, but the health data they're routing against can be shared.

Alex: That's a fantastic analogy. So Grouped Query Attention — GQA — takes, say, 64 query heads but only 8 K/V head groups. Every group of 8 query heads shares one K head and one V head. That's an 8x reduction in KV cache size.

Jenny: And that's what LLaMA 3 uses?

Alex: LLaMA 3 70B, yes. 64 query heads, 8 KV groups. And then at the extreme end, you have Multi-Query Attention — MQA — where ALL query heads share a single K head and a single V head. That's a 1/H reduction. For 96 heads, that's a 96x reduction in KV cache.

Jenny: What's the quality tradeoff?

Alex: GQA — minimal. Barely measurable on most benchmarks. MQA — slightly more noticeable, but still surprisingly small. The fact that K and V are compressible this way was honestly one of the more surprising findings in the field. Models like PaLM and Falcon use MQA and perform extremely well.

Jenny: So for anyone running inference infrastructure, this is a massive operational lever. The difference between needing 8 GPUs and needing 1 GPU for the same context length, just from choosing GQA over MHA.

Alex: Exactly. And it directly affects how many concurrent requests you can serve, how long your contexts can be, how much your KV cache memory constrains your batch size. This is one of those architecture decisions that has enormous downstream infrastructure implications.

Jenny: Okay, so let me make sure I've got the full picture. Multi-head attention splits the representational space into parallel subspaces, each specializing in different relationship types. The compute stays the same — you're partitioning, not duplicating. Heads add width within a layer, layers add depth across the network. And the KV cache cost scales linearly with heads, which is why GQA and MQA exist — they share K and V across query heads because that information turns out to be redundant.

Alex: That's a clean summary. And here's why this matters going forward — when we get into inference optimization, understanding this head structure is critical. Techniques like prefix caching, speculative decoding, even tensor parallelism — how you shard attention heads across GPUs — they all depend on understanding this anatomy. The head is the fundamental unit of attention computation, and how you manage, share, and distribute heads determines your serving efficiency.

Alex: Exactly. We've built up the individual components — embeddings, the attention mechanism, now multi-head attention with its variants.
