Alex: So Jenny, I want you to imagine something. You're running a fleet of stateless web servers behind an ALB. Every request comes in, gets processed, response goes out, server forgets everything. Clean, simple, horizontally scalable. That's basically how most LLM inference works today for single-turn requests.

Jenny: Right, and that's the dream, isn't it? Stateless is easy. No session affinity, no sticky routing, any server can handle any request. You can scale horizontally all day long.

Alex: Exactly. Now here's the problem. What happens when instead of independent requests, you have a conversation? Like a chat session where every new message depends on everything that came before it.

Jenny: Well, the model needs context, right? So you'd have to send the full history each time.

Alex: That's exactly what happens. And this is where it gets expensive in a way that might surprise you. Turn one, maybe five hundred tokens. Fine. Turn two, you're sending those original five hundred, plus the four hundred token response the model generated, plus your new two hundred token message. That's eleven hundred tokens. By turn five you're at thirty-five hundred. By turn ten, you could be looking at eight to fifteen thousand tokens.

Jenny: Oh, so it's not linear growth in cost. It's — wait, it's like quadratic in the total conversation length, right? Because each turn you're re-processing everything that came before, plus the new stuff.

Alex: Exactly right. Every turn, the server re-prefills the entire history from scratch. It's already computed attention over all those earlier tokens before. It throws that work away, and then does it again with the new message appended. It's like if every time a user hit your web app, you replayed their entire session from the first click, rebuilt all the state, just to serve the next page.

Jenny: That sounds insane. Why would anyone design it that way?

Alex: Because the alternative is keeping state alive between turns. And the moment you do that, you lose everything that made stateless inference easy. You're now in the world of session affinity, memory pressure, eviction policies, failure recovery — all the hard distributed systems problems.

Jenny: Okay, so walk me through that. What state are we actually talking about keeping alive?

Alex: The KV cache. When the model processes your prompt during prefill, it computes key and value vectors for every token at every layer of the network. Those vectors are what the model uses during attention — they're the model's "memory" of the conversation. In the stateless world, those get evicted the instant the response finishes. In the stateful world, you keep them around so the next turn only has to prefill the new tokens.

Jenny: So it's like keeping a warm instance pool. Instead of cold-starting a new instance for every request, you keep instances warm with the session state already loaded.

Alex: That's a perfect analogy. And the savings are dramatic. In the stateless approach, turn ten of a conversation re-prefills all ten turns of accumulated history. In the stateful approach, turn ten only prefills the new message — maybe a couple hundred tokens instead of ten thousand.

Jenny: Okay, so the economics are obvious. Why isn't everyone doing the stateful approach?

Alex: Four reasons, and every single one maps to a distributed systems problem you've dealt with. Number one: routing affinity. If the KV cache for conversation ABC lives on server seven, every subsequent turn of that conversation has to go to server seven. Your load balancer now needs consistent hashing on conversation ID.

Jenny: Which is fine until you get hot spots. Some conversations run for fifty turns, some users are way more active than others, and suddenly server seven is saturated while servers one through six are twiddling their thumbs. It's the same problem as session-sticky load balancing with uneven session sizes.

Alex: Exactly the same problem. And it gets worse because of challenge number two: memory pressure. These KV caches are not small. For a model like LLaMA 3 70B, you're looking at roughly 0.3 megabytes per token of KV cache. A twenty-turn conversation with five hundred tokens per turn — that's ten thousand tokens, about three gigabytes of GPU high-bandwidth memory. Per conversation. On top of a hundred forty gigs of model weights.

Jenny: Three gigs per active conversation? So if I have a hundred concurrent long conversations on one GPU server, that's three hundred gigs of KV cache alone?

Alex: Right. And that memory is competing directly with your ability to process new requests. Every gigabyte of HBM holding old conversation state is a gigabyte not available for batching new incoming requests. So you need an eviction policy.

Jenny: LRU across conversations?

Alex: LRU is the starting point, yeah. But here's the nuance — when you evict a conversation's KV cache, it's not catastrophic. The client always sends the full text history as a fallback. So the server just re-prefills from text. It's transparent to the user, just slower and more expensive on that turn.

Jenny: Oh, that's actually a nice property. It degrades gracefully. You lose the optimization but not the correctness. Like falling back from a cache hit to a database read.

Alex: Exactly. And that's a key design principle — the text is the source of truth, always. The KV cache is a derived artifact. Expensive to compute, but regenerable. You're managing two representations with completely different storage economics. Text is kilobytes. KV cache is gigabytes.

Jenny: So what does the full system design look like? Because I'm imagining multiple tiers here.

Alex: You're right to think in tiers. Picture it as four layers. At the client layer, every message includes a conversation ID and the full text history. The client doesn't know or care whether the server has cached KV — it always sends everything. The server decides.

Jenny: Smart. Keep the client dumb, let the server optimize.

Alex: Routing layer: consistent hash on conversation ID to a worker group. Within that group, prefer the specific worker with the warmest cache. But — and this is critical — add overflow routing when the primary worker exceeds a utilization threshold. It's the same hybrid locality-versus-load-balance tradeoff you see in cache-aware routing for CDNs.

Jenny: So you're saying, try to hit the cache-warm server, but don't let that server drown. Spill over to other servers if needed, accepting the re-prefill cost as the price of keeping the system healthy.

Alex: Exactly. At the serving layer, each worker maintains a KV cache pool with LRU eviction. And here's something production teams track: cache hit rate by conversation depth bucket. Turns one through three, four through ten, ten plus. Because the value of a cache hit increases dramatically with depth. Evicting a two-turn conversation costs you maybe a thousand tokens of re-prefill. Evicting a twenty-turn conversation costs you fifteen thousand.

Jenny: So you'd bias your eviction toward short conversations, where the re-prefill penalty is small.

Alex: Right. And then the storage layer — for really valuable long-running sessions, you go multi-tier. Hot conversations stay in GPU HBM. Warm-but-idle conversations get demoted to CPU RAM. Cold conversations evict entirely to text-only. Each tier has a different restoration latency. HBM is instant. CPU RAM requires a transfer back to GPU — maybe tens of milliseconds. Text-only means full re-prefill, which could be seconds for a long conversation.

Jenny: It's literally a memory hierarchy. L1, L2, main memory, disk. Same concepts, just at conversation scale instead of CPU cache scale.

Alex: Perfect mapping. Now, there's a third challenge I haven't mentioned that I think will really resonate with you. Disaggregated inference.

Jenny: Where you split prefill workers from decode workers, like separating read replicas from write primaries.

Alex: Right. But here's the tension. In a disaggregated setup, where does the KV cache live between turns? If it lives on the decode worker that handled the last turn, you now need affinity to that specific decode worker. But the whole point of disaggregation was that decode workers should be interchangeable for scheduling flexibility.

Jenny: Oh no. So the optimization that makes multi-turn cheap — keeping the KV cache warm — directly conflicts with the optimization that makes disaggregation work — stateless interchangeable workers.

Alex: Exactly. And if you try to solve it by putting KV cache in a separate storage tier, like Mooncake does, you add network transfer latency loading it back on every turn. There is genuinely no clean solution today. This is an active area of research.

Jenny: Okay, there's one more thing bugging me. What happens when you update the model? Even a minor checkpoint change?

Alex: Great instinct. KV cache vectors are outputs of specific weight matrices in the model. If those weights change — even slightly, even a LoRA adapter swap or a quantization change — every cached KV tensor is numerically wrong for the new model. There's no migration path. The latent space geometry has changed.

Jenny: So a model update invalidates your entire warm cache pool. That's like rotating encryption keys — everything encrypted with the old key is unreadable.

Alex: Right. Production systems handle this with versioned cache namespacing. Each model version gets its own isolated cache pool. When you roll out a new version, you do a blue-green deployment. New replicas spin up, traffic shifts gradually, old replicas keep serving existing warm sessions until those conversations naturally complete.

Jenny: So you drain the old cache rather than invalidating it. That's elegant. What about sampling parameters though? If I change temperature between turns, does that blow away my cache?

Alex: No, and this is a subtle but important distinction. Temperature, top-p, top-k — those are applied after the forward pass. They modify how you pick the next token from the probability distribution, but they don't affect the KV vectors that attention computed. So changing temperature between turns does not invalidate the cache.

Jenny: Wait, but — if I used high temperature on turn three and got a creative, unusual response, those generated tokens are now part of the context. The KV cache includes vectors for those specific tokens. If I'd used low temperature, I'd have gotten different tokens, different KV vectors.

Alex: Exactly right, and that's why systems like vLLM include generated token IDs in the cache key hash. A cache hit requires matching both the prompt tokens and the generated tokens. So the cache is self-consistent — it won't serve you stale vectors from an alternate generation path.

Jenny: That's a really clean design. The cache key is the full token sequence, not just the input.

Alex: Right. So to pull this all together — multi-turn inference is fundamentally a long-context problem that gets progressively worse through the session. The industry is moving from stateless re-prefill toward KV persistence, but that transition brings all the classic distributed state management challenges: affinity, eviction, memory hierarchies, failure recovery.

Jenny: And the key design insight is that graceful degradation always falls back to text. You can always re-derive the KV cache from the conversation text. You lose the optimization, not the correctness.

Alex: Which means you can be aggressive about caching without being afraid of cache loss. The failure mode is "slower," not "broken."

Jenny: I love that. Alright, so where does this lead? What's coming next?

Alex: Next we're getting into disaggregated inference — actually splitting prefill and decode onto different hardware, different scaling groups. And the multi-turn tension we just talked about is going to come roaring back, because now you have to figure out how to move KV cache between workers that are explicitly designed to be independent. Plus, we'll dig into how scheduling changes when your prefill and decode stages have completely different resource profiles — prefill is compute-bound, decode is memory-bound, and you want to pack them differently.

Jenny: So it's like we've been talking about the statefulness problem in the abstract, and next we actually have to solve it in a system where the architecture is fighting against you.

Alex: Exactly. The constraints multiply. And that's where the really clever engineering is happening right now — Mooncake's KV store approach, Ray Serve's placement groups, NVIDIA Dynamo's routing layer. It's going to be a good one.
