Alex: So I want to start with something that sounds obvious but actually breaks a lot of intuition. When you talk to a chatbot — like, you send message one, it replies, you send message two — what do you think the server is actually doing between those two messages?

Jenny: I mean, I'd assume it's holding the conversation in memory, right? Like a session. The way any stateful service would.

Alex: That's the intuition. And it's wrong for almost every production system today.

Jenny: Wait, really?

Alex: Most systems are completely stateless between turns. The moment your first reply finishes streaming, the server throws everything away. The KV cache, the attention state, all of it — gone. When you send turn two, the client sends back the entire conversation history as a fresh prompt, and the server re-prefills the whole thing from scratch.

Jenny: Hold on. So if I'm on turn ten of a conversation, the server is reprocessing turns one through nine every single time?

Alex: Every single time. Turn one, five hundred tokens. Turn two, you're at eleven hundred. Turn ten, you might be at eight thousand, fifteen thousand tokens — and the model is prefilling all of it before it can generate the first token of the new response.

Jenny: That is wildly wasteful. Why would anyone build it that way?

Alex: Because it makes the operational story trivially simple. Think about it from your world — if every server is stateless, what does your load balancer have to do?

Jenny: Nothing. Round robin. Any instance can take any request. No session affinity, no sticky sessions, no consistent hashing. If an instance dies, the retry just hits another one.

Alex: Exactly. It's the same reason stateless web tiers won. Operationally, it's a dream. The cost is just... compute. You're burning GPU cycles re-prefilling material you already processed five seconds ago.

Jenny: Okay, so the alternative is — keep the KV cache alive between turns?

Alex: Right. That's architecture two. After turn one finishes, you don't evict the KV cache. You park it — in HBM if you have room, in CPU RAM as a second tier, or in a dedicated KV store like Mooncake. Turn two arrives, you only prefill the new tokens, and you append onto the existing cache.

Jenny: So instead of ten times a growing sum, you pay ten times the average new tokens per turn. That's a huge difference.

Alex: It's the difference between quadratic and linear cost growth across a session. And for long conversations, agentic loops, extended thinking — that gap is the whole ballgame economically.

Jenny: Okay so why isn't everyone doing this? What's the catch?

Alex: There are four catches, and they're all infrastructure problems you'll recognize. First one: routing affinity. If conversation X's KV cache lives on server A...

Jenny: ...every subsequent turn for X has to land on server A. Session affinity. Consistent hashing on conversation ID.

Alex: Right. And what's the failure mode of consistent hashing under skewed traffic?

Jenny: Hot spots. One viral conversation or one chatty power user pins a single worker while the rest of the fleet is idle. We see this all the time with sticky-session web tiers.

Alex: Same problem here, just with a worse blast radius because GPUs are expensive and you can't just spin up another one in thirty seconds. So you need overflow routing — something like, "prefer the warm worker, but if it's above eighty percent utilization, spill to a cold one and eat the re-prefill cost."

Jenny: That's the same hybrid you'd build for any cache-locality-versus-load-balance tradeoff. Okay, what's catch number two?

Alex: Memory pressure. These KV caches are live. You can't evict them without losing the cheap-continuation property. And they're not small — for LLaMA-3 70B with grouped-query attention, you're at roughly 0.3 megabytes per token. A ten-thousand-token conversation is three gigabytes of HBM, just sitting there, per active session.

Jenny: On top of the model weights.

Alex: On top of 140 gigabytes of model weights, yeah. So now your KV pool is competing with new request processing for the same HBM. You need an eviction policy — LRU across conversations, recency-weighted, or you charge customers for "warm context" and let pricing do the eviction for you.

Jenny: That last one is interesting. That's basically reserved capacity versus on-demand.

Alex: Exactly that. And here's the nice part — if you do evict a conversation's KV cache, the next turn just falls back to full re-prefill from text. Slower, more expensive, but functionally transparent. The user doesn't see an error, they see latency.

Jenny: Graceful degradation. Okay, catch three.

Alex: This one's gnarly. Disaggregation. Remember, modern serving splits prefill workers from decode workers because they have different resource profiles — prefill is compute-bound, decode is memory-bandwidth-bound. Different instance types, basically.

Jenny: Right, like splitting reads and writes onto different replica fleets.

Alex: Now ask the question: where does the KV cache live between turns?

Jenny: Oh. Hm. If it's on the decode worker that handled the last turn, I need affinity to that specific decode worker. But the whole point of having a decode pool was that they're interchangeable.

Alex: You just broke the design. The interchangeability was the feature. Now you've introduced state into a tier that was supposed to be stateless for scheduling flexibility.

Jenny: So the alternative is what — a separate KV storage tier?

Alex: That's Mooncake's bet. Pull the KV out into its own fabric, load it back into whatever decode worker picks up the next turn. But now you're paying network latency to hydrate the cache on every turn.

Jenny: There's no clean answer here.

Alex: There's no clean answer today. This is genuinely an open problem. Which brings us to catch four — dual representation. The conversation text and the KV cache are two different artifacts with completely different storage economics.

Jenny: Text is kilobytes, KV is gigabytes.

Alex: And different durability requirements. The text is the source of truth — you persist it durably, replicate it, back it up. The KV cache is derived. Expensive to compute, but if you lose it, you can always regenerate it from the text. So you end up with this two-system design — durable text store plus ephemeral, tiered KV cache.

Jenny: That's basically a memory hierarchy. Hot in HBM, warm in CPU RAM, cold means "we kept the text, we'll rebuild the KV if you come back."

Alex: That's exactly the model. And each tier has a different restoration cost — HBM hit is free, CPU RAM is a memcpy, cold means full re-prefill. You pick your eviction policy by watching cache hit rate per conversation depth bucket. Turns one through three behave totally differently from turns ten and beyond.

Jenny: Okay let me ask the practical question. Most teams aren't building Mooncake. What can they actually do today?

Alex: Prefix caching. It's the middle ground that's basically everywhere now — Anthropic's prompt caching, vLLM's automatic prefix cache, SGLang's RadixAttention. You're not persisting the whole session, but you're caching shared prefix bytes across requests. And this is where prompt structure becomes a real engineering lever.

Jenny: How so?

Alex: The cache only fires on shared prefix bytes. So the composition of your prompt directly controls how much hits cache. The single biggest rule: stable content early, novel content late.

Jenny: So... system prompt first, then tools, then retrieved docs, then conversation history, then the new user message at the very end?

Alex: That order, exactly. And the failure modes are brutal. If you inject a timestamp or a request UUID into the system prompt — "current time, colon, fourteen thirty-two oh seven" — your divergence point just moved to byte zero. Every turn is a full re-prefill.

Jenny: Oh that's painful. So the timestamp belongs in the user message, not the system block.

Alex: Right. And tool definitions are part of the prefix too. If you add a tool mid-conversation, or reorder them, you've invalidated everything from the tool block onward. Define the full set up front, append-only.

Jenny: This feels like normal-form database design. Factor out the stable part, isolate the dynamic part.

Alex: That's a perfect way to put it. It's free throughput. Same model, same engine, just a prompt layout that lets the cache do its job.

Jenny: One last thing nagging me — what happens to all this cached KV when you push a new model version?

Alex: Throw it all out. The KV vectors are outputs of specific W_K and W_V weight matrices. New checkpoint, new adapter, new quantization — even minor — and the cached tensors are numerically wrong for the new attention. You can't migrate them, the latent space geometry has changed.

Jenny: So in practice it's versioned cache namespacing? Blue-green the model, drain the old cache via LRU?

Alex: Exactly. New replicas spin up with their own cache pool, traffic shifts gradually, old replicas keep serving their warm sessions until they complete. Standard deploy pattern, just applied to a cache that happens to be gigabytes per session.

Jenny: Okay, so where does this all go next? What should I be paying attention to?

Alex: So we just spent this whole episode talking about KV cache as the central object — where it lives, who owns it, how to route to it, how to evict it. The next layer of the conversation is: what happens when conversations stop being conversations and start being agents?

Jenny: Meaning the model's calling tools, looping, branching its own state?

Alex: Right. Suddenly a single "session" might be a tree, not a line. You've got speculative branches, parallel tool calls, sub-agent invocations — and each one has its own KV trajectory. The architectures we just described start to bend in really interesting ways.

Jenny: And I'm guessing disaggregation gets even weirder there.

Alex: It gets a lot weirder. Prefill, decode, and now think about a workload that's mostly decode-bound but with bursty prefill spikes when tools return. The scheduler problem is the next chapter, basically.

Jenny: Alright, that's the cliffhanger. We'll pick that up next time.

Alex: See you then.
