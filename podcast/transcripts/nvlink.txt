Alex: So today we're talking about GPU memory and interconnects — basically, what lives where inside a GPU server, and how fast data can move between different places.
Jenny: And this matters for inference because... the speed of moving data is actually the bottleneck, not the math?
Alex: Exactly right. So picture a GPU like an H100. Inside it, there's this hierarchy of memory, and each level has wildly different speeds. At the very top, you've got registers — tiny bits of memory right next to each compute core. Multiple terabytes per second of bandwidth. Blazing fast, but tiny.
Jenny: Like having a sticky note on your desk versus a filing cabinet across the room.
Alex: Perfect analogy. Then you've got shared memory, or SRAM — about 50 megabytes total, running at roughly 20 terabytes per second. This is where FlashAttention does its magic, keeping attention tiles in this fast on-chip memory instead of going to the slower stuff.
Jenny: And the slower stuff is HBM — the main GPU memory?
Alex: Right. HBM is 80 gigs on an H100, with 3.35 terabytes per second of bandwidth. That sounds fast, but it's about 6x slower than SRAM. And here's the key insight — during decode, when you're generating tokens one at a time, the GPU is barely doing any math relative to the data it needs to read. You have to load the entire model weights from HBM for every single token.
Jenny: So decode is memory-bandwidth-bound, not compute-bound. That's why people obsess over HBM bandwidth numbers.
Alex: Exactly. It's why the H100 SXM version is meaningfully faster at decode than the H100 PCIe, even though they have identical compute. The SXM has 3.35 terabytes per second of HBM bandwidth versus 2 for PCIe. Same math speed, faster memory, faster inference.
Jenny: OK so that's inside one GPU. What about when you need multiple GPUs working together?
Alex: That's where NVLink comes in. On a DGX H100 system, you've got 8 GPUs connected via NVLink at 900 gigabytes per second bidirectional per GPU. And there's an NVSwitch chip that creates a full mesh — any GPU can talk to any other at full speed simultaneously.
Jenny: Wait, 900 gigabytes per second? That's a quarter of HBM bandwidth. That's actually really fast for an interconnect.
Alex: It is, and it's what makes tensor parallelism work. Tensor parallelism needs an all-reduce after every single layer — every GPU shares its partial results with all others. At 900 gig per second, that completes in microseconds. Totally practical.
Jenny: So what happens when you need to go across servers? Like in a big cluster?
Alex: You drop to InfiniBand, which runs at about 50 gigabytes per second per port. That's 18 times slower than NVLink.
Jenny: Oh wow. So that 18x gap basically dictates your entire parallelism strategy.
Alex: That's the single most important number in this whole space. Tensor parallelism, with its constant high-bandwidth chatter, has to stay within one NVLink node. Pipeline parallelism and context parallelism, which communicate less frequently, can span servers over InfiniBand.
Jenny: So can GPUs on different servers actually reach into each other's memory directly?
Alex: Yes — through RDMA, Remote Direct Memory Access, over InfiniBand. A GPU on server A can read from HBM on server B without either CPU touching the data at all. The path goes GPU memory, straight to the network card, across the InfiniBand fabric, into the remote GPU's memory. No CPU copies, no operating system involvement.
Jenny: That's exactly how prefill-decode disaggregation works, right? The prefill worker finishes, then ships the KV cache directly into the decode worker's GPU memory?
Alex: Spot on. And that KV cache can be tens of gigabytes for long prompts, so bypassing the CPU is critical.
Jenny: OK, so here's what I'm wondering — does any of this change with newer hardware?
Alex: Great question. The B200 with NVLink 5.0 doubles bandwidth to 1.8 terabytes per second per GPU. But the real game changer is NVL72 — 72 GPUs connected via NVLink switches with 130 terabytes per second of bisection bandwidth, all within a single rack.
Jenny: So instead of 8 GPUs in your NVLink domain, you get 72?
Alex: Right. You could potentially run tensor parallelism across 72 GPUs, which means a 70 billion parameter model might not need pipeline parallelism at all. But here's the thing — across racks, you're still on InfiniBand. The fundamental constraint hasn't disappeared, the boundary just moved from 8 GPUs to 72.
Jenny: So the design principle stays the same — keep the chatty communication inside the fast domain, push the less frequent stuff across the slower links. The fast domain just got a lot bigger.
Alex: Exactly. The hierarchy always wins. You just have to know where the bandwidth cliffs are and design around them.
