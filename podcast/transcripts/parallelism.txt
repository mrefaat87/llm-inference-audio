Alex: So I want to start with a question that sounds simple but actually opens up everything we're going to talk about today. Why can't we just run a 70 billion parameter model on one GPU and call it a day?

Jenny: I mean, the obvious answer is it doesn't fit, right? The weights alone blow past the HBM budget on a single card.

Alex: Right, but it's deeper than that. Even when a model technically fits, you might not want it on one GPU. Because latency matters. If a single H100 is doing all 80 layers sequentially for one token, you're bottlenecked by that one GPU's compute. So the question becomes — okay, we have to spread the work. But across what dimension?

Jenny: And there's more than one way to slice it.

Alex: There are five, actually. And this is where I think infra people have a real advantage, because every one of these is a sharding strategy you've seen before in some other form. So let's start with the easiest one. Data parallelism.

Jenny: Let me guess — this is the one that looks like an Auto Scaling group behind an ALB.

Alex: Literally exactly that. You take your model, you make N complete copies, one per GPU or per group of GPUs, and you put a load balancer in front. Request one goes to replica one, request two goes to replica two, done. No communication between replicas at inference time. They're fully independent.

Jenny: Okay so that's the cloud-native default. Why would I ever do anything else?

Alex: Two reasons. One, it requires the whole model to fit on your base replica. If your model is 400 billion parameters, no single H100 is holding that. And two — and this is the one people miss — data parallelism does absolutely nothing for per-request latency. You can have a thousand replicas, and one user's single request still takes exactly as long as it would on one replica.

Jenny: Right, because you're scaling out, not making any individual request faster.

Alex: Exactly. So when your SLA says "first token in 200 milliseconds," DP doesn't help you. That's where tensor parallelism comes in, and this is the one I want you to really internalize because it's the workhorse of inference.

Jenny: Okay, hit me.

Alex: Take a single weight matrix — say the query projection in attention, which on Llama 70B is 8192 by 8192. That's about 67 million parameters in one matrix. With 8-way tensor parallelism, you slice that matrix column-wise across 8 GPUs. Each GPU holds an 8192 by 1024 slice. Now when a token comes in, all 8 GPUs compute their slice of the matrix multiply at the same time, in parallel.

Jenny: So instead of one GPU grinding through the whole multiply, eight GPUs each do an eighth of it simultaneously.

Alex: Right. And then they have to combine results. Each GPU has a partial answer, and you need the full answer before you can move to the next layer. So they do an all-reduce — every GPU shares its partial, every GPU walks away with the sum. Think of it as a distributed sum where everyone ends up with the same final value.

Jenny: Hang on. That sounds like a ton of synchronization. How often does that all-reduce happen?

Alex: This is the part that blows people's minds. Twice per layer. Once after the attention output projection, once after the FFN down-projection. Llama 70B has 80 layers. That's 160 all-reduces per single forward pass. Per token.

Jenny: A hundred and sixty. Per token. That's... that's a lot of collective operations.

Alex: Which is why TP only works inside a single NVLink-connected node. NVLink is 900 gigabytes per second between GPUs in the same box. The all-reduce takes microseconds. But if you tried to do those 160 all-reduces over InfiniBand at 50 gigabytes per second between nodes...

Jenny: The communication would dominate everything.

Alex: It would erase the entire benefit. So the rule is: TP stays inside one 8-GPU node. Period. NVLink is non-negotiable for tensor parallelism.

Jenny: Okay, that makes sense. So tensor parallelism is for latency — eight GPUs working on the same token at the same time, roughly 8x faster forward pass. What about pipeline parallelism? Because the analogy I had in my head was an assembly line — GPU 1 does layers 1 through 24, hands off to GPU 2 for layers 25 through 48, and so on. That seems clean.

Alex: It is clean. And it's widely used in training. But for inference, it's basically a last resort, and I want to explain why because it's counterintuitive.

Jenny: Okay, why?

Alex: Two reasons. First — bubbles. At the start of a batch, GPU 2 can't do anything until GPU 1 finishes. At the end, GPU 1 is sitting idle while the rest of the pipeline drains. In training, your batch sizes are in the thousands, so those idle periods are a tiny fraction of overall compute. In inference, your batch is sometimes one request. So the bubble can eat 30 to 50 percent of your step time.

Jenny: Oh, that's brutal. So you're paying for 4 GPUs and three of them are sitting idle most of the time.

Alex: Right. But here's the second reason, and it's the one that really kills it. Pipeline parallelism does not reduce per-token latency. The token still has to flow through every stage sequentially. If anything, it adds latency because you have inter-GPU transfers between stages. Compare that to TP, where all 8 GPUs are working on the same token simultaneously. TP actually makes one token faster. PP just spreads the model out without speeding anything up.

Jenny: Wait. So why does anyone use it at all?

Alex: When the model is too big to fit even on a fully NVLinked 8-GPU node. Then you have no choice — you have to span multiple nodes, and TP can't cross that boundary. So you do TP within each node and PP between nodes. You eat the bubble cost only at the inter-node boundary instead of paying it per layer.

Jenny: Got it. So for the Llama 405B case, you'd do TP8 within each box, and then PP2 across two boxes.

Alex: Exactly. That notation, TP8 by PP2, is something you'll see all over inference configs. Now, there's a whole different parallelism strategy that only applies if your model is a Mixture of Experts.

Jenny: Expert parallelism.

Alex: Right. So in an MoE model, the FFN layer isn't one big network — it's a bunch of smaller "expert" networks, and a router picks 2 or so for each token. So you distribute different experts to different GPUs. Expert 1 and 2 live on GPU 0, experts 3 and 4 on GPU 1, and so on.

Jenny: Okay so this is sharding by feature rather than by request or by weight slice. But that means when a token needs expert 5, it has to physically travel to whichever GPU holds expert 5.

Alex: And every other token is doing the same thing in parallel, going to whichever expert it was routed to. That's an all-to-all communication pattern. Every GPU is sending different data to every other GPU at the same time. It's the most expensive collective in distributed ML, because the pattern is unpredictable — you can't compress it, you can't batch it neatly.

Jenny: And I'm guessing the routing isn't uniform.

Alex: This is the operational nightmare. If the router consistently sends 30% of tokens to expert 3, GPU 3 is on fire while GPU 7 is sitting idle. It's a hot-shard problem, exactly like a hot partition in DynamoDB. Load imbalance is the production challenge with EP.

Jenny: That's such a familiar problem. Okay last one — context parallelism. This is the long-context one?

Alex: Right. When someone wants to feed in a 500,000 token document, the sequence itself is the bottleneck. You split the sequence across GPUs — GPU 1 owns tokens 1 to 25k, GPU 2 owns 25k to 50k, and so on. The challenge is attention, because attention requires every token to see every other token's K and V vectors.

Jenny: So GPU 1 needs to see the K and V from tokens that live on GPU 4.

Alex: Right. And the elegant solution is called ring attention. You arrange the GPUs in a ring. Each one starts with its own Q, K, and V chunk. Then you rotate the K/V around the ring step by step. At each step, every GPU computes attention against whatever K/V it's currently holding, accumulates a partial result, and simultaneously the next K/V chunk is already being shipped to it.

Jenny: Oh, so the transfer overlaps with compute. You're never stalled waiting for data.

Alex: Exactly. After N-1 rotations, every GPU has seen every K/V chunk and has the full attention output for its slice of tokens. The communication is effectively free because it's hidden behind the math.

Jenny: That's beautiful. So in production you're combining all of these.

Alex: All the time. The most common combo is TP within a node for latency, plus DP across nodes for throughput. If you're running MoE, you mix in EP for the expert layers while keeping TP for attention. If you're doing million-token contexts, you add CP across nodes. The right combination falls out of the model architecture and your SLA.

Jenny: Match the parallelism to the structure of the layer. Dense layers want TP because every token touches every weight. Sparse expert layers want EP because each token only touches a couple experts.

Alex: That's the whole rule in one sentence.

Jenny: So where does this take us next? Because we've now got the model spread across a bunch of GPUs cooperating on every token. What's the next layer of the puzzle?

Alex: The next question is — okay, you've got this beautiful parallel topology, but you're still serving multiple requests. How do you actually pack those requests through the system efficiently? Because if you naively run one request at a time, your GPUs are massively underutilized. That's where batching and scheduling come in, and specifically continuous batching, which completely changed inference economics.

Jenny: So we go from "how do we split the model" to "how do we pack requests through the model we just split."

Alex: Right. And then after that, we get into KV cache management, because once you're batching, the KV cache becomes the dominant memory consumer and starts driving every other decision in the system.

Jenny: Okay, that's a thread I want to pull on. Until next time.

Alex: See you then.
