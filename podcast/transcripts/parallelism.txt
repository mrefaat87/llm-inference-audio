Alex: So Jenny, here's a question for you. You've got a service that's too big to fit on a single EC2 instance. What do you do?

Jenny: I mean, that's day one distributed systems. You either shard it across multiple instances, or you put multiple copies behind a load balancer, or you break it into stages in a pipeline. Depends on the workload.

Alex: Right. And that's literally the entire taxonomy of parallelism strategies for serving large language models. You just named three of the five. The interesting part isn't what the strategies are — it's why you'd pick one over another, and why the answer is different for inference than it is for training.

Jenny: Okay, so let's start with the easy one. Data parallelism — that's just the load balancer approach, right? N copies of the model, each handling different requests.

Alex: Exactly. You take the full model, replicate it onto four GPUs, and put a load balancer in front. GPU zero gets requests one and five, GPU one gets two and six, and so on. Zero communication between them. Each replica is completely independent.

Jenny: That's literally just an Auto Scaling group behind an ALB. I could set that up in my sleep.

Alex: And that's the beauty of it. For models that fit on a single GPU — your 7B, your 13B parameter models — data parallelism is the move. Maximum simplicity, horizontal scaling, you already know how to operate it. But here's the thing — what happens when your model is 70 billion parameters and it physically cannot fit on one GPU?

Jenny: Then I need to split the model itself across GPUs. So that's where sharding comes in — tensor parallelism?

Alex: Right. And this is where it gets interesting because there are two fundamentally different ways to split a model across GPUs, and they have completely different performance characteristics. Let me start with tensor parallelism because it's the one that actually matters for inference. Think about a single weight matrix — say the query projection in an attention layer. For LLaMA 70B, that's an 8,192 by 8,192 matrix. With 8-way tensor parallelism, you slice that matrix into eight vertical strips. Each GPU holds one strip — 8,192 by 1,024.

Jenny: So every GPU has a piece of every layer. It's like sharding a database by column rather than by row.

Alex: That's a great way to think about it. And here's the key — when a token comes in, all eight GPUs compute their slice of the matrix multiply simultaneously. GPU zero multiplies the input by its strip, GPU one by its strip, all at the same time. Each one produces a partial result. Then you need to combine those partials.

Jenny: That's the all-reduce operation?

Alex: Exactly. All-reduce means every GPU sends its partial result to every other GPU, and they all end up with the same combined sum. Think of it as a synchronized merge step — everyone shares their partial answer, everyone gets the full answer.

Jenny: Okay, but that communication has to happen at every single layer, right? How expensive is that?

Alex: This is where the numbers get really important. For LLaMA 70B with 80 layers, you need two all-reduces per layer — one after the attention output projection and one after the feed-forward network. That's 160 all-reduces per forward pass for a single token.

Jenny: A hundred and sixty! That sounds like it would completely dominate your latency.

Alex: It would — if you were doing it over the network. Over InfiniBand at 50 gigabytes per second, each all-reduce takes about 0.3 microseconds. Multiply by 160 and you're at 48 microseconds of communication overhead per token. Doesn't sound like much, but when your decode step is only 20 milliseconds, that's real overhead that starts eating into your SLA. Now, over NVLink at 900 gigabytes per second — each all-reduce takes about 0.02 microseconds. Total overhead: about 3 microseconds. Completely negligible.

Jenny: So that's why tensor parallelism only works within a single node. You need that NVLink backplane. It's like — you wouldn't shard a database across availability zones if every query required a synchronous cross-shard join.

Alex: That is exactly the right analogy. The communication pattern is too frequent and too latency-sensitive to tolerate network hops. NVLink is like a dedicated backplane inside a placement group — it's a fundamentally different class of interconnect. And the payoff is massive: 8-way tensor parallelism means all eight GPUs work on every token together. Your forward pass runs roughly eight times faster. TTFT drops by 8x. Time between tokens drops by 8x. This is the primary tool for hitting low-latency SLAs.

Jenny: Okay, so if tensor parallelism is so good, why does pipeline parallelism even exist?

Alex: Great question. Pipeline parallelism splits the model by layers instead of within layers. GPU one holds layers 1 through 24, GPU two holds 25 through 48, and so on. A token flows through sequentially — GPU one processes it, passes the activations to GPU two, which passes to GPU three.

Jenny: That's a microservices pipeline. Service A processes the request, hands it to service B, which hands it to service C.

Alex: Exactly. And it has the same fundamental problem that microservice pipelines have — what's every downstream service doing while the first service is processing?

Jenny: Sitting idle. Waiting for input. Oh — those are the pipeline bubbles.

Alex: Right. With 4-way pipeline parallelism processing a single request, each GPU is idle 75 percent of the time. Three out of four time slots are just wasted. In training, you can hide this because you have enormous batch sizes — thousands of micro-batches flowing through the pipeline, so the bubbles at the start and end are a tiny fraction of total compute. But at inference, especially with small batches or single requests, those bubbles can eat 30 to 50 percent of your step time.

Jenny: And it doesn't even help with latency, does it? The token still has to travel through every stage sequentially.

Alex: Exactly. A single token sees the same total compute time — maybe even slightly worse because of the hand-off overhead between stages. Compare that to tensor parallelism where all eight GPUs work on the same token at the same time. Pipeline parallelism is widely used in training, but for inference it's basically a last resort — only when your model is so large it can't fit on even a full 8-GPU NVLink-connected node.

Jenny: Got it. So TP is the go-to for inference. What about MoE models — those have a different structure, right?

Alex: They do, and they need their own strategy. Expert parallelism. In a Mixture of Experts model, you have maybe 256 expert FFN sub-networks, but each token only activates two of them. You distribute different experts across different GPUs. The challenge is that when the router picks experts for a token, that token needs to physically travel to whichever GPU holds its assigned expert.

Jenny: So that's an all-to-all communication — every GPU potentially sending tokens to every other GPU.

Alex: Right, and all-to-all is the most expensive collective operation in distributed ML because the communication pattern is unpredictable. With all-reduce, every GPU sends the same data. With all-to-all, it depends entirely on which experts the router selects. And here's the operational nightmare — popular experts become hot GPUs. If the router consistently sends 30 percent of tokens to expert three, that GPU is overloaded while other GPUs sit cold.

Jenny: That's a hot partition problem. Same thing happens with database sharding when one shard key is way more popular than the others.

Alex: Exactly the same problem, exactly the same headache. Load imbalance in expert parallelism is a real production challenge.

Jenny: Okay, so we've covered data, tensor, pipeline, and expert parallelism. You said there were five?

Alex: Context parallelism — and this one is fascinating. It's for when you have extremely long sequences. 128K tokens, 512K, even a million. The sequence itself is too long to fit in one GPU's memory, so you split it across GPUs. Each GPU holds a contiguous chunk of the sequence.

Jenny: But wait — attention needs every token to see every other token. If you split the sequence across GPUs, how does that work?

Alex: Ring attention. Picture four GPUs arranged in a ring. Each one holds its chunk of Q, K, and V vectors. The Q vectors stay put — they never move. But the K and V chunks rotate around the ring. In step one, each GPU computes attention between its local Q and whatever K/V it currently holds. Then all GPUs simultaneously pass their K/V to the next GPU in the ring.

Jenny: So after three rotations — N minus one steps — every GPU has seen every K/V chunk. And while it's computing attention with the current chunk, the next chunk is already in transit.

Alex: Exactly. The transfer is overlapped with computation, so the communication overhead is minimal. It's an elegant solution. And this is different from sequence parallelism, which only splits non-attention parts of the layer and requires an all-gather to reconstruct the full sequence before attention. Context parallelism splits everything, including attention, which lets it scale to much longer contexts.

Jenny: So in production, you'd actually combine these strategies?

Alex: Always. The standard recipe is tensor parallelism within a node — 8-way TP on an 8-GPU server using NVLink. Then data parallelism across nodes for throughput — spin up N replicas. If you're serving MoE models, you add expert parallelism for the FFN layers while keeping tensor parallelism for the attention layers. And if you're handling very long contexts, you layer on context parallelism across nodes using ring attention over InfiniBand.

Jenny: It's composable. Each strategy operates on a different dimension, so they don't conflict.

Alex: Exactly right. And knowing which combination to deploy for a given model size, sequence length, and latency SLA — that's the judgment call that separates infra leaders from infra operators.

Jenny: So looking ahead — we've talked about how to spread the model across GPUs. But all of this assumes the GPUs have enough memory in the first place. Next time we should dig into what's actually consuming that memory, especially the KV cache, and why memory management becomes the bottleneck even when you've parallelized everything perfectly.

Alex: Right. Tensor parallelism gives you speed, but the KV cache is what determines how many concurrent requests you can actually serve. That's where PagedAttention comes in — and if you think of the KV cache as a memory allocator, the analogy to virtual memory paging is going to blow your mind.
