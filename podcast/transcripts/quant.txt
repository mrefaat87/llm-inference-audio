Alex: So Jenny, let me ask you something. You've managed capacity pools at AWS — what's the first thing you check when someone says "this workload doesn't fit on our hardware"?
Jenny: Memory. Always memory. Before CPU, before network — can the thing even load into the box?
Alex: Exactly. And that's the entire reason quantization exists in LLM inference. A 70 billion parameter model in its native FP16 precision is 140 gigabytes. That doesn't fit on a single H100 with 80 gigs of HBM. But if you compress those weights down to 4-bit integers, suddenly it's 35 gigs. Same model, fits on one GPU.
Jenny: Okay, so it's lossy compression. Like downsampling images for a CDN — you trade fidelity for throughput and deliverability.
Alex: That analogy is almost perfect, but I want to sharpen it. Because in quantization, there are actually two fundamentally different strategies, and they have very different performance profiles. The first is weight-only quantization — you compress the weights for storage and memory bandwidth, but when you actually do the math, you decompress back to full precision first.
Jenny: Wait, so you're loading compressed data off the wire but then inflating it before processing? That's like gzip on an HTTP response — you save bandwidth but the CPU still works on the full payload.
Alex: That's a great analogy, actually. And here's why that still helps enormously: in LLM inference, especially during the decode phase when you're generating one token at a time, the bottleneck isn't compute — it's memory bandwidth. You're loading billions of weights from HBM for every single token. If you load 4-bit weights instead of 16-bit weights, you're moving four times less data across that memory bus per step.
Jenny: So the GEMM — the actual matrix multiply — still runs at FP16 speed, but you're feeding it four times faster because you shrank what's sitting in memory.
Alex: Exactly. And I should mention — GEMM, General Matrix Multiply, is literally the single most important operation in neural network inference. Every attention projection, every feed-forward layer, it's all GEMMs. So anything that makes GEMMs go faster or makes them easier to feed with data is a massive win.
Jenny: Okay, so that's weight-only. You said there's a second approach?
Alex: Weight plus activation quantization. This is where things get really interesting. Instead of decompressing before the multiply, you keep everything in low precision — the weights AND the intermediate values flowing through the network, the activations. The matrix multiply itself runs at reduced precision end to end.
Jenny: So now you're not just saving bandwidth, you're getting actual compute speedup?
Alex: Right. On an H100, FP8 GEMMs run at roughly two times the throughput of FP16 GEMMs on the Tensor Cores. You're doing twice as many multiplies per second. That's not a bandwidth trick — that's raw compute improvement.
Jenny: Okay, but I have to push back here. If weight-only quantization already solves the memory problem and the bandwidth bottleneck, why bother with the harder approach of quantizing activations too?
Alex: Because it depends on your regime. During decode — single token generation — you're absolutely memory bandwidth bound, and weight-only is great. But during prefill, when you're processing a long prompt, you're actually compute bound. You're doing massive matrix multiplies with large batch dimensions. That's where FP8's two-times compute speedup is a game-changer.
Jenny: Oh, that makes sense. Prefill is your bursty workload, decode is your steady-state throughput. Different bottlenecks, different optimization levers.
Alex: Exactly. Now let me walk through the specific methods because each one solves a different problem. Let's start with GPTQ. This was one of the first practical INT4 methods. It goes layer by layer through the model and solves an optimization problem: find the 4-bit weights that minimize the change in that layer's output.
Jenny: Minimize change compared to what?
Alex: Compared to the original FP16 output on a calibration dataset. You run a few hundred samples through each layer, measure what the outputs look like with full precision weights, then find the INT4 weights that produce the most similar outputs.
Jenny: So it's using real data to guide the rounding decisions rather than just naively rounding each weight to the nearest integer.
Alex: Right, and it uses something called the Hessian matrix to figure out which weights matter most. Think of it this way — the Hessian tells you the sensitivity gradient. Some weights, if you perturb them a little, the output barely changes. Other weights, even a tiny rounding error cascades through and blows up the output. GPTQ identifies the sensitive ones and compensates them first.
Jenny: That's like capacity planning where some instance types are fungible and others are critical path. You don't treat them all the same when you're making allocation decisions.
Alex: Good analogy. Now, AWQ takes a different approach. Instead of looking at the weights themselves, it looks at the activations — the actual data flowing through the network. Its insight is that certain weight channels consistently see large activation values. Those channels carry more signal.
Jenny: So instead of asking "which weights are sensitive" like GPTQ does, AWQ asks "which weights are being used the hardest by real data"?
Alex: Exactly. And then it does something clever. It scales those important channels up before quantizing — spreads their values out more within the INT4 range so they get more effective precision. Then it folds the inverse scaling into an adjacent operation at zero runtime cost.
Jenny: Hang on, that's basically the same trick as SmoothQuant, right? Moving difficulty from one place to another?
Alex: You're jumping ahead, but yes, it's a related idea. The difference is that AWQ moves difficulty within the weights to protect important channels, while SmoothQuant moves difficulty between weights and activations. Let me get to that. But first — both GPTQ and AWQ are weight-only methods. They need a specialized kernel called Marlin to actually be fast at inference. The weights are stored in INT4, decompressed to FP16 for the GEMM.
Jenny: Right, the gzip analogy. Now what about FP8? You mentioned that's the production standard on H100.
Alex: FP8 is kind of elegant in its simplicity. It keeps the floating-point format — sign bit, exponent, mantissa — just in eight bits instead of sixteen. And the key advantage over integer formats is that exponent.
Jenny: Why does the exponent matter so much?
Alex: Because activations have outliers. The values flowing through a transformer aren't nicely distributed. You might have most values between negative one and one, but then a few channels spike to 500. With INT8, you'd have to set your scale to cover that 500, and now all your small values near zero get crushed into the same integer. You lose all the fine-grained information.
Jenny: Oh, that's like dynamic range problems in monitoring. If your metric scale goes to a million, you can't see the difference between 0.1 and 0.5 anymore.
Alex: Perfect analogy. FP8's exponent bits solve this automatically. It can represent 0.001 and 500 in the same tensor without precision collapse. That's why FP8 often doesn't even need a calibration dataset — the format just handles real-world distributions naturally.
Jenny: So FP8 gives you the compute speedup of quantizing activations without the headache of dealing with outliers. No wonder it's becoming the default.
Alex: Right. And the quality loss versus FP16 is often undetectable on standard benchmarks. It's converging on being the default inference format for H100 serving.
Jenny: What about A100s though? Not everyone has H100s.
Alex: That's where SmoothQuant comes in. A100s have INT8 Tensor Cores that give you about a 1.5x compute speedup. But you can't just naively quantize activations to INT8 because of those outliers we just talked about. SmoothQuant's trick is mathematical judo. It multiplies the activation channels by a scaling factor that shrinks the outlier channels, and divides the corresponding weight channels by the same factor. The product is mathematically identical, but now both distributions are smooth enough for INT8.
Jenny: So it's redistributing the quantization difficulty from activations — which are hard — to weights, which are easier because they're more regular.
Alex: Exactly. The scaling factor is computed once offline from a calibration pass, then it's baked in.
Jenny: Okay, I have to ask about GGUF because I keep seeing it everywhere in the local LLM community.
Alex: GGUF is a completely different animal. It's a file format from the llama.cpp project, optimized for CPU inference. The cool thing is it supports mixed precision within a single model. Sensitive layers — attention, early and late layers — get higher precision, like 6 or 8 bits. The big feed-forward layers in the middle get compressed more aggressively, down to 2 or 4 bits.
Jenny: That's intelligent bin packing. You're not applying the same compression ratio uniformly — you're allocating your precision budget where it matters most.
Alex: Exactly. And it uses CPU SIMD instructions — AVX-512 on Intel, NEON on ARM — for fast dequantization. It's how people run 70B models on MacBooks. But it's not used in GPU production serving. If you have GPUs, AWQ or FP8 are strictly better.
Jenny: One thing I keep hearing about — calibration data. How sensitive are these methods to what data you calibrate on? Like if I calibrate on English text but serve multilingual traffic, am I in trouble?
Alex: Moderately. You can see two to five perplexity points of degradation on low-resource languages, especially morphologically complex ones like Arabic or Korean. The fix is straightforward though — mix ten to twenty percent of your target language samples into the calibration set and you recover most of the quality without hurting English.
Jenny: And how much calibration data are we talking about?
Alex: Surprisingly little. AWQ only needs 32 to 128 samples since it's just identifying which channels have large activations. GPTQ needs a bit more, 128 to 512 samples, because it's computing full Hessians. But quality plateaus around 100 samples — the distribution matters way more than quantity. AWQ calibration on a 70B model takes maybe 10 to 30 minutes on a single GPU. GPTQ is one to four hours.
Jenny: So the decision tree for practitioners is basically — H100? Use FP8. A100? SmoothQuant INT8. Need to squeeze a model onto fewer GPUs? AWQ INT4. Running on a laptop? GGUF.
Alex: That's a solid heuristic. And here's where this connects forward. Next time we're going to talk about custom kernels — FlashAttention, Marlin, the fused operations that actually make all of this fast in practice. Because quantization gives you smaller numbers, but you need specialized GPU kernels to actually capitalize on that at the hardware level.
Jenny: Right, like having a better compression algorithm is useless if your decompression pipeline can't keep up. The kernel is the execution engine.
Alex: Exactly. And then beyond kernels, we'll get into how quantization interacts with batching and the KV cache — because the memory you save with INT4 weights is memory you can now allocate to serving more concurrent requests. The optimization techniques aren't independent. They compound.
Jenny: That's the part I'm most excited about. It's the same principle as right-sizing instances — the savings from one optimization create headroom for the next one. Can't wait to dig into that.
