Jenny: So static batching is like a charter bus. You wait until you have a full batch, everyone gets on, and nobody gets off until the longest request finishes. Jenny: That's the city bus with stops. As soon as a request finishes generating, you evict it and slide a new request into that slot. So your GPU never stalls waiting on the slowest request in the batch.

Alex: That's a perfect segue. Explain the KV cache to me like I've never heard of it. What is it, and why does it exist?

Jenny: Okay. So when you're generating tokens one at a time, each new token needs to attend to every previous token. Without caching, you'd recompute the key and value vectors for the entire sequence at every single step. That's like re-querying your database from scratch on every API call instead of caching the results. The KV cache stores those computed key-value pairs so you only compute them once and reuse them for every subsequent token.

Alex: Good. Now, what's the memory footprint look like? Why is this such a big deal operationally?

Jenny: Because it scales with sequence length times batch size times the model dimensions. So if you double your context window, you double your KV cache memory. If you double your batch size, you double it again. For a big model with long contexts and a decent batch size, the KV cache can eat more memory than the model weights themselves.

Alex: And that's exactly why techniques like PagedAttention exist — treating KV cache memory like virtual memory pages instead of one big contiguous allocation. But let's move on. FlashAttention. What problem does it solve, and here's the key part — it doesn't change the math of attention at all. So why is it faster?

Jenny: This one took me a minute to really get. FlashAttention is a memory hierarchy optimization, not an algorithmic one. The math is identical. The speedup comes from how it moves data between GPU memory levels. Standard attention writes those huge intermediate attention matrices to HBM — the GPU's main memory — and then reads them back. FlashAttention restructures the computation into tiles that fit in SRAM, the fast on-chip memory, so you avoid those round trips to HBM.

Alex: Why does that matter so much? SRAM versus HBM, how big is that gap?

Jenny: It's enormous. SRAM bandwidth is like an order of magnitude faster than HBM. So even though you're doing the same number of floating point operations, you're spending way less time waiting on memory transfers. It's like the difference between reading from an in-memory cache versus making a network call to a remote database. Same data, wildly different latency.

Alex: And the effect on sequence length?

Jenny: Standard attention is quadratic in sequence length for memory — you're materializing that full N-by-N attention matrix. FlashAttention brings memory usage down to linear because you never materialize the whole matrix at once. You process it in blocks. That's what unlocks those really long context windows in practice.

Alex: Great. Now let's talk about quantization. You've got a model with, say, seven billion parameters stored in sixteen-bit floating point. Walk me through what quantization does and what the tradeoff is.

Jenny: So quantization reduces the precision of the model weights — and sometimes activations — from higher-precision formats like FP16 down to INT8 or INT4 or even lower. Each parameter takes fewer bits, so the model is smaller in memory and faster to load and move around. The tradeoff is precision. You're essentially compressing the weights. Like going from a high-resolution image to a JPEG — you lose some fidelity, but for many use cases, the output quality is nearly indistinguishable.

Alex: Why does smaller memory footprint translate to faster inference, not just smaller models? That's the part people sometimes miss.

Jenny: Because inference on these models is almost always memory-bandwidth bound, not compute bound. The GPU spends more time loading weights from memory than it does actually multiplying matrices. So if you cut the weight size in half with INT8 quantization, you can load them roughly twice as fast, which directly speeds up token generation. It's like — if your bottleneck is network throughput, compressing your payloads speeds up the whole pipeline even though decompression adds a tiny bit of compute.

Alex: Exactly. And that's specifically true during the decode phase, the token-by-token generation, which is the bandwidth-bound part. Why do we have multiple quantization methods?

Jenny: They differ in what they consider important when choosing how to round those weights. GPTQ looks at calibration data and minimizes the overall reconstruction error across the layer. AWQ — Activation-Aware Quantization — is more selective. It identifies which weight channels matter most based on activation magnitudes, and it protects those important channels by scaling them up before quantization. So AWQ tends to preserve quality better because it's smarter about which precision to sacrifice.

Alex: Like doing capacity-aware bin packing instead of uniform allocation.

Jenny: Yeah, exactly. You don't treat every weight equally. You protect the ones that carry the most signal.

Alex: Okay, last big one. Speculative decoding. This is probably the most counterintuitive optimization we've covered. Explain the core idea.

Jenny: Alright. So the bottleneck with autoregressive generation is that you produce one token at a time, serially. Each token depends on the one before it. Speculative decoding says: what if we use a much smaller, faster model — the draft model — to quickly guess the next, say, five tokens? Then we feed all five of those guesses into the big model in one forward pass, and the big model verifies them in parallel. If three of the five guesses are correct, you just generated three tokens in the time it would have taken to generate one.

Alex: Why can the big model verify multiple tokens in parallel when it can't generate them in parallel?

Jenny: Because verification is fundamentally different from generation. When you're generating, you don't know the next token, so you have to go sequentially. But when you're verifying, you already have candidate tokens. You can feed the whole candidate sequence in at once — just like the prefill phase processes a whole prompt at once — and check whether the big model agrees with each prediction. It's the classic parallel verification trick. Generating a solution is hard and sequential, but checking a proposed solution can be done in parallel.

Alex: That's a great framing. And what determines whether this actually speeds things up in practice?

Jenny: The acceptance rate of the draft model's predictions. If the small model is usually right — say, seventy or eighty percent of the time — you're getting multiple tokens per forward pass of the big model consistently, and the overhead of running the draft model is small because it's tiny. But if the acceptance rate drops too low, you're burning compute on the draft model and then rejecting most of its guesses, so you might actually be slower than just running the big model normally.

Alex: And when does the draft model tend to be right?

Jenny: On predictable, formulaic text. Code boilerplate, common phrases, structured outputs. It's less useful when every token is a hard creative decision. Which makes sense — the easy tokens are where a small model can match a big model's behavior.
