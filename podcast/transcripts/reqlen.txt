Alex: Okay Jenny, I want you to think about something. You're running a fleet of EC2 instances, and you've got four completely different workload profiles hitting the same auto scaling group. One's a tiny API call that returns a short JSON blob. Another's a tiny API call that kicks off a ten-minute batch job. A third ingests a massive payload but returns a quick acknowledgment. And the fourth ingests a massive payload AND runs a long batch job. Would you ever serve all four with the same instance type and the same scaling policy?

Jenny: Absolutely not. That's like, day-one capacity planning. You'd be over-provisioning for the light stuff and under-provisioning for the heavy stuff. You'd split those into separate services or at least separate target groups.

Alex: Right. So here's what's wild about LLM inference — most serving systems today do exactly that mistake. They take all four of those workload profiles and shove them onto the same GPU, same scheduler, same everything. And the four profiles I'm talking about map to the combination of short or long input prompt, crossed with short or long output.

Jenny: Okay, but why does the length matter so much? A token is a token, right?

Alex: No, and this is the fundamental thing. Processing the input — what we call prefill — and generating the output — what we call decode — are bottlenecked by completely different hardware resources. They're not even the same type of work.

Jenny: Different how?

Alex: Prefill is compute-bound. You're taking all the input tokens and processing them in parallel through the model. It's pure math — matrix multiplications, attention computations, all happening simultaneously. The bottleneck is TFLOPS, how fast can your GPU do arithmetic. An H100 at 989 TFLOPS chews through prefill roughly three times faster than an A100 at 312 TFLOPS.

Jenny: Okay so prefill is CPU-bound, if I translate that to our world. You want the fastest cores you can get.

Alex: Exactly. Now decode is the opposite. Each decode step generates one token. And to generate that one token, you have to load the entire model's weights from GPU memory into the compute units. Every single step. The bottleneck isn't math speed — it's memory bandwidth. How fast can you move bytes from HBM to the compute cores.

Jenny: Oh, so it's like... the compute units are sitting there idle, waiting for data to arrive from memory?

Alex: Precisely. And this is why the H100 SXM version, with 3.35 terabytes per second of memory bandwidth, is meaningfully faster at decode than the H100 PCIe version at 2 terabytes per second — even though they have the same TFLOPS. For decode, extra TFLOPS beyond a certain point literally don't help. The math units are already done before the next batch of weights arrives.

Jenny: That's like the difference between a compute-optimized and a memory-optimized instance. You'd never run a Redis cache on a c5 and you'd never run a number-crunching job on an r5.

Alex: Perfect analogy. Now let's walk through what happens when you combine short and long on both sides. Start with the easy one — short prompt, short output. Think chatbot, quick Q&A, API calls that return a sentence or two.

Jenny: That sounds like the least problematic case?

Alex: It is, individually. Each request is cheap. But the problem is volume. You're getting thousands of these per second. And suddenly the bottleneck isn't the GPU math or the memory bandwidth — it's the scheduler overhead. Every request needs to be received, allocated into a batch, have its KV cache set up, get scheduled. At high enough request rates, the per-request overhead starts eating into your throughput.

Jenny: So it's like microservices with tiny payloads — the network and serialization overhead dominates the actual work.

Alex: Exactly. The strategy here is large dynamic batches with continuous batching as the foundation. And prefix caching helps a lot because tons of these short requests share the same system prompt — why recompute it every time?

Jenny: Okay, that makes sense. What about short prompt, long output? Like, I ask a simple question but the model writes me a five-page essay.

Alex: Now you've got a different beast. Prefill is cheap — short prompt, done in milliseconds. But decode runs for hundreds or thousands of steps. And here's the thing — every single decode step adds to the KV cache. The KV cache grows linearly with output length. So one long-running request can monopolize gigabytes of GPU memory for minutes.

Jenny: Oh, so it's a resource leak problem. The request grabs memory early and holds it forever.

Alex: Holds it until it's done generating. And you can't just kill it — the user's waiting for their response. So you need memory-aware admission control. You set a budget — "I have X gigabytes of HBM for KV cache, each active sequence is using Y and growing" — and when you're near capacity, you stop admitting new requests.

Jenny: That's literally a circuit breaker. You reject at the door instead of letting people in until the building collapses.

Alex: Right. And your other levers are reducing how much memory each token costs. KV cache quantization — storing the cache in INT8 instead of FP16, which doubles your capacity. Or architectures like GQA and MQA that share key-value heads across attention groups, shrinking the per-token footprint.

Jenny: Okay, now flip it. Long prompt, short output. Like, "here's a 50,000-token document, summarize it in a paragraph."

Alex: This is where time-to-first-token goes to hell. Processing 50,000 input tokens takes multiple seconds of prefill. And here's the nasty part — while that prefill is running, every other request that's in the middle of decoding is stalled. The GPU is occupied doing this massive parallel computation, and all those decode steps that need to happen for other users? They're waiting.

Jenny: Wait, that's head-of-line blocking. One big request in the queue delays everything behind it.

Alex: Exactly head-of-line blocking, yes. And the solution is something called chunked prefill. Instead of processing all 50,000 tokens in one shot, you break the prefill into chunks — maybe 512 or 1024 tokens at a time. Between each chunk, you let pending decode steps run. So the long prefill takes a bit longer overall, but it doesn't starve everyone else.

Jenny: That's like... time-slicing. You're preempting the big job to let the small jobs through. That's basic OS scheduling.

Alex: It is. It's literally the same insight that led from batch processing to time-sharing operating systems in the 1960s.

Jenny: Okay so now the worst case — long prompt AND long output. That's both problems at once?

Alex: Both problems, and they interact badly. Long prefill blocks decode for other requests. Long decode grows the KV cache massively. And you can't efficiently batch these monsters with short requests because the interference is severe — the short requests get terrible latency, and the long requests don't get enough memory headroom.

Jenny: So this is where you actually need to split the fleet, right? Like you said at the beginning — you wouldn't run these on the same instance type.

Alex: This is where disaggregation becomes essential. You split your serving fleet into two specialized pools. Prefill workers and decode workers. Prefill workers receive new requests, run the full prefill computation, and generate the KV cache. They're optimized for TFLOPS — they want the fastest compute possible. And they never run decode. Once prefill is done, they're free for the next request.

Jenny: And decode workers just do decode? They receive... what, the KV cache somehow?

Alex: Exactly. After prefill finishes, the KV cache — which can be gigabytes for long prompts — gets transferred over InfiniBand using RDMA directly to the decode worker's GPU memory. RDMA means remote direct memory access — the GPUs are reading and writing each other's memory without the CPU even being involved. The decode worker picks up right where prefill left off and generates tokens until the response is complete.

Jenny: So it's like a read-write replica split in a database. Writes go to one pool optimized for write throughput, reads go to another pool optimized for read latency. Each scales independently.

Alex: That's a great analogy. And the independent scaling part is crucial. If you're seeing a surge of long prompts — maybe someone's doing bulk document processing — you scale up prefill workers without touching the decode fleet. If decode is the bottleneck, you add decode workers. They're decoupled.

Jenny: Okay but hang on. You said the KV cache can be gigabytes. How fast can you actually transfer that? Because if the transfer itself takes forever, you haven't solved the TTFT problem, you've just moved the bottleneck.

Alex: You've found the emerging problem. Let me give you concrete numbers. LLaMA-3 70B with GQA uses about 320 kilobytes per token for KV cache. A 100,000-token prompt? That's about 31 gigabytes of KV cache.

Jenny: Thirty-one gigabytes?!

Alex: At InfiniBand 400 gigabits per second — which is roughly 50 gigabytes per second — that transfer takes about 625 milliseconds. Even at 800 gigabits, you're looking at 312 milliseconds. And that's before a single decode token is generated.

Jenny: So for long contexts, the network transfer is now the bottleneck, not the compute or the memory bandwidth. You've pushed the problem from the GPU to the network.

Alex: Exactly. And this is an active area of research. Mooncake uses RDMA with zero-copy to minimize the transfer overhead. NVIDIA's Dynamo framework includes a KV transfer scheduler that pipelines transfers with decode — so you're shipping chunks of the KV cache while earlier chunks are already being used for decode. And chunked prefill helps here too — you can start shipping completed KV chunks incrementally while the prefill worker is still processing later chunks.

Jenny: So you're overlapping the transfer with the compute, like how we do with streaming uploads. Don't wait for the whole thing to finish, start processing as it arrives.

Alex: Right. And I want to stress — disaggregation isn't theoretical. This is Anthropic's production serving architecture direction. The academic papers that formalize this are DistServe out of OSDI 2024 and Splitwise from ISCA 2024. NVIDIA's building it into Dynamo as their open-source inference framework.

Jenny: So if you're interviewing at an inference company and you can walk through disaggregation — including why the network transfer is the next bottleneck and what pipelining strategies exist — that's a strong signal.

Alex: Very strong signal. Because it shows you understand the full stack — the compute asymmetry, the memory management, and the networking layer that connects them.

Jenny: Alright, so zooming out — we've gone from "all requests are the same" to "there are four fundamentally different serving problems" to "maybe you need entirely separate fleets for different phases of the same request." Where does this lead next?

Alex: This leads straight into smart routing. Once you have disaggregated fleets, someone has to decide which prefill worker and which decode worker each request goes to. And that routing decision depends on predicting how expensive each request will be — which means output length prediction, load-aware routing, and cache-aware placement. It's the scheduling and routing layer that ties everything together.

Jenny: So we've built the hardware abstraction, and next we build the control plane on top of it.

Alex: Exactly. The infrastructure is the easy part. The intelligence that drives it — that's where it gets really interesting.
