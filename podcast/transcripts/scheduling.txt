Alex: So Jenny, you know how at AWS, the Network Load Balancer doesn't just blindly accept every TCP connection that comes in?

Jenny: Right, there's a connection limit. If a target group is saturated, new connections get rejected at the LB rather than queued into oblivion.

Alex: Exactly. Now imagine you're running an LLM inference service and a request comes in with a 10,000-token prompt asking for 500 tokens of output. Should you accept it?

Jenny: I mean... the obvious answer is yes? That's the job.

Alex: But here's the thing. You have an SLO — say, two seconds to first token, ten seconds total. You can actually do the math before accepting. Prefill throughput is maybe 5,000 tokens per second, so that prompt costs you two seconds just to ingest. Decode runs at 50 tokens per second, so 500 output tokens is another ten seconds. Plus whatever the queue wait is.

Jenny: So you're already over budget before you even start.

Alex: Right. And the Mooncake paper made this point really crisply — if you accept that request, you spend GPU cycles on it, you partially generate, and then you miss the SLO anyway. The user gets nothing useful, and you've burned compute that could've served someone you could actually finish in time.

Jenny: So you reject upfront. 503, Retry-After. That's literally admission control on an NLB.

Alex: That's literally admission control on an NLB. The twist is that "can I serve this?" isn't a static health check — it depends on the specific request. A 200-token prompt and a 10,000-token prompt have wildly different costs.

Jenny: Okay but — how do you know how many output tokens it's going to generate? That's the whole point of an LLM. The output length is the unknown.

Alex: That is the hard part. There's a whole subfield on output length prediction — small classifier models, prompt heuristics, sometimes you just bucket by request type. It's noisy. But even a rough estimate is better than nothing, because the alternative is admitting blind and discovering halfway through decode that you're toast.

Jenny: Got it. So this changes how you measure the system, doesn't it? Throughput alone is a lie.

Alex: Exactly the right instinct. The metric that matters is goodput — requests that meet SLO divided by requests attempted. You can have a system pumping a hundred requests per second of pure throughput, but if forty percent miss SLO, your real goodput is sixty.

Jenny: Which is the same trap as measuring an API by raw RPS instead of RPS-under-latency-budget.

Alex: Same trap. And once you optimize for goodput instead of throughput, a bunch of counterintuitive things become correct. Like — sometimes the right move is to *delay* a new request. Make its time-to-first-token worse on purpose.

Jenny: Wait, why? That sounds like you're hurting the new request.

Alex: You are. But if admitting it right now causes the in-flight requests to slow their per-token cadence — their TBT, time-between-tokens — you've just blown the SLO for everybody currently streaming. Better to make one request wait an extra 200 milliseconds than to cause ten in-flight users to start stuttering.

Jenny: Oh, that's the same logic as token bucket shaping. You sometimes hold a packet to protect the flow already in progress.

Alex: Same logic. Now — what happens when the system is genuinely overloaded and you have to evict somebody from GPU memory? Because KV cache is finite, right?

Jenny: Right, KV cache lives in HBM, you've got a fixed pool. Somebody's getting kicked out.

Alex: So you have a policy choice. vLLM's default is FCFS — last arrived gets evicted first. Simple, but really stupid in one specific case.

Jenny: Which is?

Alex: Imagine a request that's 99% done. It's been decoding for nine seconds, it's about to emit its last token. A new request shows up, memory pressure hits, FCFS says evict the new one. Fine. But flip it — what if the 99%-done one is the *last* arrived in some local window? You just threw away nine seconds of compute.

Jenny: Oof. So you want least-progress-first instead?

Alex: That's one option — evict whoever generated the fewest tokens, because you waste the least work. Another is lowest-priority-first, which matters in multi-tenant. Another, if you trust your output-length predictor, is longest-remaining-first — evict the request that frees the most KV memory per kick.

Jenny: And you'd pick between those based on whether you care more about fairness, compute efficiency, or memory pressure relief.

Alex: Exactly. None of them is universally right. SGLang actually went a step further — they predict future decode memory needs *before* admitting a request, so they don't end up in the admit-then-preempt cycle in the first place.

Jenny: That's like capacity reservation. Don't accept the workload unless you've already reserved the headroom for it.

Alex: Perfect analogy. TRT-LLM does something similar because their engines are compiled — they know exactly how much memory a given shape needs. vLLM V1 went the other direction: chunked prefill on by default, recompute-only preemption, no swap. They lean on doing prefill in small chunks so the scheduler has more decision points.

Jenny: Okay let's talk priority. In a multi-tenant world, not every request is equal. How do you actually do tiers without starving the bottom?

Alex: Weighted Fair Queuing. You assign weights — say Enterprise is 8, Paid-standard is 4, Free is 2, Anonymous is 1. Under overload, capacity gets divided proportionally. Anonymous still gets one-fifteenth of the system. Not zero.

Jenny: Which maps almost cleanly onto AWS capacity types. Reserved is your tier zero. On-Demand is the middle. Spot is best-effort, first to be reclaimed.

Alex: That's exactly the mental model. And within a tier, you still need a queue discipline. Mostly that's FIFO, sometimes a priority queue sorted by predicted output length — shortest-job-first — or by deadline.

Jenny: FIFO has the head-of-line blocking problem though, right? One huge prompt at the front stalls the whole tier.

Alex: Huge problem. A 50K-token prompt at the head of FIFO just sits there hogging prefill for ten seconds while everyone behind it waits. That's why production stacks layer it: WFQ across classes, priority queue within each class, then a token-budget admission gate before you even enter the engine's batch.

Jenny: So three layers of scheduling decisions before the GPU sees the request.

Alex: Three layers, and that's just within one replica. Then there's cluster-level routing, which has its own twist. You don't just want to pick the least-loaded replica.

Jenny: Why not? That's textbook load balancing.

Alex: Because of KV cache. If a replica already has the prefix of this conversation warm in HBM — the system prompt, the prior turns — sending the request to a "less loaded" replica means recomputing all of that from scratch. You'd torch your prefix-cache hit rate.

Jenny: Oh — that's session affinity. But the sticky key isn't the user, it's the prompt prefix.

Alex: Exactly. Hash of the prefix tokens, or a radix-tree match score. Same idea applies to LoRA adapters — you want the request to land on a replica that already has the right adapter loaded, otherwise every request triggers a swap from CPU or SSD.

Jenny: And in multi-tenant LoRA, that swap cost would be... catastrophic.

Alex: Hour-long P99s. Multi-tenant LoRA without LoRA-aware routing is basically unusable. Production routers — SGLang's sgl-router, Dynamo, vLLM's production stack — fold both into one decision: pick the replica that maximizes joint prefix-cache plus adapter-cache hit score, with a spill threshold so a hot prefix doesn't pin everyone to one replica.

Jenny: And then there's the cold start problem, which is where this gets really fun for an autoscaling person.

Alex: Right, this is the part that hits home for you. When the autoscaler decides to add a replica, you're looking at four stages. GPU procurement — could be tens of seconds, could be minutes. Container image pull — these images are ten-plus gigs because of CUDA. Model weight load — a 70B model is hundreds of gigs into HBM, a 405B is minutes. And then engine startup — CUDA graph capture, kernel autotune, sometimes a TRT-LLM compile.

Jenny: So end-to-end, a cold replica is one to five minutes. Which means by the time queue depth tells you "we need capacity," you're already in violation.

Alex: You have to trigger the autoscaler on a leading indicator, not on queue saturation. And the new replica has to be drained from the routing pool — invisible to traffic — until it passes a warmup probe. Otherwise the first real user request pays the compile latency and trips your SLO.

Jenny: Replica readiness as a routing dimension. Same as ELB pre-warming, but for GPUs.

Alex: Exactly the same shape. Okay — so where does this all lead?

Jenny: Where *does* it lead? Because it feels like we've been treating prefill and decode as if they live on the same box.

Alex: That's the perfect setup for what's next. Prefill is compute-bound, decode is memory-bandwidth-bound. They have completely different hardware appetites. Running them on the same GPU is like running your write-heavy OLTP and your analytical reads on the same database instance.

Jenny: So the next step is splitting them. Disaggregation.

Alex: Disaggregation. Separate pools, separate scaling, KV cache transferred over the network between them. It changes the routing problem, the admission problem, and the cold-start problem all at once — because now you have two replica fleets to keep warm, not one.

Jenny: And presumably the goodput math changes too, because the bottleneck shifts depending on workload mix.

Alex: It changes everything. That's the next episode. The short version — once you stop pretending one GPU should do both jobs, a lot of the contention we just talked about gets cleaner. But you trade it for a whole new class of problem: KV cache transfer cost.

Jenny: Looking forward to it. Scheduling within a box was already three layers deep — I can't wait to see what splitting the box does.

Alex: Buckle up.
