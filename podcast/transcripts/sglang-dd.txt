Alex: So if you've been running vLLM in production, you already know the magic trick — PagedAttention treats the KV cache like virtual memory, continuous batching keeps the GPU saturated, and prefix caching gives you back compute when prompts share a head. That's the baseline. The question I want to start with today is: what happens when you take that baseline and ask, what if the cache wasn't a per-request optimization, but a first-class data structure shared across every call the engine has ever seen, with a router that knows about it, a scheduler that doesn't get in its way, and a frontend language that tells the runtime which calls are siblings?

Jenny: Okay, so you're saying the pitch isn't "we're faster than vLLM" — it's "we redesigned around the cache being the protagonist."

Alex: That's exactly it. And the system is SGLang. The CMU lecture from Ying Sheng — who's one of the leads — describes it as a fast serving framework for LLMs and vision-language models. The README calls it an open-source inference engine. But the LMSYS launch blog frames it differently: SGLang is a domain-specific language embedded in Python with primitives that handle intra-program parallelism and batching. And both descriptions are true, because the thing has a frontend — the SGLang DSL — and a backend — the runtime — and they were designed together.

Jenny: Wait, hold on. A DSL? That sounds like a step backward. The whole reason the OpenAI API won is that you just send strings. Nobody wants to write programs in a custom language to call an LLM.

Alex: Right, and that's the first thing to clear up — you don't have to. The runtime ships an OpenAI-compatible API. The CMU lecture's architecture diagram literally shows three client entry points: a native generation API, an OpenAI-compatible API, and the structured language frontend. You can ignore the DSL entirely and SGLang still does everything we're going to talk about today.

Jenny: Okay, so why does the DSL exist at all then?

Alex: Because real LLM applications aren't single self-contained prompts anymore. The lecture characterizes the dominant pattern as a complex pipeline with multiple LLM calls — chained calls where a follow-up reuses the previous answer, parallel calls where one question fans out to several answers and then a select step picks one. The lecture lists three concrete shapes: multi-turn chat where the chat history grows and is reusable across turns, few-shot learning where the few-shot examples are shared across many prompts, and tree search with LLM agents where every node of the search tree shares an ancestor's history with its siblings.

Jenny: Right, and in all three of those, the structure is invisible to the runtime if you just send strings.

Alex: Exactly. The runtime sees a stream of opaque token sequences. It might notice they share a prefix if you've turned on prefix caching, but it doesn't know that this batch of eight prompts is eight branches of the same Tree-of-Thought rollout, or that those four parallel calls are siblings under a shared system prompt. The DSL exposes that. The primitives, per the launch blog: fork creates multiple parallel copies of a prompt, gen invokes a generation and stores the result in a variable, choices imposes constraints on the generation, run executes a function with arguments. So when you write fork four-ways and then gen on each fork, the runtime knows — structurally, not by string matching — that those four calls share an ancestor.

Jenny: Okay, so the DSL is basically a way to send the runtime a query plan instead of a query.

Alex: That's a great way to put it. And it has two execution modes — interpreter mode, which is eager, and compiler mode, which traces the program into a dataflow graph and enables code movement, instruction selection, and auto-tuning. That's straight from the launch blog. So you can think of it like SQL: you can run it interpreted, or you can let the planner see the whole graph and optimize.

Jenny: Got it. But you said the win is co-design. So even if I never touch the DSL, the runtime is built around the assumption that calls share structure.

Alex: Yes. And that assumption shows up in the runtime architecture. The CMU lecture's runtime diagram is small — a Server with an API server slash Tokenizer, a Detokenizer, and a Model Worker. The Model Worker holds three things: a memory pool, a radix tree cache, and an attention backend. That radix tree cache is the headline. The lecture's punchline on the very first half of its content is — and I'll quote — "Existing systems: discard KV cache after an LLM call finishes. Ours: maintain the KV cache of all LLM calls in a radix tree, a compact prefix tree."

Jenny: Wait. Discard? vLLM doesn't discard, vLLM has prefix caching.

Alex: Modern vLLM does. The line in the lecture is making the historical case — the original framing when SGLang launched in January 2024 was against a world where most engines threw the cache away when a request ended. Prefix caching in vLLM has caught up significantly. We'll come back to that caveat when we get to benchmarks because it matters a lot for how you read the headline numbers. But the structural point still holds: SGLang treats the cross-call cache as a first-class data structure with a router and a scheduler aware of it, not as a flat hash table bolted onto the side.

Jenny: Okay, before we dive into the data structure — give me the scale. Is this a research toy or do real people run this?

Alex: Real people run it at extraordinary scale. The CMU lecture says SGLang serves the production and research workloads at xAI on a hundred-thousand-plus GPUs. The README puts the broader number at over four hundred thousand GPUs worldwide and trillions of tokens in production each day, with users including xAI, AMD, NVIDIA, Intel, LinkedIn, Cursor, Oracle Cloud, Google Cloud, Microsoft Azure, and AWS. Four hundred-plus OSS contributors. This is not a research artifact.

Jenny: Okay that's serious. And the version history?

Alex: The version history is actually the cleanest way to see what the project has invested in. v0.1 in January 2024: 5x higher throughput with automatic KV cache reuse, and 3x faster grammar-based constrained decoding. v0.2 in July 2024: 3x higher throughput with a low-overhead CPU runtime. v0.3 in September 2024: 7x faster Triton attention backend for custom attention variants — that's DeepSeek's MLA — and 1.5x lower latency with torch.compile. v0.4 in December 2024: a zero-overhead CPU scheduler, structured outputs, a cache-aware load balancer, and the fastest DeepSeek inference. Read it in order: KV reuse, then CPU scheduling, then MoE and MLA acceleration, then cluster-level cache awareness. Each version solves a different bottleneck.

Jenny: It's like reading a profiler trace over twelve months.

Alex: That's exactly what it is. Each major release is "we got the GPU saturated, now what's the next biggest bar in the flame graph." And the four major techniques the CMU lecture singles out map onto that history: RadixAttention, cache-aware load balancing, zero-overhead CPU scheduling, and hierarchical KV cache. Plus structured outputs as a fifth thread.

Jenny: Okay, let's go to RadixAttention. This is the headline. Walk me through it slowly.

Alex: Slowly is the right speed. Let me start with why this is interesting at all. The CMU lecture frames the KV cache itself in three lines: it's some reusable intermediate tensors, it can be very large — over twenty gigabytes, larger than the model weights themselves — and it only depends on the prefix tokens.

Jenny: That last line is the whole game, right? Because if it only depends on the prefix tokens, then any two requests that start with the same prefix can share KV state for that prefix exactly.

Alex: Exactly. KV state is content-addressable by token sequence. If your system prompt is two thousand tokens and ten thousand users hit it today, in principle you compute the KV for those two thousand tokens once and serve all ten thousand users from it. PagedAttention gave us the memory layout — the cache is paged in fixed-size blocks so it doesn't fragment. Prefix caching, the way vLLM does it, gave us a hash-keyed lookup so two requests with the same prefix can share blocks. RadixAttention takes a step further: instead of a flat hash, it organizes every cached prefix into a tree.

Jenny: And the tree is a radix tree specifically. Why a radix tree and not a regular trie?

Alex: A radix tree compresses chains. The launch blog's exact wording is that RadixAttention is a space-efficient prefix tree where edges can be labeled with sequences of elements of varying lengths. So if you have a long unique suffix that doesn't branch, it lives on a single edge instead of one node per token. That keeps the tree shallow and cheap to walk. Per-node detail from the implementation walkthrough on sugiv's blog: each TreeNode holds children as a defaultdict keyed on token ID, an optional value tensor for KV contents, plus last_access_time and hit_count for eviction bookkeeping. Prefix matching is the obvious tree walk: descend by token ID until the next token diverges. Complexity is O of prefix length.

Jenny: Wait. Where do the actual KV tensors live? They can't be in the tree node on the GPU side because that'd shred your memory.

Alex: Great question, and this is the elegant part. The launch blog says the KV tensors are stored on the GPU in paged layout — one token per page in their description — and the tree structure itself lives on the CPU with minimal overhead. So the tree is a CPU-side index into GPU-side paged blocks. That's why it's compatible with continuous batching and paged attention out of the box — the launch blog says that explicitly. RadixAttention isn't replacing PagedAttention. It's the index over PagedAttention's pages.

Jenny: Okay, that's the moment it clicked for me. PagedAttention is the page table. RadixAttention is the directory tree on top of the page table.

Alex: That's exactly it. Or to your point earlier — PagedAttention was virtual memory paging inside a single process. RadixAttention is a shared filesystem cache across processes, where every "process" is a request and the "files" are KV blocks indexed by their content.

Jenny: Okay, walk me through what an insertion looks like. Like, request comes in. What happens.

Alex: The CMU lecture has a five-frame animated example I love. Frame one: tree is empty. Frame two: a request arrives — "You are a helpful assistant. User: Hello. Assistant: Hi." — and the tree is now a single chain from root to leaf, with the KV blocks for those tokens sitting in GPU memory. Frame three: a second request comes in that's the same system prompt and the same first turn, but then continues "User: Solve this problem... Assistant: Sure..." So we descend the tree, match the shared prefix, and extend the chain past the divergence point. The system prompt and first turn KV are reused — we never recompute them. Frame four: a third request shares only the system prompt and then asks something completely different. Now we walk down the system prompt portion, hit the point where this request diverges from the previous ones, and the tree branches. The system prompt is now a shared ancestor of two children. Frame five: memory pressure hits. We pick an idle leaf, evict it, free the GPU pages, and that node is gone. The lecture says the cache handles trees with hundreds of thousands of tokens.

Jenny: The eviction story is where I want to push. Because in any real cache, eviction policy is half the system. What's the policy?

Alex: LRU. The launch blog says it explicitly: least recently used eviction with recursive leaf-node eviction. The recursive-leaf framing is the part you need to internalize.

Jenny: Why? What's wrong with just LRU on the underlying blocks?

Alex: Because if you do LRU on blocks, you can evict an interior block of the tree while its children are still in use. And that breaks correctness — you can't serve a child from a tree where the ancestor's KV has been freed, because attention needs the full prefix.

Jenny: Right, KV is not freely composable. You need the whole chain.

Alex: Exactly. So the policy is: only ever evict leaves. That preserves the invariant that any path from root to a live node is fully resident in GPU memory. And it has a really nice emergent property — shared ancestors are sticky. As long as anything is descending from the system prompt, the system prompt's KV stays hot. The hot stuff stays hot for free, because the tree shape itself is the access pattern.

Jenny: That's basically how a buffer pool in a database works. Pages near the root of a B-tree stay pinned because everyone touches them on the way down.

Alex: Same intuition exactly. The tree shape is the access pattern, and LRU on leaves is the policy that respects it. Implementation walkthrough notes the bookkeeping is just last_access_time on each node, plus the cache-aware scheduler we'll get to in a minute that biases toward keeping nodes alive that have hot descendants.

Jenny: Okay. Numbers. What does this actually buy you?

Alex: The launch blog's headline is up to five times higher throughput versus the baselines, with the system outperforming every baseline on every benchmark tested. The CMU lecture restates it as the v0.1 milestone: 5x higher throughput with automatic KV cache reuse. Same nine workloads.

Jenny: Setup?

Alex: Llama-7B on a single A10G in FP16, twenty-four gigs. Mixtral-8x7B on eight A10Gs with tensor parallelism, also FP16. Baselines: vLLM v0.2.5, Guidance v0.1.8, and Hugging Face TGI v1.3.0. Workloads: MMLU 5-shot, HellaSwag 20-shot, ReAct Agent, Tree-of-Thought on GSM-8K, JSON Decode for Wikipedia extraction, Chat in short and long four-turn flavors, DSPy RAG, and LLaVA Bench.

Jenny: And the spread across those nine?

Alex: SGLang at 1.0 normalized throughput on every workload by construction. The second-best baseline ranges from about 0.94 — that's vLLM on Chat Long — down to about 0.03, which is vLLM on Tree-of-Thought.

Jenny: Wait, 0.03? Like thirty times slower?

Alex: Tree-of-Thought has extreme prefix sharing. It's literally a tree of generations from a shared root. If your engine doesn't share that root's KV across siblings, you're recomputing it for every branch. That's why the gap explodes there.

Jenny: And Chat Long is the closest case because the per-turn generation dominates the shared history.

Alex: Yes. The longer each turn's generation gets, the smaller the relative weight of the cached history. The implementation walkthrough actually gives a hit-rate table that makes this concrete — comparing vLLM PagedAttention to SGLang RadixAttention. Few-shot learning: vLLM 15 to 25%, SGLang 85 to 95%. Multi-turn chat: vLLM 10 to 20%, SGLang 75 to 90%. Code analysis: vLLM 5 to 15%, SGLang 60 to 80%. And then the honest case: single requests, with no sharing at all — both at zero, because there's nothing to share.

Jenny: Okay that single-request row is important. SGLang has nothing magic to give you when there's no prefix sharing.

Alex: Nothing. And the walkthrough flags that explicitly. It is not a free lunch over vLLM in general — it is a structural lunch over vLLM on workloads with structure.

Jenny: But hold on — those vLLM numbers, 15 to 25% on few-shot — was that against modern vLLM or v0.2.5?

Alex: That's the right pushback, and the launch blog's own caveat. The 5x headline was measured against vLLM v0.2.5, which predates vLLM's prefix-cache support. Modern vLLM is a much stronger baseline than that comparison reflects. The implementation walkthrough's tokens-per-second numbers are against vLLM v0.6.2, which is a more recent comparison and shows the gap closing somewhat — MMLU 5-shot 1,420 vs 4,250, that's 3.0x. Multi-turn chat 890 vs 4,180, that's 4.7x. JSON Decode 580 vs 2,900, that's 5.0x. Code generation 1,200 vs 3,600, 3.0x. Few-shot learning 650 vs 2,850, 4.4x. So the gap is still real on prefix-heavy workloads even against modern vLLM, but it's not the "thirty times" of the original v0.2.5 comparison. Same source reports first-token latency 53 to 73% faster across batch sizes one through thirty-two.

Jenny: Okay, so the rule I'm taking away: the more your workload looks like a tree with shared roots, the more SGLang's data structure pays off. Single requests, no benefit. Long unstructured chat, modest benefit. Agents, few-shot, ToT, structured output — that's where it crushes.

Alex: That's the rule the sources support. And it's the right intuition because the design is targeted exactly at structure.

Jenny: Alright, segment one was "what is it." Segment two was "the headline." Let's do the supporting cast. You said the lecture lists four major techniques and we've done one.

Alex: Four major plus structured outputs as a separate thread. The remaining three majors are cache-aware load balancing via SGL-Router, zero-overhead CPU scheduling, and hierarchical KV cache. The lecture itself marks the hierarchical-KV slide "Skipped," and the cited sources don't give us deep content on it, so I'll cover it briefly. The other two we'll go deep on, plus structured outputs at the end.

Jenny: Cache-aware load balancing first. Because honestly, the moment you have a tree-structured cache per replica, you have a sticky-session problem.

Alex: You see it instantly. And this is where infra people have an enormous advantage understanding SGLang, because you've shipped sticky-session load balancers before. Round-robin works for stateless services. The moment your replicas have local state — and a hot KV cache is local state — round-robin trashes that state by spraying related requests across replicas that don't know about each other.

Jenny: Right. If replica one has the system prompt cached and you send the next user request to replica two, replica two has to recompute the entire system prompt from scratch. You just paid for the cache twice.

Alex: Exactly. And the lecture quantifies this. Their v0.3 router was Round-Robin Data Parallel — not cache-aware. Annotated on the slide: "Not cache aware, ~20% Cache Hit Rate." Their v0.4 router is Cache-Aware Data Parallel, which introduces an Approximate Tree at the router level that mirrors the actual radix trees on the workers. Annotated: "Cache aware, ~75% Cache Hit Rate."

Jenny: Approximate tree. Why approximate?

Alex: Because the router can't synchronously know the exact contents of every worker's tree — that'd be an enormous amount of chatter for a router to do per request. Instead, workers send INSERT and EVICT messages up to the router as their local tree changes, and the router maintains an approximate copy. Implementation walkthrough says the router is in Rust and scores candidate replicas with — and the formula is very simple — score equals cache_hit_rate times two minus load_factor, then routes to the highest-scoring replica.

Jenny: That's nicely tunable. You're explicitly trading cache affinity against load. If a replica has the perfect prefix but is overloaded, the load_factor pulls you off it.

Alex: Right. And the head-to-head numbers from the lecture's table are striking. Workload with two prefixes — Prefix 1 routed to replicas one and two, Prefix 2 routed to replicas three and four. Round-robin throughput: 82,665 tokens per second, 20% cache hit rate. Cache-aware load balancer: 158,596 tokens per second, 75% cache hit rate. That's roughly 1.92x throughput from routing alone, with the underlying inference engine completely unchanged.

Jenny: Wait. Same engine, same workload, and just by changing the routing layer, you almost double throughput?

Alex: Almost double. Because the routing layer is what determines whether the engine's cache hits or misses. The implementation walkthrough corroborates with an aggregate number: 1.9x throughput improvement and 3.8x higher cache hit rates with the load balancer enabled.

Jenny: This is the part that I think people underrate. Because everyone focuses on the engine. But for cached workloads, the routing layer is part of the cache.

Alex: It's part of the cache. The router is the L1 of cache locality. The replica's tree is L2. And if the router is dumb, your L2 hit rate collapses regardless of how good the engine is.

Jenny: It's also why this stuff is hard to deploy correctly. Because if your existing fleet is behind, say, an ALB or an envoy with hash-based routing on user ID — you might already have accidental affinity if a user always hits the same replica, but that doesn't help cross-user shared prefixes like a system prompt.

Alex: Exactly the point. Hash on user ID gives you per-user cache locality, which helps multi-turn chat. Hash on prefix content gives you cross-user cache locality, which helps system prompts and few-shot. SGL-Router is doing the second.

Jenny: Okay. I want to ask one more thing about the router. Approximate tree — it's eventually consistent with the workers. What happens when the router is wrong? It thinks worker three has a prefix it doesn't actually have anymore, because an EVICT message is in flight.

Alex: Then the router sends the request, the worker doesn't have the cache, and the worker recomputes the prefix locally. It's a cache miss. The system is correct, just less efficient for that one request. There's no correctness concern from approximation because the worker always has its own real tree as ground truth — the router's tree is purely advisory.

Jenny: Right, the router is just a hint, the worker is authoritative. That's clean.

Alex: That's the design. Okay, technique three: zero-overhead CPU scheduling. This one is wild and it's the v0.4 milestone. The lecture is blunt: an unoptimized inference engine can waste more than 50% of its time on CPU scheduling.

Jenny: Wait. Fifty percent? That seems impossible. The whole point of an inference engine is the GPU does the work.

Alex: That was my reaction too. Here's the chart. Llama 1.3B, comparing vLLM v0.5.4 to SGLang v0.3. Average iteration time. vLLM v0.5.4: about 32 milliseconds per iteration, of which roughly 16 milliseconds is GPU computation and 16 milliseconds is CPU overhead. Roughly 50/50. SGLang v0.3: about 17 milliseconds per iteration, of which 16 is GPU and 1 is CPU. The CPU overhead is essentially gone. Same GPU work, half the wall-clock.

Jenny: Okay so what is the CPU even doing for that long?

Alex: The lecture lists the jobs the scheduler has per iteration: receive input messages, stream model outputs, check stop conditions, maintain the radix tree and run prefix matching, and allocate memory for the next batch. None of those are individually expensive, but they all happen per iteration of the decode loop, and the decode loop iterates once per output token. So if you're generating five hundred tokens for a request, the scheduler runs five hundred times, and each run is a few milliseconds of bookkeeping that the GPU is sitting idle for.

Jenny: That's the bubble. The GPU finishes its kernel, waits for the CPU to figure out what to do next, then starts the next kernel.

Alex: That's the bubble. And the v0.4 fix is to overlap. Instead of a Blocking Scheduler — scheduler runs, model worker runs, scheduler runs, model worker runs, all serialized — you have an Overlapped Scheduler. The next-iteration scheduling runs concurrently with the current-iteration model work. By the time the GPU finishes step N, the next batch is already prepared.

Jenny: Wait. This is just CPU pipelining. You're doing the fetch-decode for instruction N+1 while the execute is running on instruction N.

Alex: That is exactly what it is, applied to the inference loop. The lecture credits the conceptual lineage to NanoFlow from Kan Zhu's group. The two design ideas the lecture calls out: first, resolve the dependency by delaying the stop-condition check — break the synchronous tie between detecting "this request finished" and dispatching the next batch, so the next batch can start without waiting. Second, use CUDA events and streams to do fine-grained scheduling.

Jenny: Hmm. The delayed stop-condition check is interesting. Because the obvious correctness worry is — what if you launch batch N+1 with a request that should have stopped at batch N because it generated an EOS?

Alex: Right, and the resolution is that the stop check still happens, but it happens off the critical path. You can dispatch the next batch optimistically including the request, and if it turns out the request stopped, you just don't sample its next token — or you sample and discard. The cost of one wasted decode for a stopping request is negligible compared to the cost of stalling the entire pipeline waiting to know.

Jenny: That's the speculative-execution trick. Run ahead, throw away the work if you guessed wrong.

Alex: Exactly. And speculation works here because the false-positive rate is low — most decode steps don't end in EOS — and the cost of being wrong is minuscule. The lecture's profiling result for the optimized scheduler is — and the wording is great — "Zero CPU time according to the nsight profiler." The trace shows 99.8% kernels and 0.2% memory, with no visible CPU bubble between kernel launches. The implementation walkthrough phrases the same idea at the API level: torch.cuda.Event marks GPU work boundaries, and CPU batch preparation overlaps with GPU execution via futures. GPU utilization moves from 78 to 85% under the non-overlapped scheduler to 95 to 98% under the zero-overhead one. And on a downstream Llama 3.2 3B benchmark on H100, SGLang v0.4 reaches about 5,500 output tokens per second versus a SOTA OSS baseline at about 4,100. That's the 1.3x faster than SOTA OSS line.

Jenny: 1.3x by removing CPU overhead. On top of all the other wins.

Alex: On top of everything. And it's a reminder that as your GPU kernels get faster — as the model gets smaller, or the batch gets shorter, or the kernel gets more optimized — the CPU overhead gets relatively bigger. So the pipelining trick wins more as the rest of the stack improves.

Jenny: That's the same dynamic we see in databases. As storage gets faster, the CPU becomes the bottleneck, and you have to start being smart about scheduling to keep the IO subsystem fed.

Alex: Same dynamic. And once you've removed that overhead, the GPU is doing what it's supposed to do, which is compute.

Jenny: Okay, structured outputs. Tell me about the FSM thing.

Alex: Constrained decoding. The use case: you want the model to emit valid JSON, valid YAML, regex-matching text, or something matching a grammar. The conventional approach, which the compressed-FSM explainer summarizes nicely: compile the grammar to a finite state machine. At each decode step, you know your current state, so you know the set of tokens that would keep you in the valid set. Apply a logit bias that masks out the rest. The FSM tracks state during decoding, so at every step you only sample valid tokens.

Jenny: Right, this is basically guidance / outlines / xgrammar, all variations on this theme.

Alex: All variations on this theme. The compressed variant — referenced in the explainer as Jump-Forward decoding using Compressed FSM — is described at a high level only in the cited sources; the explainer doesn't go deep on implementation, deferring to SGLang's own guide for the details. But the high-level idea is this: there are spans where the grammar is deterministic. If your JSON requires a comma between two fields, the comma isn't a sampling choice — it's forced. So why pay for the model forward pass to "decide" to emit it? Just emit it.

Jenny: Wait. So you're skipping the model entirely for forced spans?

Alex: For forced spans. The grammar tells you the next ten tokens are determined — say, the literal string `"name":` — so you advance the decoder by ten tokens without running the model. You jump forward.

Jenny: That's the analogy I love. It's a query optimizer constant-folding deterministic predicates. If you can prove the value at compile time, don't run the operator.

Alex: Same idea, applied to autoregressive decoding. And what the cited sources do tell us about magnitude on the structured-decoding axis overall: the v0.1 milestone was 3x faster grammar-based constrained decoding. v0.4 brings structured outputs as a flagship capability listed alongside the zero-overhead CPU scheduler. The implementation walkthrough reports a JSON-generation operating point of 4,200 tokens per second at 99.8% validity rate and 0.4-second latency, using SGLang plus xGrammar as the grammar engine. And JSON Decode for Wikipedia extraction is one of the nine workloads in the v0.1 headline benchmark where SGLang reaches 1.0 normalized throughput.

Jenny: Why does it compose so well with RadixAttention?

Alex: Because the schema is shared. If you're extracting structured data from a thousand documents, the schema and prompt prefix are identical across all thousand calls. RadixAttention caches the prefix; the compressed FSM accelerates the structured spans inside each generation. The two wins compound.

Jenny: Got it. And the hierarchical KV cache?

Alex: This is the one the lecture itself marks "Skipped." The cited sources don't give us deep content. What we know: the README mentions prefix caching and prefill-decode disaggregation as features. The open-source roadmap slide lists prefill-decode disaggregation and expert / pipeline / context parallelism under throughput-oriented large-scale deployment. The DeepSeek case study — which we'll get to in segment five — shows an "External KVCache Storage (Optional)" tier in the architecture. The intuition, which the sources support but don't elaborate, is that you have a tiered buffer pool for KV state. Hot tier in HBM. Warm tier in host RAM. Cold tier on RDMA-attached storage.

Jenny: Same as a database buffer pool.

Alex: Same as a database buffer pool. HBM is your shared buffers, host RAM is OS page cache, RDMA storage is your disk. When KV evicts from HBM, instead of dropping it on the floor, it spills warm. When it evicts from warm, it spills cold. And on a future request whose prefix matches something cold, you pull it back up the tiers instead of recomputing it.

Jenny: This matters when recomputation is more expensive than network. Which for big prefills it definitely is.

Alex: Exactly. A two-thousand-token prefill at decent batch size is way more expensive in compute time than reading the KV from a fast network store. So if you can keep the cache around — even cold — you save real money. That's the spirit. The sources don't give us the tier sizing or transport details to go deeper, so I won't invent them.
